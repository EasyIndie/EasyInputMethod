# 开发与迭代工作流（Development Workflow）

> 目标：**单人也快、质量不降、成熟后平滑支持多人共建**。
> 本文是工作流与 CI 分层的权威说明；配套 `AGENTS.md`（铁律/验证）、`CONTRIBUTING.md`（提交规范）、`.github/workflows/`、`Makefile`。相关决策见 ADR-072、ADR-246/248/250。

---

## 1. 原则

1. **一个门禁**：`make verify` 是"可提交"的唯一标准，本地与 CI 等价。
2. **分层**：PR 跑"快"，`main`/夜间跑"全"；重活不挡内环。
3. **单人降级、团队升级**：同一套 workflow，靠分支保护 / 标签 / `CODEOWNERS` 开关切换，不重搭。
4. **铁律自动化**：能机检的绝不靠自觉（网络 / 配置 / unsafe / 许可 / DCO）。
5. **小步、可验证**：一次一个改动；删代码优于加代码（`AGENTS.md` §11）。

## 1.1 迭代与PR收尾（ADR-246）

固定分支约定以ADR-248细化：项目只保留main合入基线与dev活动迭代分支；历史恢复点在独有改动确认归并后清理。

1. **先完成本地迭代，再创建PR**。从现有任务卡选一个可独立验收的改动，统一在固定`dev`内完成实现、定向测试、必要文档与证据；提交保持单一目的，但不为每次提交、试验、验收记录或HANDOFF另开PR。先检查现有开放PR，能在同一范围继续完善就复用，不另开重复PR。
2. **控制同时开放的数量**。默认只使用固定`dev`作为活动迭代分支，`main`仅为合入与打包基线，不按任务开分支；每批`dev → main`一次推进一个待合并PR；范围稳定且`make verify`通过后再创建。没有实际并行评审需要，不提前开草稿占位。除用户明确另行要求，不另建feature/fix/docs分支；合并后同步main并继续复用dev，避免把后续PR堆在未合并分支上。
3. **创建者负责跟进到最终处置**。持续检查当前精确head的所有要求检查、冲突和评审；失败先定位修复，更新后等待新检查，不沿用旧head的绿灯。门禁通过并具有授权后完成合并，回读远端状态及main提交；仅推送、开PR或CI通过不算该轮交付完成。
4. **暂缓或被替代就明确关闭**。先保留独有证据、分支与精确提交，在原任务卡记录恢复条件，再关闭PR；不为消除积压合入未完成能力，不把历史HANDOFF覆盖当前状态。依赖PR合并后，必要时调整base并复核实际diff与新检查。
5. **阻断要具体，不遗留无人跟进的PR**。权限/审批确实阻止合并时，说明被阻止的具体PR和动作、原因及所需授权，记录下一步。可以继续不依赖它的本地工作，不能因此不断创建新的待合并PR，也不能绕过受保护main。交接须列出每个仍开放PR的负责人、当前head/检查状态、阻断和下一步；没有开放PR也明确记录。
6. **规范/交接不制造新的碎片PR**。纯交接、验收收尾或规范记录可先在固定dev验证并提交，明确尚未入main，随下一批相关必要改动一并审阅；必须在HANDOFF记录未发布提交和承接事项。仍遵守main受保护、合入走PR，不默认获得直推权限。
7. **验收包只认已合并main的精确来源**。从干净的main提交构建统一签名包，记录源码提交、构建运行、ZIP/执行/词表SHA及安装身份；存在未合并功能时逐项说明不在包内。功能分支的ad-hoc包仅作内部验证，不能冒充统一包；包已构建、已安装、已验收分别记录。
8. **减少用户重复劳动**。开发者先完成自动回归、隔离预览和包身份核验，再集中交付范围稳定的包。已验收项保留原证据，只因本次代码/数据/宿主链路影响才安排相关复验，事先说明变化、原因和操作；不因文档、PR归档或单次工具失败让用户重跑全套。历史PASS仍绑定原候选，不能直接移给新包；锁定最终RC后按既有完整验收执行。

本节是PR与迭代收尾的权威约定，`AGENTS.md`、`CONTRIBUTING.md`和迭代计划引用此处，避免分别演化出多套流程。

## 1.2 当前选择：固定dev的小批次集成（ADR-250）

这是针对单人维护的GitHub Flow适配：**固定dev开发 → 本地验证 → 一个dev→main PR → 当前head检查 → merge commit → main出包 → 受影响验收 → 原问题结案**。只复用dev，不按任务增加分支；不引入release/hotfix常驻分支或另一个执行队列。

### 日常执行

| 阶段 | 完成条件 | 留下什么 |
|---|---|---|
| 选任务/接反馈 | 复用现有任务卡，明确一个可独立验收的目标；先去重 | 卡片引用，必要时关联外部Issue |
| dev实现 | 最小复现、ADR（需要时）、代码/数据及定向回归完成 | 单一目的DCO提交；不靠PR占位 |
| 创建PR | 本地make verify全绿，必要平台构建/证据已收齐，范围稳定 | 一份最终范围说明、验证和未决项 |
| CI与评审 | 当前精确head全部要求检查通过；只追加必要修复 | 创建者负责跟进，不用旧head结果 |
| 合入 | 具备授权，使用merge commit；确认远端MERGED | main精确提交；dev快进同步 |
| 出包/验收 | 自动检查先完成；确需用户验收才交付已合入main的签名包 | version/build/source/run/ZIP/执行SHA及范围 |
| 反馈结案 | 回填原卡/Issue；产品问题所需实机证据完整 | 未完成实机时保留“待验”，不能以合并代替解决 |

同批相关实现、文档、证据一起收拢，不按提交数量、每次试验或HANDOFF分PR。PR已开后冻结无关改动，避免每次补一条记录都重启重型CI。需要切换优先级时在原卡记录断点、处置现有PR，再顺序切换；默认不并行堆积。

### 固定dev的合并与同步

GitHub官方提醒长期分支squash后继续复用，后续PR可能重复出现旧提交并增加冲突，因此本项目使用**merge commit**，保留每个有意义提交和祖先关系：[官方说明](https://docs.github.com/en/pull-requests/reference/pull-request-merges#squashing-and-merging-a-long-running-branch)。不启用要求线性历史的规则，不squash/rebase合并，不以force push修复分叉。

每轮先确认工作树干净并fetch；dev以`git merge --ff-only origin/main`同步。PR合并时用`gh pr merge <编号> --merge --match-head-commit <已核验HEAD>`；合并后再次fetch、在dev执行`git merge --ff-only origin/main`及`git push origin dev`。快进失败立即核对独有提交，不能reset丢弃本地工作。禁止合并时删除dev。

远端当前允许merge/squash/rebase，但项目约定仅用merge；auto-merge与自动删分支均关闭。main保护已要求check/macos/fuzz及分支最新、禁止强推/删除；DCO仍须按项目约定通过。此文不表示已调整远端设置，也不授予绕过权限；实际审批阻断按§1.1记录。

### 任务、反馈与验收

- `docs/tasks/`为唯一执行队列，ROADMAP是索引，HANDOFF是当前状态；GitHub Issues只作外部反馈/讨论入口，链接已有卡片和修复PR，避免重复创建同一任务。当前不另建需手动同步的Projects看板。
- 每个缺陷记录产品版本/build、安装来源/源码或诊断信息、系统/架构/客户端、输入模式、最小复现与预期/实际；只使用可公开的样例，不收真实聊天或整份个人词库。
- 区分“工程完成/待装包/待用户验收/已验收”，只有无需实机的任务可以在自动验证后直接完成。用户确认、权限/设备、五工作日等待单独记录，产品反馈不要用Closes误关；先关联，确认所需出口后结案。
- dev本地ad-hoc仅开发；统一验收包从干净main出，包已构建/已安装/已验收独立记录。文档变更不重测输入；变更影响到的路径定向复验；最终RC完整验证仍绑定同一候选。
- 内环使用现有make fast/macOS隔离入口；提交仍make verify，CI不降级。多人并行、PR排队或维护多个正式版本确有需要时再评估额外流程，不提前增加管理成本。

来源：[GitHub Flow](https://docs.github.com/en/get-started/using-github/github-flow)、[分支保护](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)。固定dev是本项目适配，官方Flow通常使用短期任务分支。

## 2. 分层 CI

| 层 | 触发 | 内容 | 目标时长 | 现状 |
|---|---|---|---|---|
| **check（fast）** | 所有 PR / push | fmt + clippy + test + deny + `verify-no-network` | ≤2 min | ✅ 已实现 |
| **heavy（条件）** | PR 命中 `crates/` `platforms/` `fuzz/` `tools/` `data/` `packaging/` 等 | macos 全量构建 + 预览冒烟；fuzz 短跑 | ~4 min | ✅ 已实现 |
| **post-merge** | `main` push | 重型检查 + 验收出包（`macos-acceptance.yml`） | ~5 min | ✅ 已实现 |
| **nightly** | 定时 | 长 fuzz、`cargo deny advisories`、基准趋势 | — | ⏳ 待办（MVP 后） |
| **on-demand** | `workflow_dispatch` | 出包、Pages、release dry-run | — | ✅ 已实现 |

**关键细节**：分支保护的必需检查是 `check` / `macos` / `fuzz`。若"路径不相关"就**跳过整个 job**，会让必需检查停在 `Expected` 而卡住合并。因此重型 job **始终运行并上报成功**，只把**具体 step** 条件化：

- `scripts/ci-detect-code-changes.sh` 判断本次 PR 是否"代码相关"（docs-only → `false`）；
- `macos` / `fuzz` 的每个重型 step 带 `if: steps.changes.outputs.code == 'true'`；
- `push` 到 `main` 一律视为代码相关（重型全跑）。

## 3. 单人提速

| 手段 | 说明 |
|---|---|
| `make fast` | 内环：`fmt-check + clippy + test`（不含 deny / 隐私断言），小改动秒级反馈 |
| `make verify` | 外环：提交前完整门禁 |
| `make hooks` | 安装 `pre-push` → 自动跑 `make verify`，失败前移（`git push --no-verify` 可临时跳过） |
| `make macos-dev` | 重建并启动唯一身份隔离窗口，私有配置/词库，复用正式菜单；关闭后重跑即可迭代 |
| `make macos-ui-snapshots` | 离屏渲染候选/关于/设置/诊断面板（亮暗 + 固定样例）到 `platforms/macos/build/ui-snapshots/`，附帧/留白报告；`UI=candidate` 只渲候选窗以少编译一半源码；未改源码时秒级复用上次二进制 |
| `make macos-preview` | 历史独立调试窗口，使用真实配置；不作为日常隔离入口 |
| auto-merge | 已有合并授权且门禁允许时可用 `gh pr merge --auto`；仍须跟进最终状态，失败或关闭自动合并后不能放置不管 |
| 固定 dev | 固定dev顺序迭代并同步main；稳定后dev→main，合并后继续复用dev，main保持受保护 |

### 不注销也能看到效果的验收（推荐先做）

| 档位 | 命令 | 能看到什么 | 代价 |
|---|---|---|---|
| ① UI 快照 | `make macos-ui-snapshots` | 候选窗 4 形态 / 关于 / 设置四分区 / 诊断，亮暗各一套；终端同时打印帧、留白、快捷键文本 | 秒级，不显示窗口，不碰真实配置 |
| ② 隔离实窗 | `make macos-dev` | 同一个 `CandidateWindow`/`SettingsPanel`/菜单组件 + 真实 Rust 会话 + 私有配置（因此能看到**默认**绑定与候选行为） | 一个自建窗口，关掉即清理 |
| ③ 固定开发 IMK | `make macos-imk-dev ACTION=install APP=<签名开发包> ARGS=--stop-host` | 固定身份下的真实系统输入法链路（IMK、marked text、真实客户端焦点、系统菜单） | 首次发现输入源可能需注销；同一设备后续同身份换包已在 B 机实测免注销，仍须核对新执行 SHA/宿主身份 |
| ④ 正式包发布验收 | `make macos-clean-install APP=<最终RC>` | 正式安装、升级/恢复、最终候选的跨应用与系统验收 | 按最终候选流程注销/重新登录一次；不用于日常每轮调试 |

第 ①② 档不碰 `~/Library/Input Methods/`、不切输入源、不改真实配置，适合改一版看一眼。③用于真实 IMK 开发，固定身份和私有数据根见 [ADR-230/报告106](reviews/106-stable-imk-development.md) 及 `.agents/skills/iterate-macos-ime/SKILL.md`；它不等于最终 RC 验收。B 机已证实固定源启用时换入不同执行 SHA 可不注销，但这只覆盖该设备/身份，A 机仍须独立验证。首次添加/系统未发现输入源时按系统要求手工处理，不能用 TIS 返回码代替实际选中状态。④只在候选锁定后执行；不要把旧 `macos-fast-reinstall` 的移除/添加流程用于固定开发源的每轮换包。

**隔离边界提醒**：`make macos-dev` 会建立私有数据根并以该入口启动预览；不要从 Launch Services、Computer Use 应用清单或 Finder 直接启动 `platforms/macos/build/.../LampyrisPreview.app`。独立预览包本身不会自动获得隔离环境，直接启动会回退到真实 `~/Library/Application Support/Lampyris`，包括写入个人词库。需要交互验收时只用 `make macos-dev` 或明确创建私有根的验收包装器；构建脚本 `dev-preview.sh --build-only` 仅用于编译，不是安全的交互启动入口。

### 单人最短反馈环

按改动风险走最短而完整的环路，避免每个小改动都重跑整套桌面验收：

1. 从一张现有任务卡开始，先写一个最小输入/显示/提交例子和预期；数据先走 `add-data-source`，用户可见行为或协议先追加 ADR。
2. Rust/状态逻辑先用失败回归证明问题，再用 `make fast` 内循环；macOS UI 用 `make macos-ui-snapshots UI=candidate` 和 `make macos-dev`，不进系统 IMK 安装链。
3. 每个行为改动完成后只跑受影响的定向测试；跨 Swift/FFI 或生成数据的改动再跑相应 `make macos-offline-tests`、strict 构建或可重复生成核对。提交前仍必须 `make verify`，不以提速为由跳过。
4. 只有触及 IMK 生命周期、预编辑、真实焦点、系统菜单或客户端兼容时，才换入固定开发签名包。先记录源码提交、zip/执行 SHA、私有根和源状态；验收后保留原包回退并复核配置/词库摘要。UI 自动化前置被拒时记 `BLOCKED`，不要重复尝试、绕过 TCC 或因此把未运行场景算失败。
5. 原生场景逐项留痕并绑定同一包/环境。一个探针只验证一个可判定问题；候选可见性与亮暗 HUD、第二屏等不同变量分开采集。候选显示、数字选词和最终文本要在同一个组合中对应起来。
6. 结果回流原任务卡；当前状态只更新 HANDOFF，历史报告保留原结论并追加后续证据。遇到外部等待/权限阻断时继续不依赖它的工程工作，不复制任务卡或新建平行验收框架。

本轮流程复核发现 `run-installed-hud-probe.py` 把候选面板、HUD、亮暗切换和可选第二屏合并，并在创建夹具/输入前要求 System Events UI 脚本可用；因此 `-10827` 会连独立的候选可见性证据也挡住。后续改探针时应复用此卡/报告，将“只读面板枚举”与需要 UI 自动化的状态/HUD 流程拆开，并允许以精确开发包可执行路径/PID核验宿主；不降低当前焦点与窗口所有权守卫。此项属于工具流程改进，不是已确认的产品窗口缺陷。

### 本地验收内环（ADR-182）

在当前功能分支的仓库根运行`make macos-dev`。窗口中的“输入法菜单”复用正式InputStateMenu，可以点验四状态文案、模式父子入口及快捷键显示；“偏好设置”使用正式生产面板。输入区、模式下拉框、菜单、设置及快捷键共享真实Rust会话与本轮私有配置。关闭窗口，或回到启动终端输入`close`结束；修改代码后重新运行命令重建，不依赖热重载。

每轮创建独有临时应用/配置/词库，正常退出清理自己的资源，失败保留证据；正式输入法不替换、输入源不切换、真实数据不回写。初次编译可能较慢，后续Rust使用增量缓存，Swift仍重新编译。各轮私有设置默认不保留，便于重复固定场景。

按改动运行定向回归：菜单`python3 platforms/macos/tests/test-input-menu.py`、隔离菜单/会话`python3 platforms/macos/tests/test-preview-menu.py`、设置`python3 platforms/macos/tests/test-settings-presentation.py`、学习`python3 platforms/macos/tests/test-wubi-learning.py`。Rust内环用`make fast`；提交前`make verify`，平台改动再跑`make macos-offline-tests`。本地一批修正稳定后再推送/公证/安装最终包，复验系统菜单IMK代理、跨应用焦点与VoiceOver等差异。

### 实机（真实 IMK 菜单）验证守则

系统输入法菜单与隔离窗口是两条链路，前者必须在真机上验证。踩过的坑与固定做法：

1. **先按键激活**。菜单只有在该输入法控制器被当前客户端激活后才包含产品项；未激活时读到的是系统通用菜单。读菜单前先在文本框里按一次普通字符键。
2. **不要在同一次登录里热替换 bundle**。停宿主→换 `~/Library/Input Methods/Lampyris.app`→手动启动→注册，之后源/菜单会间歇性失效，只能重登恢复。需要换包时：装好再登录，一轮只测一个包。需要「以默认行为为起点」验收默认值时，用 `platforms/macos/uninstall.sh --input-source-removed --purge-data` 把旧包与旧配置/词库一起移入 `uninstalled/`（移动而非删除），重登后再装新包；预检用 `--dry-run --purge-data`，它不要求先退出宿主。
3. **每次采 A/B/A 对照**。正式包 → 候选 → 正式包，三次都用同一脚本采集；正式包第二次读数不恢复即说明环境漂移，本轮数据作废。
4. **顶层阳性对照**。每轮至少点一次顶层「关于」或「设置」，证明命令链路本身可用。
5. **只改一个量**。模式/菜单类改动不要与快捷键、布局、签名同时变；一次只验证一件事。
6. **记录平台特殊键**。`⌃.` 会被系统当作取消键吞掉，需 `⌃⇧.`；菜单只渲染纯标题与真实快捷键（自定义 view/badge 会被 IMK 丢弃）。
7. **恢复顺序**：先还原 `mode` 与输入源，再换回正式包，最后核对 `config.toml` 字节、词库 SHA 与宿主 PID。任何一项不一致就停下重登，不要继续叠加动作。

现成的只读探针（AX 读取、坐标点击、合成按键、TIS 查询）见 `platforms/macos/build/*/tools/`；改动探针时同步回 `tools/macos-probe/`（待 P6 落地）。

## 4. 质量保障

**已实现**

- 分支保护必需检查 `check` / `macos` / `fuzz`；`main` 禁强推 / 禁删除。
- 解析器 fuzz（3 目标）与每周 `cargo deny advisories`（`security.yml`）。
- 可复现构建 / SBOM / SHA（`macos-acceptance.yml` + `packaging/macos/`）。
- `verify-no-network.sh`（铁律 1）；PR 模板含铁律自检清单。
- DCO 校验（`dco.yml`）：**可见但不阻断**，团队化后设为必需。

### 零诊断门禁（0 警告 0 错误）

**规矩**：任何工具链诊断（`cargo` / `rustc` / `clippy` / `cargo-deny` / `swiftc`）在迭代过程中都必须为 **0**；有诊断就当成失败修掉，不往下一件事推进。

**怎么保证**：

- `scripts/check-clean.sh` 包住 `make lint / test / deny / fast / verify`：输出原样转发，同时扫描 `warning:`、`error[x]`、`bug[…]`、`path:line:col: warning:` 等诊断形态，命中则以非 0 退出。
- CI 的 `check` job **直接调 `make lint / test / deny`**（不再自己拼命令）→ 门禁只有一份实现，不会漂移；`macos` job 跑 `make verify`，同样受管。
- `clippy` 用 `-D warnings`；Swift 宿主（`build.sh`）与调试窗口（`dev-preview.sh`）的 `swiftc` 加 `-warnings-as-errors`。
- 为什么需要 `check-clean.sh`：`cargo test` / `cargo deny` **有警告时仍返回 0**，clippy 的 `-D warnings` 也管不到 cargo 自己打印的告警（如 "output filename collision"）。

**不影响迭代效率**：门禁只是「同一次运行 + 一次 grep」，**不额外编译**；`make fast`（fmt-check + clippy + test）仍是秒级内环；macOS 宿主构建、数据复现、打包这些重活仍然只在 CI 的 `macos` job（或按需本地跑）。

**已知三个坑**（都已修，别重踩）：内部路径依赖要在 `[workspace.dependencies]` 里**显式写 `version`**，否则 cargo-deny 会把 `workspace = true` 判为通配符 / 解析失败（`bug[…]`）；`deny.toml` 的许可清单是**政策**而非当前集合，故置 `unused-allowed-license = "allow"`；两个 crate 的同名 example 会触发 cargo 的 output filename collision，需用 `[[example]] name = …` 或改名。

**待办（MVP 完成后）**

- 覆盖率上报（`cargo llvm-cov`，软阈值，不作硬卡）。
- 基准回归：把稳定的 `run-perf.sh` 作基线，夜间对比阈值并告警。
- fuzz 语料入库 + 长跑；崩溃自动建 issue。
- `nightly.yml`：长 fuzz + advisories + 基准趋势。
- 依赖机器人（Dependabot/Renovate 分组；Actions 仍**必须钉 SHA**，见 `CONTRIBUTING.md` §9）。

## 6. 面向多人共建（开关表）

同一套流程，随团队规模"开开关"，**不重写 CI**：

| 能力 | 单人（现在） | 团队（成熟后） |
|---|---|---|
| 合并 | PR + 必需检查；本地改动按完整范围收拢 | 必需 review + `CODEOWNERS` + dismiss stale |
| 队列 | 无 | **merge queue**（多 PR 竞争时） |
| CI | `check` 必跑 / 重型条件 | 重型全跑 + 分平台矩阵（P3+） |
| fuzz/bench | 夜间 | 夜间 + 门禁阈值 |
| 依赖 | 手动 / Dependabot 分组 | Renovate + 自动合低风险 |
| DCO | 可见不阻断 | 设为必需检查 |
| 发布 | `git tag` 手动 | release train + 自动 changelog |
| 治理 | — | 标签 / 里程碑 / `good first issue` |

**团队化首批动作**（有外部贡献者时）：加 `.github/CODEOWNERS` → 分支保护加"必需 review" → 开 merge queue → 把 `dco` 设为必需检查。
