# MVP 后执行计划（批次与顺序）

> 2026-11-03 整理。把 ROADMAP 里 v1.0.0 之后的散项收成**批次**，明确哪些能合并、按什么顺序做、每批的完成标志。
> 里程碑级目标见 [MVP后里程碑](MVP后里程碑.md)；本文件只管"怎么排、怎么合"。

## 0. 版本口径（先定，避免后续混乱）

| 版本 | 允许装什么 | 不允许装什么 |
|---|---|---|
| **1.0.x** | 缺陷修复、安全、安装/恢复问题 | **任何改变候选顺序/键位行为的东西**（否则用户无法用版本号区分手感变化，回滚困难） |
| **1.1.0** | 候选排序质量（ADR-304 P0/P1 + 简码数据） | 平台扩展、拼音后端替换 |
| 之后 | 按证据立项 | — |

## 2. 能合 / 不能合的判断

**应该合（同一行为面，一次换包）**
- 简码入表 ＋ 位次上移：都改"候选顺序"，分两次出包等于让用户把同一个手感问题体验两遍。
- IT-25 ＋ IT-22 受影响行 ＋ 更新器自更新：三件都要求"新签名包装机操作"，一次换包做完最省。
- 简码表（D17）＋ 任何五笔数据再生成：同一条生成链，不应分两次动 `data/generated/`。
- 功耗/冷加载基线 ＋ 样本集基线：都是"只测量不修改"，同一轮在 1.0.0 上做掉。

**不能合（会互相掩盖或扩大回滚面）**
- 排序改动塞进 1.0.x 补丁：版本号失去语义，出问题无法回到"只修 bug"的状态。
- 拼音 FSA／整句 与 五笔排序同批：失败时无法区分是谁引起的质量变化。
- 平台扩展与 macOS 质量同批：宿主层问题会污染核心引擎的回归结论。

## 3. 执行顺序与理由

```
A 发布收尾 ──┐→ B2（1.0.1：设置项一致性 + 升级闭环）──┐
             │                                        ├─→ C（1.1.0：简码 + 位次上移 + 三项装机复验）─→ D ─→ E / F / G
B 基线采集 ──┴──────────────────────────────────────┘
```

1. **A 先做**：更新器自更新、IT-25 原生验收都需要"有一个已发布的正式包"作为起点。
2. **B 与 A 并行**：基线必须在**未改排序**的 1.0.0 上采集，否则事后无法证明改善；且不需要换包，不占用试用期。
3. **C 内部顺序**：数据生成（D17 简码表 + 校验脚本）→ 核心位次上移 → 一起出 1.1.0 候选 → 装机复验（先 IT-25，再 IT-22 受影响行，最后样本集对比 + 升级闭环）。
4. **C 的回归面要提前列清**：简码入表会改变所有 1–2 码输入的行为，至少覆盖 `test-composition-navigation`、四码唯一自动上屏、混输兜底位置、`wubi_single_order_*` 旧用例（需重写）、以及"三级码"不受影响。
5. **D 不预设**：只有 C 的样本集仍显示明显"非首选选择率"时才做，一次一项。
6. **E/F/G 按需**：没有第二个用户/需求之前不动平台扩展。

## 4. 1.1.0 的验收口径（比 MVP 轻，但比补丁重）

MVP 的 IT-23 是"五工作日"仪式；排序改动直接影响手感，建议 **1.1.0 装包后自用 3 天再 tag**（不是 5 天），依据是：
候选顺序变化可以立刻用样本集量化，日常试用的边际收益低于首版；但**"换包后确认新二进制"**这条依然必须做（报告 220 教训）。

必过关卡：
- `make verify` + 离线回归零诊断
- 简码校验（25/625 计数、键位唯一、每字全码一致）
- 样本集四项指标：平均按键数、翻页次数、非首选选择率、错字率（不得劣化，简码项必须改善）
- 两台设备同包、升级路径 PASS、更新器自更新闭环
- 文档同步：`技术方案.md` 简码行、`发布说明.md`、ADR-304 状态改"已实施"

## 5. 不做（防止范围膨胀）

云同步 / 账号 / 打字统计 / 剪贴板 / 皮肤 / AI 写作 · 简码以外的新输入方案（R6 需明确需求）· 新增配置项（证据不足不加，尤其"固定顺序"开关）· 把候选排序改动塞进 1.0.x。
