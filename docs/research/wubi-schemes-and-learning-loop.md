# 五笔原理、编码方案对比、当前实现评估与「学·练·用」一体化设计

> 2026-11-06 整理。研究/设计文档，**不是**已批准的实施计划；任何落地改动先写 ADR。
> 结论的事实依据以仓库代码与数据为准（给出文件与命令，可复现）。

## 0. 一页结论

| 问题 | 结论 |
|---|---|
| 编码规则实现对不对 | **86 版的四条取码规则与末笔字型识别码实现正确**，与公开 oracle 对照 GB1 达 99.98%（`data/generated/wubi86-core-report.txt`） |
| 最大的能力缺口 | **二级简码（625 条）与三级简码（4,400+ 条）完全没进表**：2 码、3 码输入目前只能是"前缀 + 词频"，与老五笔手感差异最大。这是"输入效率"的第一优先级 |
| 数据层的隐性债务 | 简码行直接套用**全码权重**；词频来自 WindInput（D3）与 jieba（D10）拼接，不是真实输入语料；评测样本仅 200 条 |
| 多方案（98/新世纪/郑码） | 成本不在引擎，在**数据 + 规则 + 教学**三件套；建议先抽 `Scheme` 抽象，再用**一个**方案（98 或郑码）验证成本 |
| 学练用一体 | 关键不是加 UI，而是先有**结构事实库**（ADR-189）作为唯一数据源；练习/教学都从它生成，输入热路径不许被拖慢，也不许引入遥测 |

## 1. 五笔输入法原理

### 1.1 键盘分区与字根

- 25 个字母键（`z` 不作字根键，传统上留给"查询/万能键"），按**首笔笔画**分 5 区、每区 5 位：

| 区 | 笔画 | 键（位 1→5） |
|---|---|---|
| 1 | 横 | G F D S A |
| 2 | 竖 | H J K L M |
| 3 | 撇 | T R E W Q |
| 4 | 捺/点 | Y U I O P |
| 5 | 折 | N B V C X |

- 约 130 个字根按"首笔定区、次笔/笔画数定位"排入键位；**字根表是方案的身份证**——86/98/新世纪的第一处差异就在这里。

### 1.2 单字取码（86 版）

| 类型 | 规则 | 例子 |
|---|---|---|
| 键名字 | 连打该键 4 次 | 王 `gggg`、水 `iiii` |
| 成字字根 | 报户口（键）+ 首笔 + 次笔 + 末笔 | 五 `gghg` |
| 成字字根（2 笔） | 报户口 + 首 + 次（共 3 码） | 二 `fgg` |
| 成字字根（1 笔） | 报户口 + 首 + `l` + `l` | 一 `ggll` |
| 合体字（≥4 字根） | 第 1、2、3、末 字根 | 输 `lwgj` |
| 合体字（3 字根） | 3 字根 + **末笔字型识别码** | 中 `khk` |
| 合体字（2 字根） | 2 字根 + **识别码** | 和 `tkg` |

**末笔字型识别码** = 末笔笔画区（横竖撇捺折）× 字结构（左右/上下/杂合）：

| 末笔 \ 结构 | 左右 | 上下 | 杂合 |
|---|---|---|---|
| 横 | G | F | D |
| 竖 | H | J | K |
| 撇 | T | R | E |
| 捺 | Y | U | I |
| 折 | N | B | V |

识别码只用于"字根不足四码"的字——这是编码正确性的关键一环，也是初学者最大的门槛（要同时判断末笔与结构）。

### 1.3 词组取码

| 词长 | 取码 |
|---|---|
| 2 字 | 甲1 甲2 乙1 乙2 |
| 3 字 | 甲1 乙1 丙1 丙2 |
| 4 字 | 甲1 乙1 丙1 丁1 |
| ≥5 字 | 甲1 乙1 丙1 末字1 |

### 1.4 简码：五笔"快"的真正来源

| 级别 | 码长 | 数量 | 说明 |
|---|---|---|---|
| 一级简码 | 1 码 + 空格 | **25** | 25 个最高频字，一键上屏（`q`我 `w`人 `e`有 …） |
| 二级简码 | 2 码 + 空格 | **625**（25×25） | 常用的 400+ 字，实际占五笔日常输入的很大比例 |
| 三级简码 | 3 码 + 空格 | **4,400+** | 次常用字；3 码足够时不必打第 4 码 |

简码是"训练出来的肌肉记忆"：老用户的手感=简码表本身。**缺简码不是慢一点，而是手感完全不同**。

### 1.5 学习路径与重码

- 传统教学顺序：**字根（分区口诀）→ 拆字 → 识别码 → 简码 → 词组**；
- 重码靠词频与词序解决，空格取首选、数字键选次选；
- `z` 键（非标准但普遍）：查询编码/万能键，是学习期的重要拐杖。

## 2. 各种编码方案对比

### 2.1 五笔家族

| 方案 | 与 86 的差异 | 对产品的含义 |
|---|---|---|
| **86**（本产品默认） | 基准：130 字根、识别码如上 | 资料最多、老用户最多；本产品已实现 |
| **98 版** | 字根表调整（增/并若干字根）、个别字取码变化、简码表重排 | 与 86 键入差异约 10–20%；数据与教学要重做一套 |
| **新世纪** | 沿用 98 的字根体系，但**重排键位**以改善手指负荷 | 同上；用户群更小，但手感评价更好 |
| **18030/06 等** | 面向大字集（GB18030）修订，字根与取码再调整 | 生僻字覆盖更好；生态最弱 |

**结论**：多方案不是"再生成一张表"，而是 **字根表 + 取码规则 + 简码表 + 词库 + 教学文本** 五件套同时成立；缺一件就会出现"能打出字但学不会/打不快"的半成品。

### 2.2 其他形码（对比参照）

| 方案 | 核心思路 | 与五笔的关系 |
|---|---|---|
| **郑码** | 主根/副根 + 更系统的字根命名，重码率更低 | 学习曲线更陡；适合"专业录入"定位 |
| **仓颉**（繁体圈） | 5 类基本字形 + 辅助字形，规则少而规整 | 规则比五笔简单，简体生态弱 |
| **二笔/表形码** | 大幅减少字根与规则，用"低门槛"换重码率 | 与"五笔优先 + 拼音兜底"的定位重叠度低 |

对本产品的意义：**默认方案只保留一个（86）**，其余作为可选数据包，避免"默认体积/维护成本"膨胀——这与 AGENTS §11「宁可删掉一个功能」一致。

## 3. 当前实现评估

### 3.1 架构与数据流

```
拆字数据（D2 MIT / D3 WindInput）+ 字根表(D2) + 简码清单(D17) + 词表与词频(D10 jieba / D3)
        │  crates/wubi-encoder（纯规则：encode_key_name / encode_chengzi / encode_hechengzi / encode_phrase）
        ▼
data/generated/wubi86-core.tsv（48,037 条：1 码 25 / 3 码 1,930 / 4 码 46,082）
        │  crates/ime-table（排序数组 + 精确/前缀查询）
        ▼
crates/ime-core（分块排序：精确 > 补全 > 模糊；学习有界上移）＋ ime-pinyin（拼音兜底，20,194 条）
        ▼
ime-ffi → platforms/macos（IMK 宿主 / 候选窗 / 学习区）
```

### 3.2 做对了的地方（有证据）

| 项 | 证据 |
|---|---|
| 四条单字取码规则 + 识别码 5×3 表 | `crates/wubi-encoder/src/lib.rs`（`recognition_key`、`encode_chengzi` 的 1/2 笔特例、`encode_hechengzi` 的 <4 字根加识别码） |
| 词组四条规则 | `encode_phrase`（2/3/≥4 字三种分支），单测 `phrase_two_chars_takes_two_codes_each` 等 |
| 与公开 oracle 对照 | GB1 单字 99.98%（`data/generated/wubi86-core-report.txt`，双 oracle：wubi-lex + rime-wubi） |
| 排序契约 | 精确 > 补全 > 模糊；跨来源去重按来源优先级；`exact_wubi_precedes_high_frequency_completion_on_every_path` 守着 |
| 学习不越位 | `promote_learned` 只走固定步长、最多到第 2 位、不跨分块（ADR-304） |
| 一级简码入表 | 25 条（D17）+ `tools/check-level1-codes.py` 校验 + 评测 `jianma1` 首选 32%→100% |
| 零网络/零遥测 | `make verify-no-network` 逐产物符号表检查（112 产物） |

### 3.3 具体问题（按影响排序）

| # | 问题 | 影响 | 现在能怎么验证 |
|---|---|---|---|
| **P1** | **二级简码缺失**：表里没有 2 码行（`awk -F'\t' 'length($1)<=2'` 只有 25 行是一级） | 2 码输入只能"前缀+词频"；老用户 2 码空格上屏的习惯不成立，首选率显著低 | `make eval-candidates` 的 `jianma2` 类：命中 100%、首选 **93.3%**、位次 0.07——看似不差，但那是"前缀能命中"，键数仍多 1（无空格豁免） |
| **P1** | **三级简码缺失**：1,930 条 3 码全是词组，没有单字 | 常用字要打满 4 码，或 3 码后翻候选；这是日常输入里最频繁的浪费 | `grep -c` 按码长统计；可加评测类 `jianma3` |
| **P2** | **简码行复用全码权重**：`generate_core.rs` 给 1 码行的 `weight` 取自该字在全码表里的权重 | 二级/三级简码一旦入表，重码顺序会直接沿用"全码频度"，与"简码使用频度"不一致 → 首选错位 | 需要给简码引入独立频度来源（见 §4.2） |
| **P2** | **词频来源非输入语料**：WindInput（D3）权重 + jieba（D10）词频拼接 | 同码内排序与真实使用分布有偏差；改善靠 holdout 评测（200 条样本）统计力有限 | `tools/eval/baselines/1.0.2-build37.json`；扩样本即可 |
| **P2** | **学习信号单一**：只记"选了几次"，没有位次/放弃/删除/时间 | 无法区分"勉强选中"和"一眼就对"；ADR-304 P2（衰减/MRU/误选不学习）无数据基础 | 用户词库字段现状见 `docs/配置架构.md`；扩展需 ADR |
| **P3** | **无 `z` 查询/万能键** | 学习期缺"查编码"拐杖；老用户习惯缺失 | 引擎无 `z` 分支；可在教学模式先做只读查询，不动输入路径 |
| **P3** | **教学覆盖 104 / 27,823** 完整解释 | 学习区大部分字只给"编码事实"，给不出"为什么这样拆" | `crates/ime-table/src/learning.rs` 的 verified 记录数 |
| **P3** | **拼音兜底为轻量表**（20,194 条，无 n-gram/整句） | 混输时长句只能逐词；这是"拼音兜底"定位的自觉取舍 | `crates/ime-pinyin`；ROADMAP E 批 |
| **P4** | **无简码提示**（候选窗不告诉用户"这是二级简码/可按空格"） | 新手不知道能省键 | 候选窗头部现有编码/页码，可加只读提示 |

> 说明：P3/P4 不是缺陷，是范围选择；列出来是为了和"学练用"规划对齐。

### 3.4 复现命令

```sh
awk -F'\t' 'length($1)<=2' data/generated/wubi86-core.tsv | wc -l     # 25（一级简码）
awk -F'\t' '{print length($1)}' data/generated/wubi86-core.tsv | sort | uniq -c
python3 tools/check-level1-codes.py
make eval-candidates           # 各类别的命中/首选/位次/键数
make test                      # 编码规则与排序契约的单测
```

## 4. 「学 · 练 · 用」一体的设计

### 4.1 目标与硬约束

- **用**：默认输入法路径不变——零网络、零遥测、16ms 稳态门禁（ADR-307）、不因教学/练习拖慢热路径。
- **学**：从"编码事实"升级到"拆解理由"——每个字能回答"为什么取这几个字根、识别码怎么来的"。
- **练**：题目从同一份数据生成，可复现、可离线、按错误类型针对性出题。
- **闭环**：练的结果只影响**练**（题序/难度），**默认不影响候选排序**；若要让"练得多的字更靠前"，必须是用户显式开关 + 新 ADR。

### 4.2 数据层（一切的前提）

**结构事实库**（ADR-189 已立目录边界，尚未实施）：

```text
char  结构  字根序列  末笔  全码  简码等级(1/2/3)  简码频度  读音  通用频度  拆解理由模板
```

一份数据三处用：输入（生成码表）、学（拆解解释）、练（题目与答案）。**禁止**三处各维护一份。

配套要解决的两个数据问题：

1. **简码频度**：二级/三级简码的顺序不能沿用全码权重。可选来源：
   ① 公开简码表的既有顺序（最保守，与老用户肌肉记忆一致）；
   ② 通用字频 × 简码规则（可复现）；
   ③ 本地使用统计（只在本机，不参与发布数据）。
   建议：**用现有全码权重（D3）**——报告 237 的对照显示，全码权重与通用字频在 624 个码位里
   只有 5 个选字不同，且全是生僻扩展字；少一个依赖、与码表同源、可复现。
   真正的权威性问题（与官方 625 表是否一致）只有拿到可许可官方表才能验，评测本身不能自证。
2. **拆解理由**：现有 3,592 条分类型记录 + 104 条完整解释 → 用模板从事实库生成，缺事实的字明确标注"仅编码，无拆解说明"，不编造。

### 4.3 引擎层

| 组件 | 现状 | 建议 |
|---|---|---|
| 取码规则 | 硬编码 86 | 抽 `Scheme` trait（`key_map`/`encode_char`/`encode_phrase`/`level_codes`），86 为首个实现；**不改变现有排序契约** |
| 查询接口 | `ime-ffi` 已有只读教学查询 | 增加 `explain(char) -> {结构, 字根, 末笔, 识别码, 简码等级, 理由}`，同一数据源 |
| 练习生成 | 无 | `tools/` 侧生成题库（不是运行时）：字根识别 / 拆字 / 编码 / 简码 / 词组，每题带答案与错因分类 |
| 性能 | 稳态 p95 6.71ms | 教学模式只走独立窗口（复用 `Preview`），**不进入 IMK 热路径** |

### 4.4 交互层（macOS）

1. **学（已有雏形）**：候选窗内嵌学习区 → 扩展"这一步为什么是这个字根"、识别码来源、简码等级提示（只读）。
2. **练（新增）**：独立 AppKit 窗口（复用 `platforms/macos/Preview` 的引擎与候选窗）：
   - 题型：给字选字根 / 给字根拼字 / 给编码选字 / 简码速打 / 词组速打；
   - 判分：按键数、错误类型（错根、错识别码、多打一码、选错候选）；
   - 数据：本地 JSON（`~/Library/Application Support/Lampyris/practice/`），可手动导出，不联网。
3. **用**：输入法本体不因练习改变默认行为；候选窗可显示"简码等级"提示（可关）。

### 4.5 规划（建议批次）

| 批次 | 内容 | 前置 | 完成标志 |
|---|---|---|---|
| **L0** | **D17-bis 二级简码（规则推导 624 条，`cx` 待官方表）**（数据登记 + 生成 + 校验 + `jianma2` 对照） | 简码频度来源决策（§4.2） | 2 码首选率与键数达到一级简码同类水平；零劣化 |
| ~~L1~~ | ~~三级简码~~ → **暂缓（报告 239）**：按键仅 4.25→4.03、表 +53 KB、582 处与既有 3 码字撞码；真实价值在「少记识别码」，改由 L3 教学提示解决 | — | 拿到官方表且用户仍反馈识别码难记时再评估 |
| **L2** | **结构事实库 B0**（1,000 高频字试点，含拆解理由） | ADR-189 目录边界 | 单字拆解可解释率 ≥ 90%（高频 1,000 字） |
| **L3** | **学**：候选窗拆解/识别码/简码提示（只读） | L2 | 提示不影响稳态 p95；可关闭 |
| **L4** | **练**：题库生成器 + 独立练习窗口 + 本地进度 | L2、L3 | 离线可用、零遥测；题量与错因统计本地可导出 |
| **L5** | 可选：`Scheme` trait + 98 或郑码验证多方案成本 | L2（数据三件套就位） | 新方案只需数据包，不改宿主/排序契约 |

排序理由：L0/L1 直接改善"用"（用户每天感知），L2 是所有教学/练习的地基，
L3/L4 才谈得上"学练用一体"；L5 属于扩张，等前面稳定且有真实需求。

### 4.6 度量（不使用遥测）

- **用**：沿用 `tools/eval/`（离线、可复现）——命中率、首选率、平均位次、按键/条；新增 `jianma3`。
- **学/练**：本地练习记录（正确率、平均键数、错因分布），用户可自行导出；不上传、不埋点。
- 发布门禁不变：ADR-307 的稳态 p95、内存、零外联。

### 4.7 风险与边界

1. **数据合规**：二级/三级简码要登记来源与 SHA（D17-bis / D18），只接受 GPL-3 兼容许可；公开简码表也要核对许可与准确性。
2. **不要在输入热路径做教学计算**：拆解解释走独立窗口/只读接口。
3. **练习成绩不许污染候选排序**（除非用户显式开启 + ADR）。
4. **多方案不自动开工**：按 AGENTS §11，默认只保留 86；多方案是"有明确需求再立项"。
5. **教学质量优先于覆盖数量**：宁可 1,000 字讲透，不要 27,823 字都只给编码。

## 5. 建议的下一步（三件）

1. **决策简码频度来源**（§4.2 选项①②）→ 直接开 **L0 D17-bis**，这是投入产出比最高的一步。
2. **结构事实库 B0 试点**（1,000 高频字）——它决定"学/练"能不能成立，也是 ADR-189 的第一次落地。
3. **加 `jianma3` 评测类**（哪怕三级简码还没做），先把"缺三级简码损失多少键"量化出来，避免凭感觉排优先级。
