## ADR-001 核心语言：Rust

- **状态**：✅ 冻结
- **决策**：引擎与业务逻辑用 Rust 实现。
- **理由**：内存安全（输入法是高权限组件）；单一核心跨平台复用；移动端可交叉编译；生态有 `cedarwood`/`windows`/`objc2`/`jni` 等所需设施。
- **关联**：`技术方案.md` §4

## ADR-002 许可证：GPL-3.0-or-later

- **状态**：✅ 冻结
- **决策**：整个项目采用 GPL-3.0-or-later。
- **理由**：① 防"劣币驱逐良币"——阻止他人闭源包装后反噬；② 开源桌面输入法主流许可（RIME 前端、Trime、msime 等），社区推广无门槛；③ 非商业项目，无需 Apache/MIT 的"企业可闭源"空间；④ 解锁 GPL/LGPL 资源（`libpinyin`、`rime-wubi`）。
- **配套**：名称/Logo 保留权利（README 声明）；贡献用 DCO。
- **关联**：`技术方案.md` §4、`数据来源与许可.md` §5

## ADR-004 架构：Rust 核心 + 窄 C ABI + 平台薄宿主

- **状态**：✅ 冻结
- **决策**：引擎为框架无关的 Rust 库，暴露纯 C ABI；各平台写薄宿主。
- **宿主**：macOS/iOS=Swift；Windows=Rust（`windows` crate 实现 TSF）；Linux=C++ Fcitx5 薄壳；Android=Kotlin+JNI。
- **理由**：`karukan`/`vnkey`/`pure-ime`/`inputx` 已验证该模式；`objc2` 无 IMK 绑定，Swift 是现实选择。
- **关联**：`技术方案.md` §5、§10

## ADR-006 输入形态：五笔优先 + 默认混合输入

- **状态**：✅ 冻结

## ADR-007 码表：自建（编码器 + 词组自动生成）

- **状态**：✅ 冻结

## ADR-008 拼音：trait 化可插拔，Phase 1 用内置轻量兜底

- **状态**：✅ 冻结（2026-10-08 复核后修订）
- **决策**：定义 `PinyinBackend` trait。**Phase 1 用内置轻量拼音兜底**（音节→高频字词表 + 简拼，数据几百 KB）保证混输与反查；`inputx-pinyin` 在 P1-M2 先做 spike，验证 API/质量/体积后再决定；终局自研；`librime` 仅备选。
- **理由**：不把"混输兜底"绑定到单一第三方引擎（bus factor 1、年轻、API 未验证）；保持全 Rust 构建与移动端交叉编译。
- **T-M2-04 spike 复核（2026-10-08，**终局决定**）**：评估 `inputx-pinyin` 1.4.0 后，**Phase 1 不接入，保留内置轻量兜底**；`inputx-pinyin` 降为 **P2「观察」候选**（可能作为可选后端接在 `PinyinBackend` 之后），**终局仍为自研 FSA**。依据：① **体积**——core `pinyin.dict` 4.2 MiB、默认含 bigram/trigram ≈ 22.8 MiB，远超 0.6 MB 预算（决定项）；② **质量**——20 常用词 hit@1 与内置兜底持平（各 19/20），仅超长整句占优；③ **维护**——单作者、crates.io 1.4.0 滞后、API 有变动；④ **API**——facade 不含简拼/权重，`inputx-core` 未发布，需自写适配层；许可干净（非否决项）。详见 `docs/reviews/002-inputx-pinyin-spike.md`。
- **关联**：`技术方案.md` §8、`docs/reviews/001.md` P1-2、`docs/reviews/002-inputx-pinyin-spike.md`、T-M2-04

## ADR-015 词典数据结构：cedarwood（弃用 yada）

- **状态**：✅ 冻结（2026-10-08，实现阶段发现）
- **决策**：码表底层用 **`cedarwood`**（BSD-2）双数组 Trie；**弃用 `yada`**。M0 先用排序数组验证逻辑，M1 换 `cedarwood`（预测搜索 + 动态增删 + 持久化）。
- **理由**：输入法需要"由前缀枚举所有候选"的预测搜索；`yada` 只有 `common_prefix_search`（语义相反），不支持；`cedarwood` 的 `common_prefix_predict` 正是所需，且支持动态增删（用户词库）与稳定二进制持久化。
- **关联**：`技术方案.md` §6.2、§4
- **后续**：M1 的 cedarwood 迁移始终未实施；ADR-060 将 cedarwood/二进制索引降级为带触发条件的可选优化，当前实现为**排序数组 + 文本 TSV**。本条作为历史保留。

## ADR-016 单字码来源：自建编码器为唯一发布来源，第三方码表仅作验证 oracle
- **状态**：✅ 冻结（2026-10-08）
- **背景**：T-M1-04 发现 `huanfeng/WindInput` 的 `wubi86_chaizi.txt`（MIT）**第 3 列直接给出已验证的五笔86 码**（27,823 字）。一度可省去 T-M1-03 编码器。
- **决策**：
  1. **发布用单字码表只能由本仓自建编码器（`crates/wubi-encoder`）生成**；**不直接发布**任何第三方码表。
  2. 第三方码表（WindInput 等）**仅作验证 oracle**（测试/CI 对照），**不进入发布产物**。
  3. 编码器须与 oracle **全量对照**并达到约定一致率；不一致逐条调查（编码器 bug / 数据错 / 规则边界），结论归档。
  4. 尽量用**多个独立 oracle**交叉，避免单一来源错误被当成真值。
- **理由（长期正确性）**：
  1. **独立性**：发布产物不依赖第三方数据的正确性与可获得性。
  2. **可审计**：每个码可由规则重现、可解释（项目核心卖点“开源可审计”）。
  3. **可扩展**：同一编码器框架支撑五笔98/新世纪/郑码；直接吃第三方码表是死路。
  4. **可验证**：自建 + 独立 oracle 对照才是真正的质检，能发现 oracle 自身的错。
  5. **许可干净**：第三方数据不出现在发布物中，许可风险最小。
- **与 ADR-007 的关系**：结论**不变且更强**——自建码表仍是路线；本 ADR 明确“第三方码表”的**唯一定位是验证**。
- **影响**：T-M1-03（合体字+识别码）**保留且是核心**；T-M1-04 重定位为“oracle 对照”；T-M1-05 生成自建码表并报告与 oracle 的一致率。
- **关联**：`技术方案.md` §7.1、`数据来源与许可.md`、ADR-007、ADR-014

## ADR-017 结构/末笔数据来源：暂从 D3 派生（option 2），可靠来源待引入

- **状态**：✅ 冻结（2026-10-08）
- **背景**：T-M1-03 需要每字的「末笔笔画 + 字型结构」以生成识别码；D3（oracle）不直接给出这两个字段。
- **决策**：
  1. 采用 **option 2（派生）**：从 D3 识别码位反推 (末笔, 结构)，生成自有派生数据集（MIT 允许派生）。
  2. 派生数据集仅作**临时输入**，不进入发布产物；可靠独立来源（Unicode IDS / CHISE 等）引入并登记后再替换。
  3. 识别码表本身（5×3 双射）是公开规范，由本库 `recognition_key` 硬编码实现，用规范样例（中/和/对/地/要/会）做独立单测校核，不依赖 D3。
- **理由**：
  1. 离线约束下无 IDS/CHISE 等独立来源可用；D2 拆字粒度与 D3 不一致且缺字，不能可靠提供字根数（T-M1-04 已提示）。
  2. D3 第 2 列实为「每码位字形」而非纯拆字，不给出字根数 → 无法可靠区分「2 字根+识别码」与「成字字根」等，故派生仅对三码字近似成立，标注 PROVISIONAL。
- **影响**：`data/generated/wubi86-structure-laststroke.tsv` 为 PROVISIONAL 派生数据；T-M1-05 生成自建码表前需引入可靠拆字数据（含结构/末笔），并做与 D3 的全量对照回归。
- **关联**：ADR-016、`数据来源与许可.md`、T-M1-03、T-M1-05

## ADR-018 结构/末笔独立数据源：调研结论——暂无 GPL-3 兼容来源

- **状态**：🔶 结论（T-M1-05a 调研；阻塞 T-M1-05）
- **背景**：T-M1-05a 要求引入**独立于 D3** 的「字型结构（左右/上下/杂合）」与「末笔笔画（横竖撇捺折）」数据，替换 ADR-017 的 PROVISIONAL 派生数据（其来自 D3 反推，属自证）。
- **调研结论（逐一核实许可）**：
  1. **末笔（笔画顺序）**：
     - `KanjiVG`（CC BY-SA 3.0，**GPL-3 兼容 ✓**）：笔画有序、方向可判，但只覆盖日本汉字，GB2312 一级仅 **2395/3755（63.8%）**，无法覆盖简体常用字。
     - `makemeahanzi` / `hanzi-writer-data`（源自 Arphic 字体）：**Arphic Public License**，FSF 官方列表明确判定 **incompatible with the GPL** → 与 GPL-3 冲突，禁止引入。
     - `cnchar` 等 npm 库：MIT 是**代码**许可，其笔画顺序数据仍源自 Arphic/makemeahanzi → 数据许可同样不合格。
  2. **结构（IDS）**：
     - `cjkvi/cjkvi-ids`：`ids.txt` 派生自 CHISE，"许可从其条款"（未明示）；其余文件 GPLv2（是否"or later"表述含混）→ 不满足"许可明确"。
     - `chise/ids`（CHISE IDS 数据库）：仓库**无 LICENSE/COPYING**；其软件 CL-CHISE 为 LGPLv2.1，但**数据**本身无明确许可声明 → 不满足"许可明确"。
- **决策**：
  1. **停止**：不引入上述任何来源，不生成"独立结构/末笔"数据；**不退回 D3**、不伪造数据。
  2. ADR-017 的 PROVISIONAL 派生数据**继续作为 T-M1-05 的临时输入**（明确标注，不进发布产物）。
  3. T-M1-05（单字码表生成）**继续阻塞**，直至找到合格来源。
- **理由**：铁律 4（数据合规）+ T-M1-05a 禁止项（不引入许可不明 / 与 GPL-3 冲突的数据；找不到合格来源即停止）。
- **下一步候选（待后续卡评估，按优先级）**：
  1. **末笔**：KanjiVG（CC BY-SA 3.0）先覆盖其 63.8% 常用字（可行性已确认：SVG 有序笔画可判末笔方向），缺口字再寻 CC0/MIT/CC-BY 的简体笔画来源（Wikimedia/Wiktionary、国内开放数据）。
  2. **结构**：评估 Wikimedia/Wiktionary（CC BY-SA）Han 字条目中的 IDS 分解（机器可读 dump 的覆盖与正确性待测）；或向 CHISE 申请明确许可。
  3. 若长期无解：按 ADR-016「多独立 oracle」原则，用**第二份独立 wubi 码表**交叉校验派生数据（仍是码表派生，非真正独立，需另立 ADR）。
- **关联**：ADR-016、ADR-017、`数据来源与许可.md` §1.3、T-M1-05a、T-M1-05

## ADR-019 验证策略：以「多 oracle 交叉验证」替代「数据独立」

- **状态**：✅ 冻结（2026-10-08）
- **背景**：ADR-016 要求发布码表自建、第三方仅作 oracle；ADR-017 的结构/末笔为 D3 派生（PROVISIONAL）；T-M1-05a/05b 调研证明：**不存在**「GPL-3 兼容 + 许可明确 + 体积可用」的独立 IDS/结构来源 → **“数据独立”在 Phase 1 不可达成**。
- **决策**：
  1. 保留自建编码器为发布码表生成器（ADR-016 不变）。
  2. 结构/末笔沿用 ADR-017 的 PROVISIONAL 派生数据（明确标注，**不进发布产物**）。
  3. **发布前必须与 ≥2 个来源独立、许可合规的码表 oracle 全量对照**：
     - Oracle #1：WindInput（MIT）
     - Oracle #2：`rime/rime-wubi`（LGPL-3；其表源自极点五笔，**仅作测试对照，绝不分发**）
     - 可选 #3：`ibus-table-chinese` wubi-jidian86（GPL-3，测试对照）
  4. 三方不一致 → **逐条按五笔86 规范人工裁定**，记录理由；**不得“向某个 oracle 拟合”**。
  5. oracle 一律不进入发布产物（ADR-016）。
  6. 将来若获得许可明确的独立结构/末笔数据，回到 ADR-017 的升级路径替换（本 ADR 不撤回）。
- **理由**：① 编码器已由规范样例独立校核、与 D3 一致 99.98%；② 剩余风险主要是“单一 oracle 自身错误”，多源交叉可检出；③ 测试用 oracle 不涉及分发，provenance 风险可控（既有文档已允许极点系数据作回归对照）。
- **关联**：ADR-016、ADR-017、ADR-018、T-M1-04b、T-M1-05

## ADR-020 单字码表生成：以 D3 拆字为字根来源 + 成字字根规则补全

- **状态**：✅ 冻结（2026-10-08）
- **背景**：T-M1-05 按任务卡对 D2 逐字编码，发现 D2 的字形记法歧义过大（GB1 一致率仅 ~92%，天花板约 94%），不满足 ≥99% 验收；同时发现 `encode_chengzi` 对 1/2 笔成字字根的实现不完整。
- **决策**：
  1. **发布码表（`wubi86-single.tsv`）仍由本仓编码器逐字生成**（ADR-016 不变），但**字根序列来源由 D2 改为 D3 第 2 列**（WindInput `wubi86_chaizi.txt`，MIT；“每码位一字形”的干净拆字表示）。
  2. **字根表（字形→键）为公开五笔86 规范**（CC0 事实性数据），在 D3 字形记法下由编码列多数表决推导；该推导使“vs D3”的一致率成为规则自洽检验，**真正的独立校验是 rime oracle（独立谱系）**（ADR-019 口径）。
  3. D2 降级为**交叉检查**（量化其字形记法歧义），不进入发布路径；识别码/结构/末笔仍为 D3 派生（PROVISIONAL，ADR-017/019）。
  4. **`encode_chengzi` 补全标准**：1 笔=键+首笔+LL、2 笔=键+首笔+次笔、≥3 笔=键+首笔+次笔+末笔（修正 T-M1-02 的简化，原实现把 2 笔成字字根错编为 4 键）。
- **理由**：① D2 的字形记法歧义已由 T-M1-04/ADR-017 预警，本次量化确认不可用；② D3 第 2 列与编码列逐位等长、字形无歧义，可稳定支撑生成；③ 用 D3 拆字仍非“直接发布第三方码表”——码仍由自建编码器规则生成，仅字根序列输入来自 MIT 拆字数据（与 D2 同类）。
- **影响**：`wubi86-single.tsv`（D1）由 `generate.rs` 从 D3 拆字生成；与 D3 一致 99.9784%（GB1 100%）、与 rime 一致 98.77%（GB1 100%），三方不一致 0 条；D2 交叉检查 GB1 91.66% 写入报告。
- **关联**：ADR-016、ADR-017、ADR-019、T-M1-02、T-M1-05

## ADR-021 词组码表：多候选（重码）模型 + jieba 词频

- **状态**：✅ 冻结（2026-10-08）
- **背景**：T-M1-06 用 D4 生成的词组表为**单候选去重**（`code\t词组`），且词表覆盖不足；T-M1-06b 改用 `fxsjy/jieba` `dict.txt`（D10，MIT，349,045 词**带词频**）重生成并赋权。但卡步骤 3 的「同码保留权重最高者」与验收样本冲突：如 `ltif` 下 `加德满都`（频次 66）会挤掉 `输入法`（频次 19）。
- **决策**：
  1. 词组码表格式改为 `code\t词组\tweight`，采用与单字码表一致的**多候选（重码）模型**（`技术方案.md` §6.2）：一个码保留全部候选，按 `weight` 降序；**不再单候选去重**。
  2. `weight` = jieba 词频（**真实词频**，ADR-013）；词表来源 D10（MIT）。
  3. 单字码表 `weight` 同样改为 jieba 词频（缺者默认 `1`）。
- **理由**：① §6.2 已确定「一个码映射多个候选」，单候选实现与架构不符；② T-M1-07 的「重码按词频降序」需要多候选；③ 避免验收样本（尤其 `输入法`）因碰撞被丢弃；④ 内置码表可在 T-M1-09 再按词频挑选 ~10k 高频词组（`技术方案.md` §7.2）。
- **影响**：`data/generated/wubi86-phrases.tsv` 由 38,220 条（单候选）变为 337,231 条（155,726 个码，5.8 MB）；`wubi86-single.tsv` 仅 `weight` 列变更。
- **关联**：ADR-013、ADR-016、`技术方案.md` §6.2/§7.2、T-M1-06、T-M1-06b、T-M1-07

## ADR-022 macOS 宿主集成：FFI 扩展 + 配置路径 + bundle 标识（T-M3-02）

- **状态**：✅ 冻结（2026-10-08）
- **背景**：T-M3-01 的 `ime-ffi` 会话只用内置样本引擎，且无平台配置路径、无预编辑串出口、无模式切换入口；缺少可装载的 macOS 宿主。T-M3-02 需要在不破坏 ABI 契约的前提下补齐。
- **决策**：
  1. **扩展 `ime-ffi` 会话 ABI**（仍 `catch_unwind`、不透明句柄、UTF-8、负数为错误）：
     - `ime_session_new_with_data(wubi, pinyin_chars, pinyin_words)`：从真实 TSV 加载；拼音词表可空（降级单音节）；失败返回 `NULL`。
     - `ime_session_buffer(session)`：返回**借用**的组合缓冲区（预编辑串）。
     - `ime_session_set_mode(session, mode)`：按 `mixed`/`wubi`/`pinyin` 切换。
     - `ime_session_key` 成功时改为返回按键结果 `IME_KEY_CONSUMED(0)` / `IME_KEY_COMMITTED(1)` / `IME_KEY_PASS_THROUGH(2)`；`0` 与旧 `IME_OK` 兼容。
  2. **配置 ABI 增加 `ime_config_init(path)`**：由宿主在任何配置调用前告知平台路径；仍是唯一文件真值，**不使用 `UserDefaults`/环境变量存配置**（`配置架构.md` R1）。
  3. **平台配置路径**：`~/Library/Application Support/萤火虫/config.toml`。
  4. **bundle 标识**：暂用 `org.yinghuo.inputmethod`，连接名 `Yinghuo_InputMethod_Connection`，控制器类 `YinghuoInputController`；最终包名取决于 TBD-4，改动仅涉及 `Info.plist` 与常量。
  5. **bundle 格式必须为 `.app`**（不是 `.inputmethod`）：本机实测 macOS 13 的 LaunchServices 无法扫描 `.inputmethod`（`lsregister -f` 报 `-10811`），且系统内所有输入法均为 `.app`。随附 `Contents/PkgInfo`（`APPL????`）、菜单图标（`tsInputMethodIconFileKey`）与 `*.lproj/InfoPlist.strings` 本地化显示名。
  6. **`Info.plist` 结构**：输入模式清单放 `ComponentInputModeDict`（`tsInputModeListKey` + `tsVisibleInputModeOrderedArrayKey`），键名参照本机实测的既有 IMK 输入法（系统输入法与 `SogouWBInput.app`）。
  7. **UI 约束**：候选窗为纯代码 `NSPanel`；**不使用 Interface Builder / Asset Catalog**（本机无 Xcode）。
  8. **安装时机**：macOS 只在**登录时**扫描输入法 bundle；更换 bundle 后必须**注销/重登**（实测 `killall TextInputMenuAgent` 无法可靠触发重扫）。
- **理由**：① 宿主无需自建业务逻辑即可完成「按键→候选→上屏」闭环；② `buffer`/`set_mode` 是预编辑与配置模式的必要出口，仍只做转换；③ 显式 `ime_config_init` 比 `setenv` 更可验证且不触碰 R1；④ 用系统实测的 `.app` 格式与键名，避免装载失败。
- **关联**：T-M3-01、T-M3-02、`技术方案.md` §5.3/§10、`配置架构.md` §9、`platforms/macos/README.md`

## ADR-023 macOS 注册标识修正：保留经典 IMK 宿主

- **状态**：✅ 冻结修正（2026-10-08）；系统装载验收待完成。
- **背景**：T-M3-02 的 bundle ID `org.yinghuo.inputmethod` 缺少 `.inputmethod.` 后的名称段；连接名 `Yinghuo_InputMethod_Connection` 未与 bundle ID 对齐。验证机日志反复出现 `Refusing connection name for bundle: unrecognized 'InputMethodConnectionName' value`，但 bundle ID 在日志中被隐去，尚不能把每条错误归因于萤火虫。
- **决策**：
  1. bundle ID 修正为 `org.yinghuo.inputmethod.Yinghuo`；模式 ID 为 `org.yinghuo.inputmethod.Yinghuo.default`；连接名统一为 `org.yinghuo.inputmethod.Yinghuo_Connection`，同步 plist、入口与本地化。
  2. 保留 `.app` + `IMKServer`。本机 Xcode 27 模板未检出 Input Method Extension，公开 SDK 的 `IMKServer` 未标弃用，Apple 公开文档仍描述经典入口；内置输入法使用 appex 不能证明第三方必须迁移。没有公开入口证据前，不实现 `com.apple.textinputmethod-services` 扩展。
  3. 此修正不改变配置路径、引擎或 ABI；不引入 Sandbox 或任何新依赖。修正后的包须重新签名、公证并安装后验收，不能沿用旧包的票据。
- **理由/来源**：[IMK 示例作者](https://github.com/ensan-hcl/macOS_IMKitSample_2021)明确要求 bundle ID 包含 `.inputmethod.`；[IMKSwift 维护者](https://github.com/vChewing/IMKSwift)说明连接名采用 bundle ID + `_Connection`；[Apple IMK 文档](https://developer.apple.com/documentation/inputmethodkit)仍说明在 main 中创建 `IMKServer`。以上支持先修正注册元数据，不构成 macOS 27 实机装载已通过的证据。
- **关联**：修正 ADR-022 第 4 条；T-M3-02、SIG-2、TBD-4（英文名仍暂定）。

## ADR-032 macOS 发布候选与可信分发

- **状态**：冻结（2026-10-08，用户授权推进发布；实际上传/安装需遵守用户当前卸载约束）
- **决策**：本地构建维持 ad-hoc；分发必须 Developer ID Application + hardened runtime + 时间戳 + 公证及 stapler，安装脚本只接受通过 Gatekeeper 的固定标识 bundle。发布源码中的相对软链只允许指向包内有效目标，另附软链清单；拒绝绝对/越界/损坏链接。发布候选附 CycloneDX SBOM、运行时依赖许可、数据来源/许可、完整对应源码、构建清单及 SHA-256。离线本地准备和 Apple 上传分别显式执行，不自动安装。
- **理由**：ADR-022 中 Phase 1 不签名前提已被本机 SIG-1 实测推翻；不提供关闭 Gatekeeper 的捷径。源码与数据许可满足第三方审计和 GPL 分发要求。
- **安装**：默认当前用户目录；系统域仅明确 --system 并以管理员运行。重复安装同一字节产物幂等；不同版本拒绝覆盖，先卸载备份。卸载先切换/移除系统设置输入源，拒绝仍运行的宿主，移动 bundle 到输入法目录之外并保留用户数据。默认提供 --dry-run，开发不触碰安装目录。
- **复现边界**：固定 Cargo.lock/工具链/已登记数据，记录主机架构、Swift/SDK 版本；暂只声明相同环境可构建并比较未签名载荷，Apple 签名、公证和 ZIP 元数据不保证字节一致。首个候选仅本机构建架构，Intel/旧系统验收仍独立待办。
- **关联**：T-M3-03、P1-M5、ADR-023/030/031、隐私与安全 §4。
- **后续**：发布候选附“完整对应源码”的做法已被 ADR-064 取代——二进制包不再含 `SOURCE/`，改为在同一发布位置提供源码包（GPL-3.0 §6(d)）。本条其余（签名/公证/可信安装）仍有效。

## ADR-033 同环境构建路径归一化

- **状态**：冻结（2026-10-08）
- **决策**：正式 macOS 构建将 Rust workspace 路径映射到 /yinghuo-src，锁定 registry/vendor 的每个依赖映射到 /yinghuo-dependencies/name-version；Swift 从仓库根以相对源码路径编译，使用 file-prefix-map 和 whole-module-optimization，将生产宿主合为单一编译单元，避免多个临时对象排序差异；链接器 oso_prefix 去除对象调试映射目录并启用 reproducible；正式链接去除 STABS/DWARF 调试映射（-S），保留正常 UUID 和符号，显式目标 macOS 13（与 plist 一致）。Cargo locked 构建，归档 SOURCE 携带提交标识，构建不要求 .git。

## ADR-035 多会话共享只读词表

- **状态**：冻结（2026-10-08）
- **决策**：码表及拼音后端由 Arc 持有，只读数据可跨会话共享；引擎选项、组合、分页、候选、用户词库仍由各自会话持有。FFI 数据加载缓存使用规范路径/长度/mtime 为键、Weak 为值，各类最多 4 个键，锁保护首次加载；文件变化重新加载，不保活已无会话的数据。
- **理由**：5 个真实数据会话内存约66MiB；IMK 每个客户端独立会话，重复载入违反常驻预算。共享不可变已登记资源不需要引擎执行 IO、不增加依赖或配置。
- **边界**：不视 mtime/长度为安全哈希；正式包完整性依赖签名与发布 SHA。开发替换文件必须改变 mtime/长度；并发使用期间修改文件不影响既有会话快照，新会话加载新版本。
- **关联**：ADR-030/031、Phase 1 多应用/常驻内存验收。

## ADR-036 宿主操作取消预编辑的边界

- **状态**：冻结（2026-10-09）
- **决策**：正式菜单切模式、词库操作及反查面板前，同步清除客户端 marked text、会话组合与候选窗；模式保存失败则提示并保留当前模式/组合。失焦或显式复位重置成对引号状态，保持模式和临时中英/全半角偏好。
- **理由**：此前菜单只取消 Rust 组合或隐藏候选，客户端预编辑可能残留；成对引号状态也不应跨输入上下文延续。普通选字/取消组合不重置引号，避免一句内的闭引号失效。
- **关联**：ADR-028/034、P1-M4 失焦无残留验收；配置仍仅由 ime-config 持久化。

## ADR-037 长候选的屏幕边界

- **状态**：冻结（2026-10-09）
- **决策**：默认候选横排，超过当前屏幕可见宽度时自动竖排；单条超长词在可见宽度内截断并提供完整 tooltip，数字索引/选字文本不变。几何计算可注入可见区域供本地边界验证，实际 show 仍使用当前 NSScreen。
- **理由**：只限制候选窗原点无法处理窗体本身宽于屏幕的用户词条；保证面板自身留在可见区域，不增加排版偏好或皮肤配置。
- **关联**：ADR-026/029、P1-M4 候选不错位验收。

## ADR-038 用户候选有界查询与频次缓存

- **状态**：冻结（2026-10-09）
- **决策**：用户词库查询先按来源/精确命中/频次/文本选出最多256个借用条目，再分配候选；与现有每引擎256条的前缀查询一致，继续输入缩小范围即可找到更具体词条。核心排序对每个候选只求一次用户频次，不在比较器中反复分配查询键。
- **理由**：接近2MiB/10000条合成词库、五会话实测稳态40.30MiB，最大按键19.434ms；复制全部匹配并重复查频次违反预算。保持五笔优先与精确候选优先规则。
- **关联**：ADR-025/029/030/035、最大用户词库发布预检；词库文件容量不变。

## ADR-039 用户词库共享不可变快照

- **状态**：冻结（2026-10-09）
- **决策**：同进程同文件用户词库使用 Arc<Entries> 只读快照，各 Store 的路径/错误及刷新状态独立；写入在已有文件锁下复制当前快照并原子替换，发布新快照。Weak 缓存最多4组，键包含规范路径、mtime、长度与 Unix inode/device，避免等长原子替换漏刷新。导出读取当前文件快照，不导出过时会话副本。FFI 失焦释放用户词库快照；正式宿主激活时预加载，避免失焦会话长久保留旧版词库。
- **理由**：有界查询后最大词库五会话仍36.67MiB，重复快照违反预算；复用不可变数据，不降低解析/容量限制或持久化规则。无配置或网络新增。
- **关联**：ADR-029/035/038；快照是词条数据而非偏好配置。其他平台文件身份策略可在对应宿主阶段补充。

## ADR-040 / 激活时预热候选窗口 / 已采纳

- **决策**：候选窗口复用现有标签，首次输入法激活时创建窗口并在隐藏状态预热中文字体和布局，随后清空候选。预览使用相同窗口初始化逻辑。
- **理由**：真实 AppKit 预检首次窗口/字体初始化约34–96ms，连续更新反复创建标签造成堆分配和碎片；将初始化移到激活阶段，缩短首键路径，不生成输入或学习记录。
- **关联**：Phase 1 性能 DoD、`docs/reviews/003-macos-performance.md`；预热耗时单独报告，正式 IMK 验收仍待完成。

## ADR-041 / 拼音索引共享文本 / 已采纳

- **决策**：内置拼音后端的单字反查索引以 Arc<str> 共享相同音节，解析阶段局部驻留，加载完成后释放驻留表；全拼、简拼与词反查索引共享同一个不可变词文本。查询返回值及公开接口继续使用 String。
- **理由**：大量汉字共享少量音节，逐字持有独立字符串造成重复分配；共享不可变音节降低常驻内存，不改变多音字首选读音规则。
- **关联**：Phase 1 内存预算、`docs/reviews/003-macos-performance.md`；不增加依赖或全局缓存。

## ADR-042 / 候选标签固定层级实验 / 未采纳

- **决策**：保留实验源码/补丁，产品继续使用 ADR-040 标签复用实现。修正持续输入探针的释放池范围后重新判断内存增长。
- **理由**：固定视图层级实验未消除同步探针的增长曲线（22000键约36.7MiB），没有足够证据支持产品改动；探针窗口隐藏和主循环回调位于释放池外，存在测试失真。
- **关联**：`docs/reviews/003-macos-performance.md`；实验保存在 `/private/tmp/yinghuo-stable-views-experiment.*`。

## ADR-043 / GitHub Actions 自动验收出包 / 已采纳

- **决策**：普通 PR CI 上传无凭据审核包；独立 macOS 验收工作流在 main 推送或手动触发时，先验证/构建，再以 GitHub Secrets 中的 Developer ID p12 与 App Store Connect 团队 API p8 签名、公证、staple，生成源码/SBOM/许可/SHA 验收附件。不创建公开 Release。
- **理由**：用户指定放弃 App 专用密码，凭据一次配置用于后续自动出包；临时 runner 钥匙串及私钥文件仅在签名阶段存在并 always 清理。不在 PR/fork 代码上使用签名凭据，产物上传路径只含 ZIP/SHA，不含密钥目录。
- **关联**：ADR-032、T-M3-03、`packaging/macos/CI-ACCEPTANCE.md`；证书到期/密钥撤销仍需维护，不承诺永久有效。

## ADR-044 / 复用组织签名凭据 / 已采纳

- **决策**：macOS 出包工作流引用 EasyIndie 的 APPLE_CERTIFICATE_P12_BASE64、APPLE_CERTIFICATE_P12_PASSWORD、APPLE_ASC_API_KEY、APPLE_ASC_API_KEY_ID、APPLE_ASC_ISSUER_ID，映射到脚本参数；API 私钥接受完整 PEM 或 Base64，保留原 Base64 参数兼容性。
- **理由**：用户已在组织配置共享凭据，避免各仓库重复维护；不读取或输出 Secret，权限仍限 main 签名步骤。
- **关联**：ADR-043、packaging/macos/CI-ACCEPTANCE.md；实际签名公证需首次 CI 验证。

## ADR-045 / CI 临时钥匙串搜索与指纹签名 / 已采纳

- **决策**：临时钥匙串加入当前用户搜索列表，保留原列表并在退出时恢复；从该钥匙串的有效签名身份中按完整名称精确选取唯一 SHA-1 指纹，codesign 使用指纹和显式钥匙串。
- **理由**：运行37876973106证实同名身份有效，但codesign按名称仍找不到，须消除搜索路径和名称解析差异；指纹仅用于定位证书，不是文件完整性摘要。
- **关联**：ADR-043/044；清理测试覆盖搜索列表恢复与无有效身份拒绝，日志不包含私钥。

## ADR-046 / 回车提交原始组合码 / 已采纳

## ADR-055 macOS 13 ad-hoc 本地验收与全架构候选

- **状态**：冻结（2026-10-09）
- **背景**：ADR-032 依据 macOS 26/27 机器上“非 Apple 签名不被枚举”的实测，宣布 Phase 1 不签名前提被推翻；但那次实测时 bundle ID 仍是错误的 `org.yinghuo.inputmethod`（ADR-023 之前），**签名与注册元数据两个变量被混在一起**。
- **决策**：
  1. **本地开发/本机验收可用 ad-hoc**：在 macOS 13.7.8（Intel、`security find-identity` 为 0）上，ad-hoc 签名 + 正确 bundle ID `org.yinghuo.inputmethod.Yinghuo` 的 `.app` 被 TIS 正常枚举（`enabled=true`、`selectCapable=true`、共 284 源），用户实体输入 `wq→你`、`nihao→你好` 通过。**macOS 13 不要求公证**；日常迭代与阶段性真机验收不再依赖签名机。
  2. **分发与 macOS 26+ 仍按 ADR-032**：对外分发必须 Developer ID + hardened runtime + 公证 + stapler；macOS 26/27 更严的签名要求维持实机结论，不因本条而削减。
  3. **全架构候选（universal）**：`build.sh --universal` 同时为 arm64 与 x86_64 构建 staticlib 和 Swift 宿主并 `lipo` 合成；`prepare.sh` 依可执行文件的 `lipo -archs` 标注 `universal`/`arm64`/`x86_64`；CI 安装两个 rustup target 并出 universal 候选；`run-repro.sh` 以 `--universal` 重建并逐字节校验（本轮本机实测通过）。
- **理由**：ADR-023 的注册标识修正是 macOS 13 可见性的充分条件；签名/公证面向分发与新版系统，不应作为本地迭代门槛。单包同时覆盖 Apple Silicon 与 Intel，避免维护两份候选，也让 Intel 本机能直接安装 CI 产物。
- **链接注意**：`-whole-module-optimization` 下**不能**用 `-L … -lime_ffi`（链接器会选到 `libime_ffi.dylib`，把绝对构建路径写进 `LC_LOAD_DYLIB`，破坏可分发与可复现）；必须用 `-Xlinker <lib.a>` 强制静态归档。
- **关联**：ADR-023/024/032/033、SIG-1/SIG-2、T-M3-03、P1-M5；`platforms/macos/README.md`、`packaging/macos/CI-ACCEPTANCE.md`。

## ADR-056 英文/包名定为 Lampyris（关闭 TBD-4）

- **状态**：冻结（2026-10-09）
- **背景**：ADR-003 定了中文名「萤火虫」，英文/包名在 `yinghuo` / `lampyris` 间一直未决（TBD-4），代码里暂用 `org.yinghuo.inputmethod.Yinghuo`。`yinghuo` 是拼音，非中文用户难以拼读、记忆与检索，不利于产品面向国际；`org.yinghuo.*` 也是一个无所有权的机构段。
- **决策**：
  1. **英文/包名 = `Lampyris`**；中文名保持「萤火虫」。
     - **读法**：/læmˈpɪərɪs/，近似 “lam-PEER-iss”，重音在第二音节（学术拉丁语中 y 读 /ɪ/，也有人读 /læmˈpaɪrɪs/）。
     - **词源**：希腊语 λαμπυρίς（“发光的虫、萤火虫”），源自 λάμπω（“发光、照耀”）。
     - **含义**：萤科（Lampyridae）下的一个属，模式种 *Lampyris noctiluca* 即欧洲常见萤火虫；直接表达“自带微光”，契合“默认离线、不依赖云端”的产品寓意。
  2. **bundle 标识**：采用自有域名 `jokerhub.cn` 的反向 DNS `cn.jokerhub`：bundle ID `cn.jokerhub.inputmethod.Lampyris`，模式 ID `cn.jokerhub.inputmethod.Lampyris.default`，连接名 `cn.jokerhub.inputmethod.Lampyris_Connection`（保留 ADR-023 的 `.inputmethod.` 规则）；调试窗口 `cn.jokerhub.lampyris.debugpreview`。
  3. **改名范围**：可执行/App `Lampyris.app`、控制器类 `LampyrisInputController`、bundle 资源 `Lampyris.icns` / `LampyrisTemplate.png`、安装/卸载校验与路径、发布物与 CI 附件名 `Lampyris-*`、SBOM 组件名、用户词库默认导出名、备份目录，以及 ASCII 化的应用支持目录 `~/Library/Application Support/Lampyris/`。
  4. **不改**：中文代码/文档注释中的「萤火虫」；`assets/icons/yinghuo-*` 设计稿文件名（历史资产）；历史记录（`docs/experiments/**`、`docs/archive/**`、`docs/tasks/T-M3-02.md`、`docs/reviews/003|005`）。ADR-022 §4、ADR-023、ADR-032、ADR-033、ADR-050、ADR-055 中的旧标识作为历史保留，本条取代其中的“当前标识”。

## ADR-057 候选窗显示候选来源（混输可解释性）

- **状态**：冻结（2026-10-09）
- **背景**：`技术方案.md` §2.2 要求混输时「五笔候选在前（标注“五笔”），拼音候选在后（标注“拼”）」，候选携带 `source` 贯穿排序与词频记账。`ime-core` 与 `ime-ffi` 已实现 `CandidateSource` → `IME_SOURCE_*`（0=码表、1=拼音、2=词组）并随 `ImeCandidate.source` 暴露；但 Swift 宿主 `ImeCandidate` 只保留 `text`/`code`/`isPrefix`，候选窗只收 `[String]`，混输时用户无法区分来源（报告 006 MVP-02）。
- **决策**：
  1. **FFI 契约不变**：沿用既有 `ImeCandidate.source`，不新增 ABI、不改顺序/去重/学习归属（仍由 `ime-core` 依 `source` 处理）。
  2. **来源贯穿到窗口**：Swift `ImeCandidate` 增加 `source`（映射 `IME_SOURCE_*`）；`CandidateWindow` 在候选文本后用 `NSAttributedString` 追加小号次要色中文标签：码表→「五笔」、拼音→「拼」、词组→「词」。
  3. **显示规则**：仅当**当前页**候选来源 ≥2 种时显示标签（这正是混输需要区分的场景）；单一来源页不显示，模式本身不改变此规则，避免常态噪声。
  4. **布局**：标签 11pt 次要色、与正文同基线，沿用既有超宽竖排/屏幕约束逻辑，不新增弹层或改变命中区域。
- **理由**：来源是混输可解释性的关键（五笔优先、拼音兜底），但只在真正混合时才有区分价值；FFI 已有字段，改动集中在宿主侧，小且可独立验证（独立窗口可自测）。
- **关联**：`技术方案.md` §2.2；报告 006 MVP-02；ADR-022/023/024；`platforms/macos/Sources/{ImeSession,CandidateWindow,InputController}.swift`、`platforms/macos/Preview/main.swift`。

## ADR-058 配置变更无按键即时刷新

- **状态**：冻结（2026-10-09）
- **背景**：`配置架构.md` §11.1 要求“改 `config.toml` 保存后，正在输入的候选窗立即按新设置变化，无需重启”；`ime-config`（快照 + 原子写 + `subscribe`）与 `ime-ffi`（`ime_config_subscribe`）已具备通知能力，文件监视也会触发 `reload` 并只广播**变化**的键。但 Swift 宿主只在每个按键的 `handle` 里读 `mode`/`candidate.count`，候选窗的 0.2s 计时器只刷新主题；外部改 `candidate.count`/`mode` 时，显示中的候选不会主动重新分页/取消，只能等下一次按键才生效（报告 006 MVP-03）。
- **决策**：
  1. 宿主新增全进程单例 `ConfigWatcher`：在首个所有者注册时经 `ime_config_subscribe` **只订阅一次**；回调可能在 `ime-config` 文件监视线程上触发，**绝不直接触碰 AppKit**，一律 `DispatchQueue.main.async` 派发到主线程。
  2. 当前所有者（`LampyrisInputController`）在 `activateServer` 注册处理器、`deactivateServer` **按身份解绑**（多控制器互不误清）；不重复订阅、不泄漏。
  3. 主线程收到通知后即时应用：`session.prepare()` 重套引擎选项；`candidate.count` 变更 → `set_page_size` 并重画当前候选；`mode` 变更 → `set_mode`（取消组合、清预编辑、隐候选窗）。主题仍由窗口计时器与显式刷新覆盖。
  4. 保留按键路径的读取作为幂等兜底（订阅失败也不影响输入）。
- **理由**：符合配置架构 §4/§11「唯一真值 + 即时生效」，把配置变化从「下一按键」提前到「保存即生效」，且订阅仅发生一次，避免重复/泄漏。
- **关联**：`配置架构.md` §4/§11、报告 006 MVP-03、ADR-008/009、Skill `add-config-option`；`platforms/macos/Sources/{Config,InputController,CandidateWindow}.swift`、`Preview/main.swift`。

## ADR-059 配置错误反馈（保留有效快照 + 可读错误）

- **状态**：冻结（2026-10-09）
- **背景**：`配置架构.md` §11.5 要求“写坏语法 → 输入法照常工作（用上一份快照）并提示错误行”。现状：`ime-config` 的 `reload()` 确实保留旧快照，但 `FileWatcher` 的 `let _ =` 把错误丢弃；`ime-ffi` 首启 `ConfigStore::load` 失败时静默降级为 `with_defaults`；Swift `main` 忽略 `ime_config_init` 结果，宿主对错误毫无可见性（报告 006 MVP-04）。
- **决策**：
  1. `ime-config` 的 `ConfigStore` 记录最近一次加载/重载失败原因（`last_error()`，含行号）；新增 `load_or_defaults()` 在**首启坏文件**时降级为默认值并保留错误。
  2. `reload` 在错误状态**发生变化**时广播哨兵键 `CONFIG_ERROR_KEY = "*error"`（不与 Schema 键冲突），修复后同样广播以清除；状态未变不重复广播。
  3. `ime-ffi` 暴露 `ime_config_last_error()`（UTF-8，空串=无错误，借用指针），首启改用 `load_or_defaults`。
  4. 宿主：`ImeConfig.errorMessage()`；控制器在激活与配置变更时检查，同一错误**只弹一次** `NSAlert` 并 `NSLog`，修复后自动复位（`lastAlertedConfigError`）；输入菜单常驻一条「配置错误：…」条目。
  5. **不引入第二配置**：错误只读，绝不自动改写/删除用户文件；错误提示不影响输入（沿用上一份快照）。
- **理由**：同时满足“照常工作 + 提示错误行”与“宿主可见且不反复弹窗”；错误经既有订阅通道即时到达，无需新增轮询。
- **关联**：`配置架构.md` §7/§11.5、报告 006 MVP-04、ADR-058、Skill `add-config-option`；`crates/ime-config/src/{lib,watch}.rs`、`crates/ime-ffi/src/config.rs`、`platforms/macos/Sources/{Config,InputController}.swift`、`Preview/main.swift`。

## ADR-060 词典数据结构：文本 TSV 真值 + 排序数组（cedarwood 降级为可选优化）

- **状态**：冻结（2026-10-09）
- **背景**：ADR-015 冻结 `cedarwood` 双数组 Trie，并计划「M0 排序数组验证、M1 换 cedarwood」；`技术方案.md` §4/§6.2/§11 也按 cedarwood/`.imedict`/mmap 描述。但事实上 M1 从未迁移：**仓库任何 `Cargo.toml` 都没有 cedarwood**，`ime-table` 一直是排序 `Vec`，`ime-dict` 只实现了用户词库（ADR-029 有界 TSV），没有 `.imedict` 编译器/mmap 装载器。实测规模：`wubi86-core.tsv` 491,854 B / 37,828 行 / 30,384 个码；`pinyin-chars.tsv` 575,473 B；`pinyin-core.tsv` 262,131 B（8.4MB 全量词表**不默认装载**，ADR-031）；按键→候选 P95 在预算内、常驻约 18.5 MiB（≤ 30 MB）。即：文档与事实不一致，且现有方案已满足 DoD。
- **决策**：
  1. **源数据格式 = 纯文本 TSV**（`code\ttext\tweight`）为唯一可审计真值；**不引入二进制 `.imedict`** 作为 Phase 1 交付物。
  2. **系统码表内存索引 = 排序数组**（精确二分 + 同前缀连续区间）——保留为当前实现。
  3. **用户词库 = 有界 TSV v1**（ADR-029，`ime-dict`），与系统表分离、查询期合并；不在 DAT 上做动态增删。
  4. **cedarwood / 编译期二进制索引 + mmap 降级为“带触发条件的可选优化”（P2+）**，不再是 Phase 1 交付项。
  5. **迁移触发条件**（任一满足才立项评估）：① 单表码数/条目数超过实现卡约定阈值；② 按键→候选 P95 连续 >16 ms 或长尾 >50 ms 且定位到码表扫描；③ 常驻内存逼近 30 MB；④ 需要默认装载远大于当前规模的数据。若采用，强制：**TSV→二进制可复现编译 + 提交 SHA-256 + 仓库内校验器**（二进制只能是可验证派生物）。
  6. **立即修正实现债**（单独卡片）：`CodeTableEngine::convert` 目前为统一支持 `z` 通配而**全表线性扫描**；改为 `exact`（二分）+ 前缀区间扫描，`z` 通配走受控分支。这是小改动、不改行为、可回归。
  7. **文档追认**：更新 `技术方案.md` §4/§6.2/§7/§11、`ROADMAP.md`、`T-M1-09` 等，使其反映已交付事实，不再宣称 `.imedict`/mmap 已交付。
- **理由**：项目价值在“更小、更干净、可被第三方验证”；文本真值 + 显式排序键比不透明二进制更符合长期可审计性。当前规模无性能压力，过早引入 DAT 只增依赖与验证负担。**cedarwood 的价值是规模/内存，不是正确性**，故以可测触发条件而非“计划必然”来管理。
- **关联**：ADR-013/014/015/021/029/031、报告 006 MVP-01/12；`crates/ime-table`、`crates/ime-dict`、`技术方案.md` §4/§6.2/§7.2/§11。

## ADR-061 解析器 fuzz：有界目标 + 确定性边界语料（dev-only）

- **状态**：冻结（2026-10-09）
- **背景**：`AGENTS.md` 安全工程铁律要求“解析器要有 fuzz 目标”；`Makefile` 已有 `make fuzz`（`dict_parser`）但仓库无 `fuzz/` 目录，目标不可运行（报告 006 MVP-06）。解析器是**唯一不可信输入入口**：用户词库 TSV（`ime-dict::parse`）、系统码表 TSV（`ime_table::Table::from_tsv`）、拼音 TSV（`ime_pinyin::TablePinyinBackend::from_tsv`）。
- **决策**：
  1. 建立独立 `fuzz/`（cargo-fuzz）crate `lampyris-fuzz`，**属于独立 workspace、不属于主 workspace**，不参与 `make verify`、不入发布产物；新增三个目标：`dict_parser`（兼容现有 Makefile）、`table_parser`、`pinyin_parser`。
  2. **有界**：每个目标先对输入长度设上限（256 KiB）再调用解析器，避免 fuzz 输入诱导无界分配；用户词库解析本身已有 2 MiB / 10k 条上限。
  3. 在主 workspace 加**确定性边界语料单测**（截断行、缺列、多余列、CRLF、BOM、NUL、非 BMP、超范围数字、空字段、超长行），作为 `make verify` 每次都跑的“短时验证”，**不依赖 nightly**。
  4. `libfuzzer-sys` 等仅作为 `fuzz/` 的 dev 依赖（MIT/Apache-2.0），不受主 `deny.toml` 约束（不入发布依赖树）。
  5. `make fuzz` 依次运行三个目标，默认限时（`FUZZ_SECONDS`，可用 `make fuzz FUZZ_SECONDS=120` 调整）。
- **理由**：fuzz 是“不可信输入”的持续保障，但 nightly 工具链不应进入主构建；把确定性边界语料放进常规测试，等于每次 CI 都做一次有界 fuzz，重活留给 `make fuzz`。
- **关联**：AGENTS 铁律、报告 006 MVP-06、ADR-029（用户 TSV v1）；`crates/ime-dict`、`crates/ime-table`、`crates/ime-pinyin`、`fuzz/`。

## ADR-062 组合缓冲区有界（超限忽略后续字母）

- **状态**：冻结（2026-10-09）
- **背景**：报告 006 MVP-07 指出 `ime-core::Session` 的组合缓冲区**无长度上限**（`handle_key` 对 `'a'..='z'` 只 `push`），且 `recompute` 不读 `Engine::max_code_length()`。在真实数据上用 `cargo run --release -p ime-cli --example compose_bound`（新增复现基准）实测，单键/累计耗时随长度**超线性**增长：

  | 模式串 | 64 | 256 | 1024 |
  |---|---|---|---|
  | `a`（累计 ms / 最慢单键 ms） | 5.7 / 0.46 | 317 / 4.58 | **16712 / 69.95** |
  | `nihao` | 1.6 / 0.34 | 48.7 / 2.95 | 1945 / 13.56 |
  | `zhongguo` | 0.6 / 0.11 | 10.2 / 0.19 | 402 / 4.78 |

  即：粘贴/长按产生千级字母串时会瞬时冻结（单键 70ms、整段 16.7s），违反 DoD “按键 < 16ms”。约束：五笔码 ≤4、拼音引擎按 **32** 码设计、用户词库编码 ≤ **64**（ADR-029）。
- **决策**：
  1. **组合缓冲区硬上限 `MAX_COMPOSE_LEN = 64`**：达到上限后，后续 `a..z` 字母键**被忽略**（返回 `Consumed`）——不硬截断已输入内容、不误上屏、不透传插入。上限 64 覆盖所有引擎的合法码长（含用户编码 64），不损害任何正常输入。
  2. **引擎门控**：`recompute` 跳过 `max_code_length() < buffer.len()` 的引擎（五笔 4 / 拼音 32），避免对不可能匹配的长码做无用功。
  3. 非字母键（退格/Esc/空格/回车/数字/翻页）在上限处**仍正常**，可回退、取消、上屏。
- **理由**：既钉住 DoD 时间/内存上界，又保持“不回改已输内容”的直觉行为；64 是三个引擎合法码长的并集上界，没有任何合法码长会被截断。
- **复现**：`cargo run --release -p ime-cli --example compose_bound -- data/generated 256,512,1024`。
- **关联**：报告 006 MVP-07、ADR-029、`技术方案.md` §12 DoD；`crates/ime-core`、`crates/ime-cli/examples/compose_bound.rs`。

## ADR-063 正式数据加载失败可诊断（不把样本兜底当正常）

- **状态**：冻结（2026-10-09）
- **背景**：严格打包会阻止缺失文件，但**正式宿主**在资源缺失/损坏时仍静默回退内置样本引擎，只 `NSLog` 一句（报告 006 MVP-09）；用户面对的是一个“只能打几个演示字”的输入法，却得不到任何可见解释。
- **决策**：
  1. `makeSession()` 区分**真实数据加载成功**与**降级**，并记录可读原因：资源目录缺失 / 缺码表 / 码表解析失败 / 缺拼音字表（拼音兜底不可用）。
  2. 一旦降级，宿主**可见**：输入菜单常驻「数据文件错误：…」条目 + **同一错误只弹一次** `NSAlert`（沿用 ADR-059 的去重模式）+ `NSLog`。
  3. 内置样本引擎**仅作为不崩溃的安全网**，绝不当作正常发布功能；提示文案明确“请重新安装完整包”，恢复步骤见 `docs/故障恢复.md` §4。
  4. 独立调试窗口（ADR-024）仍从参数加载真实数据、**失败即退出**（不样本兜底），保持不变。
- **理由**：与配置错误一致，“出错要看得见且不反复弹”；样本兜底保命但不掩盖安装损坏。
- **关联**：报告 006 MVP-09、ADR-059（错误提示模式）、ADR-024；`platforms/macos/Sources/InputController.swift`、`Preview/main.swift`、`docs/故障恢复.md`。

## ADR-064 分发采用 GPL-3.0 §6(d)：二进制包不含源码、同处提供源码包

- **状态**：冻结（2026-10-09）
- **背景**：GPL-3.0-or-later §6 允许多种“传递目标代码”方式；ADR-032 选的是**更严**的做法——发布候选 ZIP 内附完整 `SOURCE/`（含 vendor）。用户希望**发布包不带源码**（体积与分发简洁），但本项目保持 GPL 不换许可。
- **决策**：采用 **§6(d)**——
  1. 二进制包**不再包含** `SOURCE/`；改为在**同一发布位置**提供 `Lampyris-0.1.0-source.tar.gz`（`git archive` 全源码 + `cargo vendor` 锁定依赖 + `SOURCE-COMMIT`），并附 `.sha256`。
  2. 二进制包保留**许可证与声明**：`LICENSE`（GPL-3）、`DATA-LICENSES`、`DATA-SOURCES.md`、`SBOM.cdx.json`、`cargo-tree.txt`，新增 `SOURCE.txt` 写明“对应源码与二进制同处发布”。
  3. `prepare.sh` 同时产出两份产物；`run-repro.sh` 用**源码包**离线重建，与二进制包内可执行文件/默认数据逐字节比对（可审计性不降）。
  4. 仓库可继续保持 private：§6(d) 只要求**源码本身可公开获取**，以源码 tarball 形式提供即可。
- **理由**：满足“包不含源码”同时保持合规；二进制包更小；源码包 + SHA + 离线重建保留第三方审计能力。
- **关联**：ADR-032（本条取代其“发布候选附完整对应源码”的当前做法）、`packaging/README.md`、`packaging/macos/{prepare.sh,manifest.py,RELEASE-README.md}`、`platforms/macos/tests/run-repro.sh`、`docs/{发布说明.md,macos-release-checklist.md}`。

## ADR-065 发布渠道：GitHub Release（产物）+ GitHub Pages（入口）

- **状态**：冻结（2026-10-10）
- **背景**：分发包（二进制 + 对应源码包，ADR-064）需要一个长期、版本化的发布渠道；用户选定 **GitHub Release** 放产物、**GitHub Pages** 放下载指引/文档。当前仓库 private、无 tag/Release/Pages。
- **决策**：
  1. **产物**：GitHub Release，tag 形如 `v0.1.0`；附件 = 二进制 ZIP + `.sha256` + `Lampyris-0.1.0-source.tar.gz` + `.sha256`——**二进制与源码同页**（满足 GPL-3.0 §6(d)）。
  2. **入口**：GitHub Pages 静态站（落地页 + 安装指引 + 指向最新 Release）；站点不承载大文件。
  3. **触发与不自动发布**：`release.yml` 仅 **tag / 手动**触发；初期 `pages.yml` 也仅**手动**（转公开并启用 Pages 后再放开 push）。
  4. **权限最小化**：只有 `release.yml` 拿 `contents: write`；Pages 用 OIDC（`pages: write` + `id-token: write`）；其余工作流保持 `contents: read`。第三方 Actions 固定审定 commit（同 MVP-10）。
  5. **发布不接触签名密钥**：Release 直接使用 CI 已**签名/公证**的 acceptance 产物，避免扩大密钥面。
  6. **前置**：仓库**转公开**（Release/Pages 对公众可用）+ 公开前复核（`docs/reviews/004-public-readiness.md`）+ 分支保护。
- **理由**：Release 提供长期、版本化、带 SHA 的分发点；Pages 提供人类可读入口；二者与 §6(d) “同处提供源码”一致。
- **关联**：ADR-064、报告 006 MVP-11、`docs/reviews/004`、`docs/发布说明.md`、`.github/workflows/{release,pages}.yml`、`site/`。

## ADR-066 用户词库写入不做逐次 fsync（会话结束时 flush）

- **状态**：冻结（2026-10-10）
- **背景**：T-MVP-07 基准（`cargo run --release -p ime-dict --example learn_cost`）显示：`Store::learn` 每次全量原子写 + `fsync`（文件 + 父目录），2,000 次平均 **25.6ms**、最坏 **164ms**，直接阻塞输入线程（选词上屏）。分测：目录 fsync ≈8ms、文件 fsync ≈15ms。
- **决策**：
  1. **写入路径不 fsync**：只做 `write(tmp) + rename`（POSIX 原子替换）——保证文件**一致**。
  2. 新增 `Store::flush()`：在**会话结束**（`focus_out` 释放词库 / `Drop`）与导出时统一 `fsync`；无脏数据时为空操作。
  3. 配置写入（`ime-config`）**仍保留 fsync**（写入频率低，非热点）。
  4. 崩溃最多丢**最近一次学习**，不损坏文件；`docs/故障恢复.md` 补充说明。
- **理由**：用户词库是高频写、且可由用户重建；一致性由原子 rename 保证，耐久性代价换来选词不再卡顿（实测 25.6ms → ~4ms）。
- **关联**：T-MVP-07、ADR-029（有界 TSV v1）、ADR-064；`crates/ime-dict`、`crates/ime-ffi`（`focus_out` 触发 Drop flush）。

## ADR-067 快捷键对齐搜狗/微信且可配置（单独 Shift 切中英）

- **状态**：冻结（2026-10-10）
- **背景**：用户反馈 `Ctrl+Shift+Space` / `Shift+Space` **不生效**（真实 IMK 事件下 `charactersIgnoringModifiers` 未必为 `" "`），且要求对齐搜狗/微信习惯（**单独按 Shift 切中英**、**Shift+Space 切全/半角**）且快捷键可配。
- **决策**：
  1. **全部配置化**：新增 `hotkey.toggle_english`（默认 `"shift"` = 单独按 Shift）与 `hotkey.toggle_width`（默认 `"shift+space"`）；`hotkey.toggle_mode` 保持 `"ctrl+shift+m"`。取值：`shift`（仅 toggle_english 的含义）/ 组合键 `ctrl|shift|alt|cmd + 键` / `none`（关闭）。
  2. **单独 Shift** 通过 `flagsChanged` 检测：按下→记录；抬起且期间无其它键→切中英；与其它键同按（Shift+Space、Shift+字母）不触发。
  3. **空格用物理键码**（49）判定，不再依赖 `charactersIgnoringModifiers`，修复真实派发差异。
  4. 删除宿主硬编码组合；菜单保留「临时中英切换」「临时全/半角」入口。
  5. **事件掩码**：IMK 默认只转发 `keyDown`，必须在 `IMKInputController.recognizedEvents` 中**显式声明** `flagsChanged`（否则 `handle` 收不到修饰键变化，这就是“单独 Shift 不生效”的根因）；同时一并接管 `leftMouseDown` 以保留默认的“点击组合外则结束组合”。
- **理由**：对齐主流中文输入法；可配置适应个体习惯；键码判定对布局/派发更健壮。
- **关联**：`配置架构.md` §5/§6/§8、Skill `add-config-option`、T-MVP-06；`crates/ime-config/src/schema.rs`、`platforms/macos/Sources/{ImeSession,InputController}.swift`、`Preview/main.swift`。

## ADR-068 快捷键/交互对齐主流（中英标点 Ctrl+. 与 ,/. 翻页）

- **状态**：冻结（2026-10-10）
- **背景**：为降低学习成本，要求对齐主流中文输入法。常见默认：中英=**单独 Shift**、全/半角=**Shift+空格**、中英标点=**Ctrl+.**（搜狗/微软/RIME）、候选翻页=**,**/**.**。我们的中英/全半角默认已与主流一致（ADR-067），但**无中英标点快捷键**，且候选态 ,/. 不翻页。
- **决策**：
  1. 新增可配 `hotkey.toggle_punctuation`（默认 `"ctrl+."`）：切换 `input.punctuation`（chinese/english）并**写回配置**；`none` 关闭。

  3. 中英/全半角默认保持 ADR-067（`shift`、`shift+space`），与主流一致。
- **理由**：三项切换键均与搜狗/微软/微信/RIME 一致，用户零迁移成本；同时保留可配置以适应个体差异。
- **关联**：ADR-067、`配置架构.md` §5/§6/§8、Skill `add-config-option`；`crates/ime-config/src/schema.rs`、`platforms/macos/Sources/{Config,ImeSession,InputController}.swift`、`Preview/main.swift`。

## ADR-070 偏好设置面板（Schema 驱动、非模态、即时生效）

- **状态**：冻结（2026-10-11）
- **背景**：PROD-01/ARCH-08、UX-01/TD-04——所有偏好只能改 `config.toml`，普通用户门槛高。`ime_config_schema()` 早已备好；`配置架构.md` §11 验收第 6 条要求“设置界面不含任何选项硬编码，完全由 Schema 渲染”。本次打通该通路。
- **决策**：
  1. **形态**：macOS 宿主内 **AppKit 非模态面板**（`NSPanel`，utility window），入口＝输入法菜单「偏好设置…」（⌘,）。同进程直接调 `ime-config`，**无需 IPC**；不引入 SwiftUI/新依赖。
  2. **零硬编码**：选项清单、类型、范围、默认、分组全部来自 `ime_config_schema()`。为提供中文短标题与枚举显示名，`OptionSpec` 与 C ABI 各**追加两个字段**：`title_zh`、`enum_labels_zh`（与 `enum_values` 一一对应的 NUL 分隔列表，**空串终止**）。持久化值仍是英文标识。
  3. **控件**：bool→复选框、int→步进器、enum→下拉（显示 `enum_labels_zh`）、string（快捷键）→文本框（留空写 `none`）。
  4. **唯一写入路径**：只经 `ime_config_set()`（bool/int 用 TOML 字面量，枚举/字符串用带引号字符串）；不碰 `UserDefaults`/第二文件（R1–R4）。
  5. **即时生效**：`ime_config_set` 广播后由 `ConfigWatcher` 派发（ADR-058）；`ConfigWatcher` 由**单观察者**改为**多观察者**（宿主控制器 + 设置面板各自订阅，`owner` 释放自动失效）。
  6. **枚举终止约定修正**：`build_schema` 原先只给 enum 列表加单个 NUL，与头文件“空串终止”约定和解析器不一致（旧单测只测 `mode`，靠相邻内存为 0 未暴露）；统一补足为空串终止（双 NUL）。
- **理由**：Schema 已有元数据足以驱动表单；加选项时 UI 自动出现，无需改宿主代码（R4）。非模态便于“边打边调”，改动即时写回并广播。
- **关联**：PROD-01/ARCH-08、UX-01/TD-04、`配置架构.md` §8/§9/§11、Skill `add-config-option`；`crates/ime-config/src/schema.rs`、`crates/ime-ffi/{src/config.rs,include/ime.h}`、`platforms/macos/Sources/{Config,Settings,InputController}.swift`、`platforms/macos/Preview/main.swift`。

## ADR-071 用户反馈入口（GitHub Issues，用户主动、App 不发送）

- **状态**：冻结（2026-10-11）
- **背景**：需要给用户一个反馈问题/提建议的入口；但本项目承诺“不联网、零遥测、不出设备、无账号”（`隐私与安全.md` §1），不得引入上报/统计/账号。
- **决策**：
  1. **入口**：输入法菜单新增「反馈问题与建议…」（`IMKInputController.menu()`，紧邻「偏好设置…」）。
  2. **渠道**：打开**公开的 GitHub Issues 新建页**（`https://github.com/EasyIndie/EasyInputMethod/issues/new`）——用户在自己浏览器里、登录后自行决定是否提交；敏感漏洞走 `SECURITY.md` 的私密安全公告（面板内给出该链接）。
  3. **App 不发送任何数据**：仅调用 `NSWorkspace.open(URL)` 将**静态**链接交给系统浏览器；**不在 URL 里预填**环境信息。

- **理由**：这是不引入网络/账号/遥测的可行反馈渠道；用户可见、可控、可审计。`verify-no-network.sh` 不扫描 Swift 宿主，且该动作不产生 socket/DNS 调用；App 自身仍无网络能力。
- **关联**：`docs/隐私与安全.md` §1/§6、`SECURITY.md`、T-P2-03、`ROADMAP` P2；`platforms/macos/Sources/{Feedback,InputController}.swift`、`platforms/macos/Preview/main.swift`。

## ADR-072 迭代工作流：分层 CI 与单人/团队开关

- **状态**：冻结（2026-10-11）
- **背景**：项目为单人迭代，既要快又要保质量；同时希望成熟后平滑支持多人共建。现状：`fuzz`/`macos` 每个 PR 都跑（docs-only 也跑），只有 `make verify` 一个命令；DCO 仅写在 `CONTRIBUTING.md` 无 CI 校验；无 `CODEOWNERS`/覆盖率/基准门禁。
- **决策**：
  1. **CI 分层**（`ci.yml`）：`check`（fmt/clippy/test/deny/verify-no-network）**恒跑**；`macos`/`fuzz` 保留 job **始终上报成功**，仅具体 step 按“代码相关变更”条件化（`scripts/ci-detect-code-changes.sh`），避免必需检查停在 `Expected`。docs-only 仅跳重型，`check` 仍全跑（不降质量）。
  2. **本地提速**：新增 `make fast`（内环）与 `make hooks`（`pre-push` → `make verify`，可 `--no-verify` 跳过）。
  3. **DCO 自动化**：新增 `dco.yml` 校验每个普通提交的 `Signed-off-by`（合并提交豁免）；当前**可见但不阻断**，团队化后由分支保护设为必需。
  4. **团队化开关**：`CODEOWNERS`/必需 review/merge queue/覆盖率与基准门禁等**延后**到 MVP 后或首个外部贡献者，不现在启用。
  5. **不改变现有必需检查与分支保护**（`check`/`macos`/`fuzz` 仍必需）。
- **理由**：路径条件化在不牺牲代码质量的前提下减少 docs-only 等待；DCO “可见不阻断”既暴露问题又不拖个人迭代；团队能力用开关而非重搭。
- **关联**：`AGENTS.md` §6、`CONTRIBUTING.md` §2/§4/§9、ADR-043/065；`docs/开发工作流.md`、`.github/workflows/{ci,dco}.yml`、`Makefile`、`scripts/{ci-detect-code-changes,install-hooks}.sh`、`scripts/hooks/pre-push`。

## ADR-073 反馈入口健壮性：异步打开外部链接 + 可用性门控

- **状态**：冻结（2026-10-11）
- **背景**：`FeedbackUI` 在主线程**同步**调用 `NSWorkspace.open(url)`。当浏览器/LaunchServices 暂时无法完成打开（实测：设备关闭代理、GitHub 不可达）时，该调用阻塞主线程与菜单事件循环，表现为“点击无反应，随后菜单所有项均失效”。用户要求：GitHub Issues 反馈不可用时不显示入口。
- **决策**：
  1. 打开外部链接统一走**异步** API `NSWorkspace.open(_:options:configuration:completionHandler:)`（`FeedbackUI.openExternally`）；**禁止**再用同步的 `NSWorkspace.open(url)`；失败仅记日志。
  2. 菜单「反馈问题与建议…」仅在 `FeedbackUI.isAvailable` 为真时显示；判据是**纯本地**的 LaunchServices 查询（系统是否存在能打开该 https 链接的应用），**不联网、不探测 GitHub 可达性**（铁律 1）。
  3. **边界**：网络层不可达（如代理关闭导致 GitHub 打不开）在零网络前提下本机无法识别；此场景入口仍显示，但点击不再卡死，浏览器展示其自身的网络错误页。
- **理由**：非阻塞是纯粹的正确性修复（与网络无关）；可用性门控只能建立在零网络可获知的信息上，否则违反铁律 1。
- **关联**：ADR-071/072；`platforms/macos/Sources/{Feedback,InputController}.swift`、`docs/隐私与安全.md` §6、T-P2-03。

## ADR-074 反馈入口改为完全本地（复制模板，不打开浏览器）

## ADR-076 输入状态回到一级菜单（显示当前值与快捷键）

## ADR-081 零诊断门禁（0 警告 0 错误，本地 + CI）

- **状态**：冻结（2026-10-11）
- **背景**：`make verify`（pre-push 门禁）长期**通过但刷屏**：477 行输出里有 cargo 的 `output filename collision`、cargo-deny 的 `wildcard` / `license-not-encountered`，以及 swiftc 的条件转换告警。它们都不是失败，但会变成“背景板”：真出问题时没人看得见。
- **决策**：
  1. **规则**：任何工具链诊断（`cargo` / `rustc` / `clippy` / `cargo-deny` / `swiftc`）必须为 **0**；出现即当作失败修掉。
  2. **新增 `scripts/check-clean.sh`**：运行命令并原样转发输出，同时扫描 `warning:` / `error[…]` / `bug[…]` / `path:line:col: warning:`；命中则非 0 退出。因为 `cargo test` / `cargo deny` **有警告也返回 0**，而 clippy 的 `-D warnings` 看不到 cargo 自身的输出。
  3. **接入**：`make lint / test / deny / fast / verify` 统一经它把关；CI 的 `check` job **改为直接调这些 make 目标**（门禁单一实现，不漂移）；`build.sh` / `dev-preview.sh` 的 `swiftc` 加 `-warnings-as-errors`。
  4. **清完既有噪声**：workspace 内部依赖在 `[workspace.dependencies]` **显式写 `version`**（否则 cargo-deny 判为通配符 / 解析失败）；`deny.toml` 置 `unused-allowed-license = "allow"`（许可清单是**政策**而非当前集合）；`ime-pinyin` 的生成 example 用 `[[example]] name = …` 取唯一输出名（不改文件名与生成数据里的路径标注）；修掉 Swift 的两处多余条件转换。
- **理由**：质量门禁只有在“全绿即无噪声”时才能被人信任；而门禁实现为「同一次运行 + 一次 grep」，**不额外编译**，`make fast` 仍是内环、重活仍只在 CI 的 `macos` job，故不影响迭代效率。
- **关联**：ADR-072（分层 CI / hooks）；`scripts/check-clean.sh`、`Makefile`、`.github/workflows/ci.yml`、`deny.toml`、`Cargo.toml`、`platforms/macos/{build.sh,dev-preview.sh,Sources/InputController.swift}`；`docs/开发工作流.md` §4。

## ADR-082 引擎常驻内存优化（MEM-1：紧凑数组 + 简繁懒加载）

- **状态**：冻结（2026-10-11）
- **背景**：机器 B（macOS 27 / arm64）实测宿主物理足迹 **43.8 MB**，超 [`技术方案.md`](技术方案.md) §12「常驻内存 ≤ 30 MB」。用 `ime-ffi/examples/mem_probe`（`/usr/bin/time -l`）测得引擎峰值 RSS **22.08 MiB**：启动 0.9 + 五笔 7.9 + 拼音 5.6（字 1.9 + 词 3.7）+ **简繁 7.7**。根因是所有表都**逐条 `String` 分配**（`Vec<(String, Vec<Entry>)>`、多张 `HashMap<String,…>`），既无字符串 interning 也无紧凑存储，2.17 MB 文本膨胀约 11×。
- **决策**：
  1. **简繁表按需懒加载**（`ime-ffi`）：默认 `input.chinese_variant = simplified` 时**不**加载 `variant-s2t.tsv`；首次切到繁体时才载入。切换点见 `session`/`InputController`。
  2. **`ime-table::Table` 改紧凑数组**：`code` 与 `text` 各自的字节拼到连续缓冲，用偏移/长度索引；候选按 `(text_off, text_len, weight)` 扁平存储，组用区间表示。不再逐条 `String`/`Vec` 分配。对外查询 API（`exact`/`prefix`/`Engine`）**行为不变**。
  3. **`ime-pinyin::TablePinyinBackend` 精简**：**本轮推迟**（见“结果”：引擎已在预算内，无必要先改）。
  4. **设置面板关闭即释放视图树**：`SettingsPanel.windowWillClose` 置空 `window`/`rows`/`sectionViews`，降低驻留节点（下次 `show()` 重建）。
  5. **内存纳入回归**：新增 `crates/ime-ffi/examples/mem_probe.rs` 作为可复现的稳态基线工具；`技术方案` §12 门槛保持 **≤ 30 MB**（本轮以优化达标，不改门槛）。
  6. 文本 TSV 仍是**唯一真值**（ADR-060 不变）；不引入 mmap/二进制格式（本轮）。
- **理由**：11× 膨胀来自「每条一个小分配」的常数开销（malloc 头 + `String`/`Vec` 容量），压缩为连续内存后，同等数据的内存占用先看**内容本身**而非分配次数；简繁懒加载则让**默认路径**完全不背这份成本。
- **结果（2026-10-11，机器 B macOS 27 / arm64）**：
  - 引擎**稳态**物理足迹：五笔 **2.19 MiB**；+拼音字 4.50、+拼音词 **6.73**、+简繁（懒）6.77（简繁未加载）。
  - 宿主**全新启动**：**23.3 M**（优化前 43.8 M）；`run-imk-acceptance.sh` **14/14**（⑪ 23.3M ≤ 30M）。
  - 已知：**打开偏好设置面板**会临时抬升（~+15M），根因是 **macOS 27 AppKit 内部用 SwiftUI/AttributeGraph 渲染 + 体型较大的 AppKit 主题**（`malloc_history` 已定位，非我们的数据）；关闭后释放控件对象，但分配器不必然交还页面。故 ⑪ 在**正常输入场景**达标；面板驻留作为 macOS 基线记入 `MVP-05.md` §2.4。
- **关联**：ADR-060（词典结构，本 ADR 是其「触发条件下优化」的落实）、ADR-069（简繁）；[`docs/tasks/T-P2-04-memory.md`](tasks/T-P2-04-memory.md)、`crates/ime-table`、`crates/ime-pinyin`、`crates/ime-ffi`、`platforms/macos/Sources/InputController.swift`、`crates/ime-ffi/examples/mem_probe.rs`。

## ADR-085 实机验收临时剪贴板与输入源恢复

## ADR-086 验收动作限定已登记对象及聚焦文本控件

- **状态**：采纳（2026-10-11，IT-01第三子步）。
- **决策**：两实机脚本的输入、快捷键、读取和清空动作共用所有权检查；同一次AppleScript中核对目标应用frontmost与前台文档/窗口ID，然后执行限定动作。文本输入还需AXFocusedUIElement为预期文本角色。任一检查失败立即退出，不能重新前置已有窗口后继续。TextEdit读取/清空显式寻址登记ID，不使用front document作为写入目标。

- **关联**：ADR-083/085，IT-01。原生应用协议及控件角色仍须隔离实测；此步不解除live禁用。

## ADR-087 IMK验收配置恢复保护与输入源还原

- **状态**：采纳（2026-10-11，IT-01第四子步）。
- **决策**：IMK脚本切换前读取原输入源精确ID，退出还原；配置文件监听/损坏测试使用临时恢复日志记录原始字节和测试最后已知文件摘要，修改前核对，退出只在摘要仍匹配时原子恢复。外部修改、未登记写入、恢复失败均保留日志和备份，报告BLOCKED，不覆盖新内容。源文件不存在/符号链接时拒绝启动该测试。

- **理由**：本机TextEdit及CocoaStandard字典的document未定义id，window才定义integer id；此前mock只验证脚本生成，不能证明协议可执行。
- **关联**：ADR-083/086的所有权原则继续有效，以本ADR修正对象类型；原生AX/实际创建关联仍待隔离验证。

## ADR-089 原生无输入协议探针及有界执行

- **状态**：采纳（2026-10-11，IT-01隔离验证）。
- **决策**：协议探针只创建空白TextEdit文档、校验窗口关联并关闭本次对象；不发按键、不读既有文档或改变输入源/配置。正常/注入失败两路径核对原有窗口ID保留。AppleEvent超时5秒，外层进程超时15秒；非零/超时必须BLOCKED，禁止记为通过。锁屏时停止UI验证，待解锁再执行。
- **理由**：本轮锁屏导致原生请求无返回，编译和mock不能证明运行时协议。超时后无法确认对象状态时不关闭front/every文档。
- **关联**：ADR-088、IT-01；当前原生实测仍未通过。

## ADR-093 快捷键语义校验与跨宿主规范表示

- **状态**：采纳（2026-10-12，IT-04）。
- **决策**：ime-config统一解析快捷键，大小写不敏感、允许token两侧空白；control/option/command别名规范为ctrl/alt/cmd，修饰键按ctrl/alt/shift/cmd排序。空串及none关闭；仅中英切换允许单shift。组合键需至少一个不重复修饰键及一个ASCII图形字符（不含+）或space；不支持其他命名键。有效快照内不同动作不能使用相同快捷键（含默认值）；非法或冲突设置不写文件，重载保留上一快照。FFI提供按配置键读取的kind/modifiers/key规范结构；菜单与执行共用Swift适配器，宿主不重复解析配置语法。
- **理由**：当前自由字符串接受banana和冲突键，菜单与运行时别名解析不同；必须将校验和规范表示集中在唯一配置模块。
- **关联**：ADR-070、IT-04、配置架构。默认键保持；旧非法配置需按可见错误修复，首次坏配置回落默认值，禁用项不参与冲突。

## ADR-094 全半角持久偏好变化取代临时覆盖

- **关联**：IT-05、ADR-028、配置架构§5。

## ADR-095 组合中引擎设置更新无提交重算

- **状态**：采纳（2026-10-12，IT-06）。
- **决策**：会话仅在引擎选项实际变化时重新configure；若正在组合，以原buffer重新计算候选，忽略引擎自动提交意向并回第一页。无变化/重复通知及外观更新不重算，不改buffer、committed或会话模式。FFI同步刷新个人词库排序及候选视图；两宿主既有通知路径直接调用configure即可更新。
- **理由**：旧configure只改引擎标志，缓存候选不更新；每键都会configure，不能无条件重算或触发隐式自动上屏。
- **关联**：IT-06、ADR-058。真正键入仍保留既有自动提交规则。

## ADR-096 保存失败可见且已识别快捷键不透传

## ADR-097 资源错误与有效字形状态

## ADR-098 进程内错误提示统一门控与串行呈现

- **状态**：采纳（2026-10-12，IT-09）。
- **决策**：配置/数据提示由进程单例门控，按通道记录当前错误周期已提示的消息，控制器切换不重复弹窗；通道恢复清空周期，后续错误可重新提示。提示排队串行，显示前重新读取当前原因，已恢复/改变的过期项不弹出。设置和输入菜单保留当前错误文本，不持久化错误记录。
- **理由**：旧每个IMK控制器各自记录lastAlerted，切客户端重复打断；异步排队在恢复后仍可能弹旧错误，嵌套模态框也影响输入。
- **关联**：IT-09、ADR-059/096/097；UI提示状态是临时内存，不新增配置存储。

## ADR-104 基础模糊音按音节有界扩展与精确优先

## ADR-106 用户词库失败不发布内存变更

## ADR-159：五笔非首项主动选择的自适应本地学习权重

- **状态**：工程实现与本地验证通过，新包原生验收待推进（2026-10-14，IT-25）。
- **证据**：私有词库首项1000、同组后项0；连续4次主动选择后项并重新加载，旧实现仍保持历史首项。学习写入存在，但单位计数难改变累计历史偏好，不等于用户已装包的具体根因全部确认。
- **决策**：五笔非首项数字/显式候选选择（含后页第一项）采用自适应学习增量：同来源、同精确/补全类别、与当前输入匹配的已学其他候选最大权重/4向下取整＋1；目标原权重加此增量。后页空格也视为主动选择；首页空格和首页首项仍加1，拼音仍沿原策略。低历史权重时与原单位学习一致；不因一次误选必然抢首。
- **存储**：沿有界TSV v1四列，词频列明确为学习权重，不再承诺实际输入次数。无时间/文档/应用上下文、无新配置或依赖。候选组权重接近u32容量上限时同组权重减半（正值至少1）再更新，避免饱和永久固化；归并及重算在既有原子事务内。旧文件兼容，不批量迁移/删除词条。
- **边界**：排序层级和基础词频不变；当前已显示候选不跳位，下一组合反映新权重。明确选择不等于允许忽略重码自动上屏，四码唯一契约不变。通配匹配不能直接拿含z查询作词库前缀，退回所选完整码同组。写失败不改变内存快照、不阻碍已提交文本。
- **关联**：IT-25、报告010、ADR-029/060。验证普通与主动学习、精确/补全/来源边界、后页数字、重载、失败回滚、近饱和、跨进程合并、零网络与strict宿主；新包原生验收尚待。

## ADR-162 拼音组合中的显式音节隔音符

- **状态**：采纳（2026-10-14，IT-27第一步）。
- **决策**：拼音或混输组合且有拼音后端时，ASCII单引号作为音节边界写入原码，不触发标点提交；连续分隔符消费但不重复加入。未组合、英文和纯五笔保留原引号行为。缓冲长度仍有界，退格/取消/原码Enter沿既有规则。
- **解析**：按分隔符切开后分别最长合法切分，各段必须完整且非空；不得跨显式边界合并音节，未完成尾段无候选，等待后续字母。xian与xi'an可区分；既有简拼及v代ü不变。显式边界先只走精确拼音，不展开模糊音以免改写边界。
- **学习**：候选采用标准空格音节码，持久化仍规范成现有无空格字母码，不把单引号写入词库。无音节边界元数据的自建词不因简单删除隔音符强行匹配；合法词表候选仍获得既有学习加权。无格式迁移/配置/新数据。
- **理由**：默认xi'an会中途提交西‘，已有西安词表因此不可达；隔音符是基础拼音语法，不扩展成整句或全简混拼。
- **关联**：IT-27、报告011；常用多音读音权重属于后续独立评估，不随此改动手调词频。最终包原生待验。

## ADR-163 构建期多音字次读音保守权重

- **状态**：采纳（2026-10-14，IT-27第二步）。
- **证据**：现有生成器把jieba单字全频次复制给D5所有读音，默认xian首选见/省而先第3，xing省压住行。只按词组比例重分会使地de、降xiang等常用次读音跌出首屏，拒绝该方案。
- **决策**：只改变构建期拼音字表权重，不改运行时排序/协议。D5首选读音权重保持jieba全字频次W；其余读音权重=max(1,min(W,floor(W/3)+E))。E为D4权威词读音与D10有频次词表交集、逐字音节对齐且均被D5收录的词频之和；同词仅计一次，以最终D4读音为准。无语料支持时仍保留三分之一底线，缺单字频次W=1，保留全部合法读音。E用u64饱和累计。

- **关联**：IT-27、ADR-162、报告014；纯拼音及混输首屏、隔音符/简拼/v代ü/学习回归，最终包原生待验。

## ADR-176 教学覆盖的有类型核验与不确定性

- **状态**：采纳（2026-10-15，D2/D14教学扩充）。

- **许可**：发布D2派生内容前扩充来源用途及派生登记，附aardio MIT全文与版权；不打包上游字体/PUA，不导入D3编码列。项目键位事实/核验记录与派生物保留CC-BY-SA-4.0归属。
- **性能/证据**：教学行按Unicode排序建立只读索引，以二分定位，不在每个输入按键全表扫描；生成器报告完整/选根/部分/拒绝覆盖及SHA，可复现。测试分别覆盖三类真实规则、missing及不一致拒绝，不把“码相同”冒充完整语义核验。

## ADR-208 默认快捷键统一 ctrl+shift 前缀

- **状态**：采纳（2026-10-18，用户要求；配合 ADR-206/207 的菜单行样式）。
- **问题**：原有默认值前缀不统一（`ctrl+.`、`ctrl+,`、`shift+space` 等），记忆成本高；学习区默认在某些旧配置里为 `none`，菜单与设置难以形成一致的心智模型。
- **决策**：优先平台/主流输入法惯例，其次才用统一前缀。最终默认值：模式 `ctrl+shift+m`、全/半角 `ctrl+shift+space`、学习区 `ctrl+shift+l`、关于 `ctrl+shift+a`；中英切换保留单独 `shift`（对齐搜狗/微信）；设置 `ctrl+,` 沿用平台惯例；标点改为 `ctrl+shift+.`（实测单个 `ctrl+.` 在 IMK 路径下被系统当作取消键吞掉，无法触发）；简/繁由 `ctrl+shift+f` 改为 `ctrl+shift+t`（`ctrl+shift+f` 与常见编辑器的全局查找冲突）。默认值仍只由 `crates/ime-config/src/schema.rs` 定义；设置页可改、可 `none`，冲突检测沿用 ADR-093。**已有显式配置不静默覆盖**，需在设置页修改，或由用户明确要求时按 `ime-config` 写回。
- **取舍**：统一前缀可记忆，但 `ctrl+shift+s/p/f` 在编辑器里各有含义；因此只对“没有公认惯例”的动作使用统一前缀，其余回到惯例键。
- **验证**：ime-config 单测（默认值与唯一性/冲突校验）；组件与预览回归核对菜单右侧提示；真机确认新默认生效、旧显式值保持到用户改动为止。

## ADR-209 默认快捷键改用 Option（⌥）语义前缀

- **状态**：采纳（2026-10-18，用户要求「以 Option/Alt 表示开关或选项，让快捷键与功能语义对应，并避免与系统/其它应用冲突」；取代 ADR-208 的前缀部分）。
- **问题**：ADR-208 的统一 `ctrl+shift` 前缀与系统输入法切换键 `⌃Space` 冲突：切换输入源后仍按住的空格会被重投递给新输入法，快按 Shift 时被当成 `⌃⇧Space` 而误切全/半角（报告 074）。同时 `ctrl+shift+<字母>` 在编辑器里语义彼此无关，记忆成本高。
- **决策**：默认值统一为 **⌥（Option/Alt）+ 语义首字母**，中英切换仍为单独 `⇧`（搜狗/微信惯例）：模式 `alt+m`、全/半角 `alt+space`、中英标点 `alt+p`、简/繁 `alt+t`、学习区 `alt+l`、设置 `alt+,`、关于 `alt+a`。默认值仍只写在 `crates/ime-config/src/schema.rs`，作用域不变；`none`/空仍表示关闭，冲突检测沿用 ADR-093；**已有显式配置不静默覆盖**。
- **理由（实测）**：`defaults read com.apple.symbolichotkeys` 中已启用的系统快捷键里没有「仅 ⌥ + 字母」的组合（含 ⌥ 的都带 ⌘ 或 ⌃，如 `⌃⌥Space`、`⌃⌥⌘8`），`⌘Space`（Spotlight）与 `⌃Space`（切换输入法）也都不被占用；`alt+space` 因此彻底避开系统切换键。US/ABC 布局下 `⌥M`=µ、`⌥T`=†、`⌥P`=π、`⌥L`=¬、`⌥A`=å、`⌥,`=≤、`⌥Space`=NBSP，**均非死键**；`⌥E/N/U/I` 是死键（´ ˜ ¨ ˆ），**禁止绑定**，本轮未使用。
- **取舍与风险**：① Option+字母本来是 macOS 输入特殊符号的方式，绑定后这些符号在输入法激活时不可输入（µ † π ¬ å ≤ NBSP）；② Terminal/readline 的 Meta 绑定（`M-t` 交换词、`M-l`、`M-a`）与部分编辑器快捷键会让位，用户可在设置页改绑或关闭；③ 不绑定 `⌃⌥`（VoiceOver 的 VO 键）与 `⌘` 组合（系统/应用快捷键密集区）；④ 逗号键在 `⌥,` 下会失去 ≤ 输入，仍可通过设置改回。
- **验证**：`cargo test -p ime-config`（默认值/冲突/别名）；`settings-presentation`（⌥L/⌥空格/⌥,/⌥A 显示）；`controller-menu`/`preview-menu`（菜单 keyEquivalent 为 Option）；`Preview` 自测改按 ⌥M/⌥P/⌥T/⌥Space；`make verify` 全绿。系统菜单实机与其它应用冲突矩阵仍待新签名包复验（报告 075）。
- **关联**：ADR-068/181/207/208（历史默认值）、报告 074/075、`docs/配置架构.md`。

## ADR-210 全/半角默认快捷键由 ⌥Space 改为 ⌥F

- **状态**：采纳（2026-10-18，用户报告 `⌥Space` 与 ChatGPT 的虚拟宠物/陪伴输入快捷键冲突；局部取代 ADR-209 中的 `alt+space`，其它默认值不变）。
- **问题**：`⌥Space` 原本用于避开 `⌃Space`（切换输入法）与 `⌘Space`（Spotlight），但空格本身就是高频占用键：ChatGPT 桌面端的虚拟宠物输入也绑定了 `⌥Space`，两者在输入法激活时直接冲突；且 `⌥Space` 在文本中等价 NBSP，误触代价高。
- **决策**：`hotkey.toggle_width` 默认值改为 **`alt+f`**（F = Full-width / 全半角），其余默认仍按 ADR-209：模式 `alt+m`、中英 `shift`、标点 `alt+p`、简繁 `alt+t`、学习区 `alt+l`、设置 `alt+,`、关于 `alt+a`。默认值只写在 `crates/ime-config/src/schema.rs`；冲突检测沿用 ADR-093；**已有显式配置不静默覆盖**，需在设置页修改。
- **理由**：① `⌥F` 在 US/ABC 布局下输出 `ƒ`（非死键），可正常绑定；② 与现有 `⌥M/P/T/L/,/A` 无重复，且避开 `⌥Space`/`⌃Space`/`⌘Space` 三条与空格相关的系统或应用快捷键；③ F 覆盖 Full/Half 语义，符合 ADR-209 的「语义首字母」原则；④ Terminal 的 `Meta-F`（forward-word）会让位，这与 ADR-209 已接受的 Meta 绑定取舍一致。
- **取舍与风险**：`⌥F` 会占用 `ƒ` 输入；Terminal/readline 的前移词快捷键失效。用户可在设置页改绑或设为 `none`。
- **验证**：`cargo test -p ime-config`（默认值/冲突/别名）；`settings-presentation` 与 `ui-snapshots` 显示 `⌥F`；`wubi-learning` 的宽度快捷键用例改按 `⌥F`；B 实机把已装包配置改为 `alt+f` 后菜单与四状态往返生效（报告 079）。
- **关联**：ADR-209（被局部取代）、ADR-093、报告 074/075/078/079、`docs/配置架构.md`、`docs/发布说明.md`。

## ADR-211 统一输入法状态反馈（光标旁 HUD）

- **状态**：采纳（2026-10-18，用户要求「设计统一的输入法状态变化感知方式，让用户在操作菜单或快捷键后能及时确认变化」）。
- **问题**：中英、全/半角、简/繁、标点、模式、学习区等状态只在输入法菜单文字和设置页里变化。菜单在中文输入法激活时不一定可见（终端、全屏应用、远程会话尤其明显），用户按完快捷键后无法确认是否生效，容易误以为是「快捷键/透传失效」。
- **决策**：新增统一的轻量状态浮层（HUD）：
  - 触发：所有会改变状态的菜单命令与快捷键共用同一入口——中英（中文/英文）、全半角（全角/半角）、简繁（简体/繁体）、标点（中文标点/英文标点）、模式（混输/五笔/拼音模式）、学习区（学习区：开/关）。
  - 呈现：光标上方 8pt 的胶囊，14pt 内边距、34pt 高、圆角 10；1.15s 后淡出（遵循「减弱动态效果」时无动画）。
  - 行为：不抢焦点、不接收鼠标、不写任何配置、不改变输入会话；定位取 IMK 光标矩形，取不到退回鼠标位置并夹在屏幕可见区内。
  - 无障碍：`NSAccessibility` announcement 播报同一文案；视图本身带 `staticText` 角色与标签。
  - 测试隔离：`NSApp.activationPolicy() == .prohibited` 或离屏验收环境下不创建浮层。
- **补充（同日，候选窗内联）**：候选框可见时不再弹 HUD，改为在顶部右侧、翻页区左侧显示两字状态芯片（混输/五笔/拼音、中文/英文、全角/半角、简体/繁体）加一个标点符号芯片（`。`/`.`）；学习区不在头部显示，因为候选框下方学习区本身即可感知。激活态用 accent 底色，默认态弱化为次要色；芯片宽度随内容变化，右对齐到翻页按钮左侧并保持同一中心线，候选窗重新定位以防超出屏幕。候选窗关闭时仍用 HUD；HUD 的定位由后续 ADR-212 改为固定屏幕位置（不再跟随光标）。
- **理由**：候选窗只在组合态出现，菜单又依赖输入法激活；HUD 是唯一跨应用、跨全屏/终端都一致的确认方式。文案映射集中在 `StateFeedback`，菜单、设置与 HUD 共用同一份语义，避免三处各写一套。
- **取舍**：默认常开，暂不新增关闭开关（如需要再加 `appearance.state_hud`，需单独 ADR）；1.15s 的浮层不阻塞输入，但会出现在录屏/截图中。
- **验证**：`make macos-ui-snapshots` 新增亮/暗 HUD 快照与文案断言；`controller-menu`（无窗口）验证菜单命令路径与文案映射；快捷键路径由 `wubi-learning`/本地验收覆盖；`make verify` 全绿。
- **关联**：ADR-206/209/210、报告 080、`platforms/macos/Sources/StateHUD.swift`。

## ADR-212 状态提示改为固定位置（屏幕顶部居中），不再跟随光标

- **状态**：~~采纳~~ **被 ADR-213 取代（同日，用户认为离屏观感不佳）**（2026-10-18，报告 083 实测 `attributes(forCharacterIndex:)` 在空行/末尾返回空或异常矩形，光标跟随不可靠；用户要求改为固定、可预期的提示位置）。
- **调研**：macOS 自带的输入源切换提示在 Sonoma 后靠光标显示，但系统不聚焦输入框时可能完全不显示，社区也有「位置飘忽/打扰」的反馈；第三方 LnHud 默认**屏幕居中**、可选 9 宫格与显示器，理由是「菜单栏角落容易错过、全屏时不可见」；LangBanner 在**当前工作显示器居中**显示大号提示；Fcitx5 也有独立的 OSD overlay。`UNUserNotification` 不适合高频开关：需要授权、受专注模式/通知中心排队影响、无法自定义时长与位置，还会堆积通知历史。
- **决策**：
  - 状态提示（HUD）改为**固定位置**：当前鼠标所在显示器的可见区域**顶部居中**（菜单栏下 16pt），不读取光标矩形；找不到鼠标所在屏时退回主屏。
  - 仍为非激活、点击穿透的 `NSPanel`，跨 Space/全屏显示；1.15s 后淡出，遵循「减弱动态效果」，VoiceOver 播报。
  - 候选框可见时继续用候选框内联芯片，不弹 HUD（ADR-211 保持）。
  - **不使用应用通知**做状态提示；通知只保留给真正的错误/一次性事项（现有错误弹窗不变）。
- **理由**：固定位置可预测、可自动化断言，不依赖 IMK 的不可靠矩形；顶部居中是 macOS 输入源提示的传统位置，既不挡正文又足够醒目；鼠标所在屏与「当前工作区」一致，多屏下不会跑到别的显示器。
- **取舍**：提示离光标较远，需要用户抬眼看一次；后续若需要可加 `appearance.state_hud_position`（center/corner）配置，需另开 ADR。
- **验证**：`StateHUDLayout` 纯函数单测（居中、顶部间距、屏幕选择）；`candidate.hud` 亮暗自适应断言保留；离屏快照与真机复验见报告 084。
- **关联**：ADR-211（候选内联芯片保留；HUD 定位部分被本 ADR 取代）、报告 083/084、`platforms/macos/Sources/StateHUD.swift`。

## ADR-213 状态提示回到光标跟随，且仅在聚焦输入框时显示

- **状态**：采纳（2026-10-18，用户否决 ADR-212 的固定位置：离屏截图观感不佳；要求与 macOS 自带输入源提示保持一致——靠光标、无聚焦时不显示）。**取代 ADR-212**。
- **问题**：固定顶部居中虽然可预测，但离光标远、观感突兀；macOS 自带输入源提示本身是光标旁的小图标，用户对「在光标附近出现」已有心智预期。
- **决策**：
  - 状态 HUD 回到**光标上方**（水平居中于插入点、间距 8pt），不再固定屏幕位置；到时不作淡出动画（后台宿主里 `NSAnimationContext` 可能不推进），直接隐藏以保证可靠可见。
  - **只有聚焦文本输入框且能取到有效光标矩形时才显示**；取不到（无客户端/空文档/`attributes` 返回零）时**不显示**，不再退到鼠标位置。
  - 屏幕按光标所在屏选择并夹在可见区内；候选框可见时继续用内联芯片（ADR-211）。
  - 不使用应用通知。
- **理由**：把「位置可预测」建立在「只在有焦点的输入框附近出现」这一与系统一致的行为上；去掉鼠标兜底后，提示不会再出现在与输入无关的位置。
- **取舍**：空文档或客户端不暴露光标矩形时没有提示（与系统行为一致）；需要用户在真实输入场景中验证。
- **验证**：`candidate.hud-position` 改为断言光标上方定位、边界夹取、零矩形不显示；隔离窗口/真机复验见报告 085。
- **关联**：ADR-211（候选内联芯片）、ADR-212（被取代）、**ADR-214（修订「空文档」与光标来源）**、报告 083/084/085/094。

## ADR-214 状态 HUD 的光标来源：firstRect 优先，attributes 只对有文本的客户端兜底

- **状态**：采纳（2026-10-19，用户澄清预期；**修订 ADR-213 中「空文档不显示」的表述**）。
- **问题**：A 机（macOS 13.7.8）验收（报告 094）暴露三件事：
  1. **终端不显示**：Terminal.app 有聚焦光标、候选窗定位正常，但状态 HUD 不出现——日志显示 `hudCaretRect()` 连续 64 次
     `attributes(forCharacterIndex:)` 都拿不到有效矩形，最终返回 nil；
  2. **Finder 误显示**：Finder 前台（桌面/图标视图，没有文本输入框）切换状态仍弹 HUD，位置在桌面某处——
     Finder 的图标视图文本客户端 `length()==0`，却能从 `attributes` 返回一个“伪光标”矩形；
  3. **空文档**：用户确认「有焦点光标就该显示」，ADR-213 原文「空文档不显示」与实际预期不符。
- **决策**（2026-10-19 首轮真机测量后修正，见报告 095）：
  - HUD 光标矩形由 `StateHUDCaretResolver` 解析：**`attributes(forCharacterIndex:)` 优先**（AppKit 文本视图的线高矩形，位置准），
    **`firstRect(forCharacterRange:)` 兜底**（终端类客户端只实现这一条）；两者都取不到时不显示（仍不退到鼠标位置）。
  - **没有文本的伪光标不算**：光标中心必须落在**前台应用的普通窗口（层号 ≥ 0）**内，否则不显示。
    Finder 桌面/图标视图的伪光标只落在桌面层窗口里；Finder 搜索框、TextEdit、终端都在普通窗口里。
    （报告 096 实测：`windowLevel()` 对 Finder 桌面与搜索框都返回 19，不能用来区分；改用窗口归属判断。）
  - **屏内校验**：解析出的光标中心必须落在某块屏幕内，否则不显示（终端等客户端会返回翻转/像素坐标的矩形）。
  - **前台应用校验**：缓存的 `activeClient` 只在它的 `bundleIdentifier()` 等于当前前台应用时才使用，避免跨应用陈旧定位。
  - 同一解析器沿用「光标在空行/末尾时向前回退最多 64 个字符」的既有规则。
- **实测数据（A，macOS 13.7.8，包 `7f51687` 只走 firstRect 的临时版本）**：
  TextEdit 用 `firstRect` 时提示底边距行顶 13pt（`attributes` 路径为 8pt）→ 位置更准的是 `attributes`；
  Finder 桌面 `firstRect` **也返回有效矩形**（(64,644)，所以光换 API 治不了 D7）；
  Terminal 的 `firstRect` 可用（光标/窗口在屏外时提示也跟着到屏外），但垂直比光标行顶高 26pt（行高 18 + 8）。
- **理由**：把「有没有真实插入点」交给两个互补 API 判定，而不是按应用名做例外；终端与 AppKit 文本视图都实现 `firstRect`，
  而图标视图的“文本客户端”没有真正的插入点。
- **取舍**：若有客户端只实现 `attributes` 且 `length()==0`，会失去 HUD（与系统输入源提示一致）；需要在真机复验。
- **验证**：`candidate.hud-source` 断言六种组合（空文档 / 终端式 firstRect / Finder 伪光标 / Finder 重命名 / attributes 优先 / 都取不到）+ 屏内校验；
  A 机 Swift 5.8.1 下同源 `Sources/*.swift` 编译的小程序 **9/9 PASS**；真机（Terminal / Finder / TextEdit 空文档）待新签名包复验（报告 095）。
- **关联**：ADR-211（候选内联芯片）、ADR-213（本 ADR 修订其中「空文档」与客户端来源部分）、报告 087/094。

## ADR-215 验收专用数据根覆盖（LAMPYRIS_SUPPORT_DIR）

- **状态**：采纳（2026-10-19，IT-01 隔离验收需要）。
- **问题**：真实 IMK 验收必须跑**已安装**宿主，而宿主的数据根写死为 `~/Library/Application Support/Lampyris/`；
  验收过程中的学习写入会改动用户真实配置/词库，IT-01 因此一直无法安全执行（`run-imk-acceptance.sh` 保持 `exit 3`）。
- **决策**：
  - `ImePaths.supportDirectory()` 在环境变量 `LAMPYRIS_SUPPORT_DIR`（**绝对路径**）存在时改用该目录；
    未设置时行为与以前完全一致。配置与词库都经这一条路径（词库路径 = 配置文件同目录下的 `user-dictionary.tsv`），
    因此一个变量即可把两者的读写重定向到私有根。
  - 仍然**只经 `ime-config`** 读写配置；不写入 `UserDefaults`、注册表或第二个配置文件；不改默认路径、不改 Schema。
  - 只读环境变量、只影响当前进程；不提供命令行开关、不做持久化，产品默认行为不变。
- **理由**：让「已安装宿主的真实 IMK 验收」与「用户数据」解耦，是 IT-01 的核心前提；用环境变量比新增配置项更窄、
  更易审计（`launchctl setenv` / `launchctl unsetenv` 即可开关，且不落盘）。
- **取舍**：任何能设置该变量的进程都能改宿主数据根——因此只在本机验收使用，并且验收后必须 `unsetenv` 并核对
  真实 `config.toml`/词库摘要未变。不是面向用户的功能。
- **验证**：`ImePaths.supportDirectory(environment:applicationSupport:)` 为纯函数，可在单测里断言三态
  （未设置→Application Support/Lampyris；绝对路径→该路径；相对路径→忽略）；真机验收见报告 098。
- **关联**：ADR-056（数据目录）、ADR-083…091（IT-01 所有权/隔离）、报告 097/098。

## ADR-216 隔离公证 CI 的架构与目标根扩展

- **状态**：采纳（2026-10-19，IT-14 前置需要）。
- **问题**：ADR-129 的隔离公证流水线只能产出 arm64、且目标根被写死为 `/private/var/folders/…`；
  A（Intel / macOS 13）上「已装独有包输入 / Safari / Terminal」因此全部 BLOCKED（报告 100）。
- **决策**：
  - 工作流增加 `arch` 输入（`arm64` / `x86_64` / `universal`）。固定 arm64 runner，Rust 用 `--target`
    交叉编译 `ime-ffi` staticlib，Swift 侧显式 `-target <arch>-apple-macosx13.0`；`universal` 用 `lipo` 合并。
  - 目标根不再限定 `/private/var/folders`，改为「接收设备的系统临时目录内」：`/private/var/folders/<A>/<B>/T/`
    或 `/private/tmp`、`/tmp`、`/private/var/tmp`、`/var/tmp` 的直接子目录；仍要求 `lampyris-imk-<UUID>`、
    绝对、规范化、无 `..`，拒绝真实数据目录与其它非临时路径。
  - 保留 ADR-129 的安全约束：先在 runner 自己的同 UUID 根构建并跑隔离探针，**签名前**重绑 `IMKTestRoot`，
    之后不在 runner 上执行接收方绑定包；产物额外带 `TARGET-ARCH.txt` 并由流水线用 `lipo`/PlistBuddy 复核。
- **理由**：A 机没有 Developer ID 证书，只能由 CI 出包；单靠 arm64 包无法在 Intel 机器上补验原生协议。
  将架构与目标根参数化后，同一套所有权/签名门禁可复用到任意接收设备。
- **取舍**：交叉构建的载荷只在声明的机器/系统上实测（本轮 x86_64 + macOS 13.7.8）；
  universal 仅做本机与流水线架构断言，不代表双架构都做过真机验收。
- **关联**：ADR-124/129/130/131、IT-01/IT-14、报告 100/102；工具 `packaging/macos/prepare-isolated-ci.py`、
  `.github/workflows/isolated-imk-notary.yml`、`platforms/macos/tests/isolated-imk.py`。

## ADR-217 HUD 的禁用判据只看显式测试开关

- **状态**：采纳（2026-10-20，报告 102 §9 实测发现状态提示从不显示）。
- **问题**：`StateHUDController.disabled` 原本是
  `LAMPYRIS_ACCEPTANCE_OUTPUT != nil || NSApp.activationPolicy() == .prohibited`，本意是「无头回归不要建浮层」。
  但 IME 宿主的 `Info.plist` 里 `LSBackgroundOnly = 1`，AppKit 对这类常驻后台进程返回的
  `activationPolicy` **恒为 `.prohibited`** —— 于是真实宿主也命中了「测试模式」，HUD 被整段跳过。
  现象：HUD 窗口从未创建（面板数量不增加，只有候选窗被改成 400×32 后隐藏），屏幕像素 0 变化；
  同配置的最小 `NSPanel` 对照可见，环境已排除。
- **决策**：禁用判据只认显式开关 `LAMPYRIS_ACCEPTANCE_OUTPUT`（离屏回归本来就设它），删除
  `activationPolicy == .prohibited` 这一条；并在代码注释里写明「IME 宿主恒为 `.prohibited`，不能当测试判据」。
- **理由**：`activationPolicy` 描述的是进程形态，不是测试意图；用它做旁路会在真实宿主上静默关闭功能。
- **取舍**：以后若需要「测宿主但不显示浮层」，用显式环境变量，不再借用窗口形态。
- **关联**：ADR-211（候选窗内联状态）、ADR-214（HUD 光标矩形）、报告 094/096/102、`platforms/macos/Sources/StateHUD.swift`。

## ADR-218 按键路径的内嵌计时钩子（仅测试启用）

- **状态**：采纳；**接线待验证**（2026-10-20，IT-12 需要「按键→候选」的真实耗时）。
- **问题**：IT-12 的门槛是「按键→候选 < 16 ms」（技术方案 §12），但此前的宿主级采样只能靠外部
  AX 轮询（p50 ≈ 217 ms，其中 osascript 发送就占 115 ms），是**上界**，不能用于门禁判断。
- **决策**：在宿主内加一个默认关闭的计时钩子 `PerfTrace`：
  - 开关：产品路径只认环境变量 `LAMPYRIS_PERF_TRACE`；**隔离测试入口恒定启用**，输出固定为私有根内
    `perf-trace.jsonl`——宿主常由系统/LaunchServices 启动，环境变量与标记文件都注入不可靠，只有「测试入口自己写死」
    能稳定拿到样本；
  - 记录内容：`engineUs`（引擎算完候选）、`totalUs`（到候选窗/预编辑更新完成）、`candidates`、`committed`，
    以及面板动作 `{panel, totalUs}`；**不记录任何输入内容**；
  - 未启用时只有一次环境读取后走 Bool 短路；文件以 0600 写入。
- **理由**：只有进程内计时能区分「引擎耗时」与「IMK 客户端回写耗时」；外部轮询无法回答 16 ms 门禁。
- **取舍 / 未决**：env 路径在一次手动测试中给出 3 个样本（total 18.7 / 22.8 / 9.5 ms，engine 0.11 / 0.31 / 1.73 ms）。
  标记路径已确认「宿主启动时读到了标记并启用计时」（`LAMPYRIS-PERF enabled` 日志），但**手工启动的宿主不接管
  客户端连接**，而反复 SIGTERM 之后 macOS 会停止按需启动宿主，两种方式都拿不到可重复的采样。
  矩阵探针的 `trace` 场景在拿不到样本时 BLOCK。重新登录后复测（2026-10-20 14:1x）：
  - 系统**没有**再按需拉起宿主（切换输入源后实例数为 0）；`launchctl setenv` 也到不了 `open` 启动的进程（env 计数 0）；
  - `open` 启动的宿主偶尔能接客（候选窗 497×70 出现过一次），随后又不接（同一会话内可复现失败）；
  - 结论：卡点是**宿主启动/接管时序 + 包签名**。可用组合（已实测两次）：**CI 公证隔离包** + 私有根
    `perf-trace.enabled`（内容=输出路径）+ 顺序「`open` 拉起 → 切一次输入源让客户端绑定 → 再发键」。
    ad-hoc 本地构建会被 Gatekeeper `CoreServicesUIAgent` 拦下（抢焦点、宿主不接客），不能用来采样。
  - 实测（公证包，n=45，两次运行）：total p50 14.1 / 14.9 ms，p95 20.6 / 23.5 ms，max 32.7 ms；engine p50 1.0 ms；
    面板 42 ms（设置）/ 165 ms（关于）。即**引擎远低于 16 ms 门槛，端到端 p95 超过**，瓶颈在 IMK 客户端回写与候选窗更新。
  - 采集入口：`platforms/macos/tests/run-installed-perf-trace.sh`（顺序脚本化：open → 切源 → 新文档 → 一轮按键探测
    候选窗 → 14 轮采样 → 面板 → 分位数）。该脚本带 3 轮重试，拿不到候选窗就失败退出，不写假样本。
  - 未决：**反复 SIGTERM 宿主的会话里，系统会停止按需拉起/接管**（实测：重新登录后两次成功采到 n=45；
    之后多轮 pkill 后即使走同一顺序也不再接客）。因此采样应在「新登录 + 少杀进程」的会话里做；
    矩阵探针的 `trace` 场景同样会因此 BLOCK（它只报 BLOCK，不给数字）。
- **关联**：技术方案 §12、IT-12、报告 102/103、`platforms/macos/Sources/PerfTrace.swift`、
  `platforms/macos/tests/isolated-imk/main.swift`、`run-installed-perf-matrix-probe.py`。


## ADR-219 验收探针离线回归与提交前检查点修复

- **状态**：采纳（2026-10-20，B 机验收前置）。
- **决策**：failure/INT/TERM 场景以唯一的提交按键行为锚点插入中断，不再依赖其前一行必须是输入源检查；保留新增焦点轮询与原有源、文本范围及恢复守卫。离线 mock 明确返回焦点角色，按完整行替换小数等待，并覆盖轮询失败时零发键、完整恢复。
- **理由**：`6ed5da1` 的焦点轮询插入后旧替换锚点失效；mock 不返回文本区角色，且前缀替换把 `sleep 0.25` 变为 `sleep 05`，使正式候选 CI 离线回归超时。不能通过放宽守卫或增加超时掩盖问题。
- **补充**：性能矩阵回归仍断言过期错误文案；改为检查实际缺失文件守卫、30 行最低样本门槛及当前错误文案，不改变采样门槛。沙箱外完整回归证明 tools private copy 项通过。
- **关联**：ADR-133/218、报告 104；仅恢复测试场景预期语义，不修改产品输入行为。


## ADR-220 性能探针逐动作自有窗口与输入源守卫

- **状态**：采纳（2026-10-20，B 机实测前置）。
- **决策**：性能探针的字符、提交、删除及设置/关于/简繁快捷键统一走 `owned_do`；仅增加固定白名单动作。原生发键前保留同次 AppleScript 的文档、前台、窗口与文本区身份检查；有隔离 helper/root 的调用同时核对当前精确输入源属于该隔离身份。焦点或输入源守卫失败立即终止，不吞错继续、也不以重试掩盖。宿主仍不可用时可记录有界启动失败，不向未知窗口发键。
- **理由**：现有性能脚本存在直接 System Events 发键及忽略 refocus 失败的路径，违反报告 104 的逐批保护边界，无法安全在 B 机执行。
- **关联**：ADR-133/218/219、报告 104。只修改探针与测试，不修改产品源码、候选身份、采样门槛；记录探针版本与候选提交分别绑定。
