## ADR-001 核心语言：Rust

- **状态**：✅ 冻结
- **决策**：引擎与业务逻辑用 Rust 实现。
- **理由**：内存安全（输入法是高权限组件）；单一核心跨平台复用；移动端可交叉编译；生态有 `cedarwood`/`windows`/`objc2`/`jni` 等所需设施。
- **关联**：`技术方案.md` §4

## ADR-002 许可证：GPL-3.0-or-later

- **状态**：✅ 冻结
- **决策**：整个项目采用 GPL-3.0-or-later。
- **理由**：① 防"劣币驱逐良币"——阻止他人闭源包装后反噬；② 开源桌面输入法主流许可（RIME 前端、Trime、msime 等），社区推广无门槛；③ 非商业项目，无需 Apache/MIT 的"企业可闭源"空间；④ 解锁 GPL/LGPL 资源（`libpinyin`、`rime-wubi`）。
- **配套**：名称/Logo 保留权利（README 声明）；贡献用 DCO。
- **关联**：`技术方案.md` §4、`数据来源与许可.md` §5

## ADR-004 架构：Rust 核心 + 窄 C ABI + 平台薄宿主

- **状态**：✅ 冻结
- **决策**：引擎为框架无关的 Rust 库，暴露纯 C ABI；各平台写薄宿主。
- **宿主**：macOS/iOS=Swift；Windows=Rust（`windows` crate 实现 TSF）；Linux=C++ Fcitx5 薄壳；Android=Kotlin+JNI。
- **理由**：`karukan`/`vnkey`/`pure-ime`/`inputx` 已验证该模式；`objc2` 无 IMK 绑定，Swift 是现实选择。
- **关联**：`技术方案.md` §5、§10

## ADR-006 输入形态：五笔优先 + 默认混合输入

- **状态**：✅ 冻结

## ADR-007 码表：自建（编码器 + 词组自动生成）

- **状态**：✅ 冻结

## ADR-008 拼音：trait 化可插拔，Phase 1 用内置轻量兜底

- **状态**：✅ 冻结（2026-10-08 复核后修订）
- **决策**：定义 `PinyinBackend` trait。**Phase 1 用内置轻量拼音兜底**（音节→高频字词表 + 简拼，数据几百 KB）保证混输与反查；`inputx-pinyin` 在 P1-M2 先做 spike，验证 API/质量/体积后再决定；终局自研；`librime` 仅备选。
- **理由**：不把"混输兜底"绑定到单一第三方引擎（bus factor 1、年轻、API 未验证）；保持全 Rust 构建与移动端交叉编译。
- **T-M2-04 spike 复核（2026-10-08，**终局决定**）**：评估 `inputx-pinyin` 1.4.0 后，**Phase 1 不接入，保留内置轻量兜底**；`inputx-pinyin` 降为 **P2「观察」候选**（可能作为可选后端接在 `PinyinBackend` 之后），**终局仍为自研 FSA**。依据：① **体积**——core `pinyin.dict` 4.2 MiB、默认含 bigram/trigram ≈ 22.8 MiB，远超 0.6 MB 预算（决定项）；② **质量**——20 常用词 hit@1 与内置兜底持平（各 19/20），仅超长整句占优；③ **维护**——单作者、crates.io 1.4.0 滞后、API 有变动；④ **API**——facade 不含简拼/权重，`inputx-core` 未发布，需自写适配层；许可干净（非否决项）。详见 `docs/reviews/002-inputx-pinyin-spike.md`。
- **关联**：`技术方案.md` §8、`docs/reviews/001.md` P1-2、`docs/reviews/002-inputx-pinyin-spike.md`、T-M2-04

## ADR-015 词典数据结构：cedarwood（弃用 yada）

- **状态**：✅ 冻结（2026-10-08，实现阶段发现）
- **决策**：码表底层用 **`cedarwood`**（BSD-2）双数组 Trie；**弃用 `yada`**。M0 先用排序数组验证逻辑，M1 换 `cedarwood`（预测搜索 + 动态增删 + 持久化）。
- **理由**：输入法需要"由前缀枚举所有候选"的预测搜索；`yada` 只有 `common_prefix_search`（语义相反），不支持；`cedarwood` 的 `common_prefix_predict` 正是所需，且支持动态增删（用户词库）与稳定二进制持久化。
- **关联**：`技术方案.md` §6.2、§4
- **后续**：M1 的 cedarwood 迁移始终未实施；ADR-060 将 cedarwood/二进制索引降级为带触发条件的可选优化，当前实现为**排序数组 + 文本 TSV**。本条作为历史保留。

## ADR-016 单字码来源：自建编码器为唯一发布来源，第三方码表仅作验证 oracle
- **状态**：✅ 冻结（2026-10-08）
- **背景**：T-M1-04 发现 `huanfeng/WindInput` 的 `wubi86_chaizi.txt`（MIT）**第 3 列直接给出已验证的五笔86 码**（27,823 字）。一度可省去 T-M1-03 编码器。
- **决策**：
  1. **发布用单字码表只能由本仓自建编码器（`crates/wubi-encoder`）生成**；**不直接发布**任何第三方码表。
  2. 第三方码表（WindInput 等）**仅作验证 oracle**（测试/CI 对照），**不进入发布产物**。
  3. 编码器须与 oracle **全量对照**并达到约定一致率；不一致逐条调查（编码器 bug / 数据错 / 规则边界），结论归档。
  4. 尽量用**多个独立 oracle**交叉，避免单一来源错误被当成真值。
- **理由（长期正确性）**：
  1. **独立性**：发布产物不依赖第三方数据的正确性与可获得性。
  2. **可审计**：每个码可由规则重现、可解释（项目核心卖点“开源可审计”）。
  3. **可扩展**：同一编码器框架支撑五笔98/新世纪/郑码；直接吃第三方码表是死路。
  4. **可验证**：自建 + 独立 oracle 对照才是真正的质检，能发现 oracle 自身的错。
  5. **许可干净**：第三方数据不出现在发布物中，许可风险最小。
- **与 ADR-007 的关系**：结论**不变且更强**——自建码表仍是路线；本 ADR 明确“第三方码表”的**唯一定位是验证**。
- **影响**：T-M1-03（合体字+识别码）**保留且是核心**；T-M1-04 重定位为“oracle 对照”；T-M1-05 生成自建码表并报告与 oracle 的一致率。
- **关联**：`技术方案.md` §7.1、`数据来源与许可.md`、ADR-007、ADR-014

## ADR-017 结构/末笔数据来源：暂从 D3 派生（option 2），可靠来源待引入

- **状态**：✅ 冻结（2026-10-08）
- **背景**：T-M1-03 需要每字的「末笔笔画 + 字型结构」以生成识别码；D3（oracle）不直接给出这两个字段。
- **决策**：
  1. 采用 **option 2（派生）**：从 D3 识别码位反推 (末笔, 结构)，生成自有派生数据集（MIT 允许派生）。
  2. 派生数据集仅作**临时输入**，不进入发布产物；可靠独立来源（Unicode IDS / CHISE 等）引入并登记后再替换。
  3. 识别码表本身（5×3 双射）是公开规范，由本库 `recognition_key` 硬编码实现，用规范样例（中/和/对/地/要/会）做独立单测校核，不依赖 D3。
- **理由**：
  1. 离线约束下无 IDS/CHISE 等独立来源可用；D2 拆字粒度与 D3 不一致且缺字，不能可靠提供字根数（T-M1-04 已提示）。
  2. D3 第 2 列实为「每码位字形」而非纯拆字，不给出字根数 → 无法可靠区分「2 字根+识别码」与「成字字根」等，故派生仅对三码字近似成立，标注 PROVISIONAL。
- **影响**：`data/generated/wubi86-structure-laststroke.tsv` 为 PROVISIONAL 派生数据；T-M1-05 生成自建码表前需引入可靠拆字数据（含结构/末笔），并做与 D3 的全量对照回归。
- **关联**：ADR-016、`数据来源与许可.md`、T-M1-03、T-M1-05

## ADR-018 结构/末笔独立数据源：调研结论——暂无 GPL-3 兼容来源

- **状态**：🔶 结论（T-M1-05a 调研；阻塞 T-M1-05）
- **背景**：T-M1-05a 要求引入**独立于 D3** 的「字型结构（左右/上下/杂合）」与「末笔笔画（横竖撇捺折）」数据，替换 ADR-017 的 PROVISIONAL 派生数据（其来自 D3 反推，属自证）。
- **调研结论（逐一核实许可）**：
  1. **末笔（笔画顺序）**：
     - `KanjiVG`（CC BY-SA 3.0，**GPL-3 兼容 ✓**）：笔画有序、方向可判，但只覆盖日本汉字，GB2312 一级仅 **2395/3755（63.8%）**，无法覆盖简体常用字。
     - `makemeahanzi` / `hanzi-writer-data`（源自 Arphic 字体）：**Arphic Public License**，FSF 官方列表明确判定 **incompatible with the GPL** → 与 GPL-3 冲突，禁止引入。
     - `cnchar` 等 npm 库：MIT 是**代码**许可，其笔画顺序数据仍源自 Arphic/makemeahanzi → 数据许可同样不合格。
  2. **结构（IDS）**：
     - `cjkvi/cjkvi-ids`：`ids.txt` 派生自 CHISE，"许可从其条款"（未明示）；其余文件 GPLv2（是否"or later"表述含混）→ 不满足"许可明确"。
     - `chise/ids`（CHISE IDS 数据库）：仓库**无 LICENSE/COPYING**；其软件 CL-CHISE 为 LGPLv2.1，但**数据**本身无明确许可声明 → 不满足"许可明确"。
- **决策**：
  1. **停止**：不引入上述任何来源，不生成"独立结构/末笔"数据；**不退回 D3**、不伪造数据。
  2. ADR-017 的 PROVISIONAL 派生数据**继续作为 T-M1-05 的临时输入**（明确标注，不进发布产物）。
  3. T-M1-05（单字码表生成）**继续阻塞**，直至找到合格来源。
- **理由**：铁律 4（数据合规）+ T-M1-05a 禁止项（不引入许可不明 / 与 GPL-3 冲突的数据；找不到合格来源即停止）。
- **下一步候选（待后续卡评估，按优先级）**：
  1. **末笔**：KanjiVG（CC BY-SA 3.0）先覆盖其 63.8% 常用字（可行性已确认：SVG 有序笔画可判末笔方向），缺口字再寻 CC0/MIT/CC-BY 的简体笔画来源（Wikimedia/Wiktionary、国内开放数据）。
  2. **结构**：评估 Wikimedia/Wiktionary（CC BY-SA）Han 字条目中的 IDS 分解（机器可读 dump 的覆盖与正确性待测）；或向 CHISE 申请明确许可。
  3. 若长期无解：按 ADR-016「多独立 oracle」原则，用**第二份独立 wubi 码表**交叉校验派生数据（仍是码表派生，非真正独立，需另立 ADR）。
- **关联**：ADR-016、ADR-017、`数据来源与许可.md` §1.3、T-M1-05a、T-M1-05

## ADR-019 验证策略：以「多 oracle 交叉验证」替代「数据独立」

- **状态**：✅ 冻结（2026-10-08）
- **背景**：ADR-016 要求发布码表自建、第三方仅作 oracle；ADR-017 的结构/末笔为 D3 派生（PROVISIONAL）；T-M1-05a/05b 调研证明：**不存在**「GPL-3 兼容 + 许可明确 + 体积可用」的独立 IDS/结构来源 → **“数据独立”在 Phase 1 不可达成**。
- **决策**：
  1. 保留自建编码器为发布码表生成器（ADR-016 不变）。
  2. 结构/末笔沿用 ADR-017 的 PROVISIONAL 派生数据（明确标注，**不进发布产物**）。
  3. **发布前必须与 ≥2 个来源独立、许可合规的码表 oracle 全量对照**：
     - Oracle #1：WindInput（MIT）
     - Oracle #2：`rime/rime-wubi`（LGPL-3；其表源自极点五笔，**仅作测试对照，绝不分发**）
     - 可选 #3：`ibus-table-chinese` wubi-jidian86（GPL-3，测试对照）
  4. 三方不一致 → **逐条按五笔86 规范人工裁定**，记录理由；**不得“向某个 oracle 拟合”**。
  5. oracle 一律不进入发布产物（ADR-016）。
  6. 将来若获得许可明确的独立结构/末笔数据，回到 ADR-017 的升级路径替换（本 ADR 不撤回）。
- **理由**：① 编码器已由规范样例独立校核、与 D3 一致 99.98%；② 剩余风险主要是“单一 oracle 自身错误”，多源交叉可检出；③ 测试用 oracle 不涉及分发，provenance 风险可控（既有文档已允许极点系数据作回归对照）。
- **关联**：ADR-016、ADR-017、ADR-018、T-M1-04b、T-M1-05

## ADR-020 单字码表生成：以 D3 拆字为字根来源 + 成字字根规则补全

- **状态**：✅ 冻结（2026-10-08）
- **背景**：T-M1-05 按任务卡对 D2 逐字编码，发现 D2 的字形记法歧义过大（GB1 一致率仅 ~92%，天花板约 94%），不满足 ≥99% 验收；同时发现 `encode_chengzi` 对 1/2 笔成字字根的实现不完整。
- **决策**：
  1. **发布码表（`wubi86-single.tsv`）仍由本仓编码器逐字生成**（ADR-016 不变），但**字根序列来源由 D2 改为 D3 第 2 列**（WindInput `wubi86_chaizi.txt`，MIT；“每码位一字形”的干净拆字表示）。
  2. **字根表（字形→键）为公开五笔86 规范**（CC0 事实性数据），在 D3 字形记法下由编码列多数表决推导；该推导使“vs D3”的一致率成为规则自洽检验，**真正的独立校验是 rime oracle（独立谱系）**（ADR-019 口径）。
  3. D2 降级为**交叉检查**（量化其字形记法歧义），不进入发布路径；识别码/结构/末笔仍为 D3 派生（PROVISIONAL，ADR-017/019）。
  4. **`encode_chengzi` 补全标准**：1 笔=键+首笔+LL、2 笔=键+首笔+次笔、≥3 笔=键+首笔+次笔+末笔（修正 T-M1-02 的简化，原实现把 2 笔成字字根错编为 4 键）。
- **理由**：① D2 的字形记法歧义已由 T-M1-04/ADR-017 预警，本次量化确认不可用；② D3 第 2 列与编码列逐位等长、字形无歧义，可稳定支撑生成；③ 用 D3 拆字仍非“直接发布第三方码表”——码仍由自建编码器规则生成，仅字根序列输入来自 MIT 拆字数据（与 D2 同类）。
- **影响**：`wubi86-single.tsv`（D1）由 `generate.rs` 从 D3 拆字生成；与 D3 一致 99.9784%（GB1 100%）、与 rime 一致 98.77%（GB1 100%），三方不一致 0 条；D2 交叉检查 GB1 91.66% 写入报告。
- **关联**：ADR-016、ADR-017、ADR-019、T-M1-02、T-M1-05

## ADR-021 词组码表：多候选（重码）模型 + jieba 词频

- **状态**：✅ 冻结（2026-10-08）
- **背景**：T-M1-06 用 D4 生成的词组表为**单候选去重**（`code\t词组`），且词表覆盖不足；T-M1-06b 改用 `fxsjy/jieba` `dict.txt`（D10，MIT，349,045 词**带词频**）重生成并赋权。但卡步骤 3 的「同码保留权重最高者」与验收样本冲突：如 `ltif` 下 `加德满都`（频次 66）会挤掉 `输入法`（频次 19）。
- **决策**：
  1. 词组码表格式改为 `code\t词组\tweight`，采用与单字码表一致的**多候选（重码）模型**（`技术方案.md` §6.2）：一个码保留全部候选，按 `weight` 降序；**不再单候选去重**。
  2. `weight` = jieba 词频（**真实词频**，ADR-013）；词表来源 D10（MIT）。
  3. 单字码表 `weight` 同样改为 jieba 词频（缺者默认 `1`）。
- **理由**：① §6.2 已确定「一个码映射多个候选」，单候选实现与架构不符；② T-M1-07 的「重码按词频降序」需要多候选；③ 避免验收样本（尤其 `输入法`）因碰撞被丢弃；④ 内置码表可在 T-M1-09 再按词频挑选 ~10k 高频词组（`技术方案.md` §7.2）。
- **影响**：`data/generated/wubi86-phrases.tsv` 由 38,220 条（单候选）变为 337,231 条（155,726 个码，5.8 MB）；`wubi86-single.tsv` 仅 `weight` 列变更。
- **关联**：ADR-013、ADR-016、`技术方案.md` §6.2/§7.2、T-M1-06、T-M1-06b、T-M1-07

## ADR-022 macOS 宿主集成：FFI 扩展 + 配置路径 + bundle 标识（T-M3-02）

- **状态**：✅ 冻结（2026-10-08）
- **背景**：T-M3-01 的 `ime-ffi` 会话只用内置样本引擎，且无平台配置路径、无预编辑串出口、无模式切换入口；缺少可装载的 macOS 宿主。T-M3-02 需要在不破坏 ABI 契约的前提下补齐。
- **决策**：
  1. **扩展 `ime-ffi` 会话 ABI**（仍 `catch_unwind`、不透明句柄、UTF-8、负数为错误）：
     - `ime_session_new_with_data(wubi, pinyin_chars, pinyin_words)`：从真实 TSV 加载；拼音词表可空（降级单音节）；失败返回 `NULL`。
     - `ime_session_buffer(session)`：返回**借用**的组合缓冲区（预编辑串）。
     - `ime_session_set_mode(session, mode)`：按 `mixed`/`wubi`/`pinyin` 切换。
     - `ime_session_key` 成功时改为返回按键结果 `IME_KEY_CONSUMED(0)` / `IME_KEY_COMMITTED(1)` / `IME_KEY_PASS_THROUGH(2)`；`0` 与旧 `IME_OK` 兼容。
  2. **配置 ABI 增加 `ime_config_init(path)`**：由宿主在任何配置调用前告知平台路径；仍是唯一文件真值，**不使用 `UserDefaults`/环境变量存配置**（`配置架构.md` R1）。
  3. **平台配置路径**：`~/Library/Application Support/萤火虫/config.toml`。
  4. **bundle 标识**：暂用 `org.yinghuo.inputmethod`，连接名 `Yinghuo_InputMethod_Connection`，控制器类 `YinghuoInputController`；最终包名取决于 TBD-4，改动仅涉及 `Info.plist` 与常量。
  5. **bundle 格式必须为 `.app`**（不是 `.inputmethod`）：本机实测 macOS 13 的 LaunchServices 无法扫描 `.inputmethod`（`lsregister -f` 报 `-10811`），且系统内所有输入法均为 `.app`。随附 `Contents/PkgInfo`（`APPL????`）、菜单图标（`tsInputMethodIconFileKey`）与 `*.lproj/InfoPlist.strings` 本地化显示名。
  6. **`Info.plist` 结构**：输入模式清单放 `ComponentInputModeDict`（`tsInputModeListKey` + `tsVisibleInputModeOrderedArrayKey`），键名参照本机实测的既有 IMK 输入法（系统输入法与 `SogouWBInput.app`）。
  7. **UI 约束**：候选窗为纯代码 `NSPanel`；**不使用 Interface Builder / Asset Catalog**（本机无 Xcode）。
  8. **安装时机**：macOS 只在**登录时**扫描输入法 bundle；更换 bundle 后必须**注销/重登**（实测 `killall TextInputMenuAgent` 无法可靠触发重扫）。
- **理由**：① 宿主无需自建业务逻辑即可完成「按键→候选→上屏」闭环；② `buffer`/`set_mode` 是预编辑与配置模式的必要出口，仍只做转换；③ 显式 `ime_config_init` 比 `setenv` 更可验证且不触碰 R1；④ 用系统实测的 `.app` 格式与键名，避免装载失败。
- **关联**：T-M3-01、T-M3-02、`技术方案.md` §5.3/§10、`配置架构.md` §9、`platforms/macos/README.md`

## ADR-023 macOS 注册标识修正：保留经典 IMK 宿主

- **状态**：✅ 冻结修正（2026-10-08）；系统装载验收待完成。
- **背景**：T-M3-02 的 bundle ID `org.yinghuo.inputmethod` 缺少 `.inputmethod.` 后的名称段；连接名 `Yinghuo_InputMethod_Connection` 未与 bundle ID 对齐。验证机日志反复出现 `Refusing connection name for bundle: unrecognized 'InputMethodConnectionName' value`，但 bundle ID 在日志中被隐去，尚不能把每条错误归因于萤火虫。
- **决策**：
  1. bundle ID 修正为 `org.yinghuo.inputmethod.Yinghuo`；模式 ID 为 `org.yinghuo.inputmethod.Yinghuo.default`；连接名统一为 `org.yinghuo.inputmethod.Yinghuo_Connection`，同步 plist、入口与本地化。

  3. 此修正不改变配置路径、引擎或 ABI；不引入 Sandbox 或任何新依赖。修正后的包须重新签名、公证并安装后验收，不能沿用旧包的票据。
- **理由/来源**：[IMK 示例作者](https://github.com/ensan-hcl/macOS_IMKitSample_2021)明确要求 bundle ID 包含 `.inputmethod.`；[IMKSwift 维护者](https://github.com/vChewing/IMKSwift)说明连接名采用 bundle ID + `_Connection`；[Apple IMK 文档](https://developer.apple.com/documentation/inputmethodkit)仍说明在 main 中创建 `IMKServer`。以上支持先修正注册元数据，不构成 macOS 27 实机装载已通过的证据。
- **关联**：修正 ADR-022 第 4 条；T-M3-02、SIG-2、TBD-4（英文名仍暂定）。

## ADR-033 同环境构建路径归一化

- **状态**：冻结（2026-10-08）
- **决策**：正式 macOS 构建将 Rust workspace 路径映射到 /yinghuo-src，锁定 registry/vendor 的每个依赖映射到 /yinghuo-dependencies/name-version；Swift 从仓库根以相对源码路径编译，使用 file-prefix-map 和 whole-module-optimization，将生产宿主合为单一编译单元，避免多个临时对象排序差异；链接器 oso_prefix 去除对象调试映射目录并启用 reproducible；正式链接去除 STABS/DWARF 调试映射（-S），保留正常 UUID 和符号，显式目标 macOS 13（与 plist 一致）。Cargo locked 构建，归档 SOURCE 携带提交标识，构建不要求 .git。
- **理由**：真实源码包离线重建发现，panic 源码位置包含本机 Cargo registry 路径，vendor 构建造成二进制差异；消除构建目录变化及个人绝对路径。同工具链/SDK/架构再比较载荷，签名和 ZIP 元数据仍不承诺跨环境一致。
- **边界**：不覆盖用户显式额外编译选项，构建说明要求复现相同选项；无运行时配置变化、无依赖新增。
- **关联**：ADR-032、P1-M5 可复现构建验证。

## ADR-035 多会话共享只读词表

- **状态**：冻结（2026-10-08）
- **决策**：码表及拼音后端由 Arc 持有，只读数据可跨会话共享；引擎选项、组合、分页、候选、用户词库仍由各自会话持有。FFI 数据加载缓存使用规范路径/长度/mtime 为键、Weak 为值，各类最多 4 个键，锁保护首次加载；文件变化重新加载，不保活已无会话的数据。
- **理由**：5 个真实数据会话内存约66MiB；IMK 每个客户端独立会话，重复载入违反常驻预算。共享不可变已登记资源不需要引擎执行 IO、不增加依赖或配置。
- **边界**：不视 mtime/长度为安全哈希；正式包完整性依赖签名与发布 SHA。开发替换文件必须改变 mtime/长度；并发使用期间修改文件不影响既有会话快照，新会话加载新版本。
- **关联**：ADR-030/031、Phase 1 多应用/常驻内存验收。

## ADR-036 宿主操作取消预编辑的边界

- **状态**：冻结（2026-10-09）
- **决策**：正式菜单切模式、词库操作及反查面板前，同步清除客户端 marked text、会话组合与候选窗；模式保存失败则提示并保留当前模式/组合。失焦或显式复位重置成对引号状态，保持模式和临时中英/全半角偏好。
- **理由**：此前菜单只取消 Rust 组合或隐藏候选，客户端预编辑可能残留；成对引号状态也不应跨输入上下文延续。普通选字/取消组合不重置引号，避免一句内的闭引号失效。
- **关联**：ADR-028/034、P1-M4 失焦无残留验收；配置仍仅由 ime-config 持久化。

## ADR-037 长候选的屏幕边界

- **状态**：冻结（2026-10-09）
- **决策**：默认候选横排，超过当前屏幕可见宽度时自动竖排；单条超长词在可见宽度内截断并提供完整 tooltip，数字索引/选字文本不变。几何计算可注入可见区域供本地边界验证，实际 show 仍使用当前 NSScreen。
- **理由**：只限制候选窗原点无法处理窗体本身宽于屏幕的用户词条；保证面板自身留在可见区域，不增加排版偏好或皮肤配置。
- **关联**：ADR-026/029、P1-M4 候选不错位验收。

## ADR-038 用户候选有界查询与频次缓存

- **状态**：冻结（2026-10-09）
- **决策**：用户词库查询先按来源/精确命中/频次/文本选出最多256个借用条目，再分配候选；与现有每引擎256条的前缀查询一致，继续输入缩小范围即可找到更具体词条。核心排序对每个候选只求一次用户频次，不在比较器中反复分配查询键。
- **理由**：接近2MiB/10000条合成词库、五会话实测稳态40.30MiB，最大按键19.434ms；复制全部匹配并重复查频次违反预算。保持五笔优先与精确候选优先规则。
- **关联**：ADR-025/029/030/035、最大用户词库发布预检；词库文件容量不变。

## ADR-039 用户词库共享不可变快照

- **状态**：冻结（2026-10-09）
- **决策**：同进程同文件用户词库使用 Arc<Entries> 只读快照，各 Store 的路径/错误及刷新状态独立；写入在已有文件锁下复制当前快照并原子替换，发布新快照。Weak 缓存最多4组，键包含规范路径、mtime、长度与 Unix inode/device，避免等长原子替换漏刷新。导出读取当前文件快照，不导出过时会话副本。FFI 失焦释放用户词库快照；正式宿主激活时预加载，避免失焦会话长久保留旧版词库。
- **理由**：有界查询后最大词库五会话仍36.67MiB，重复快照违反预算；复用不可变数据，不降低解析/容量限制或持久化规则。无配置或网络新增。
- **关联**：ADR-029/035/038；快照是词条数据而非偏好配置。其他平台文件身份策略可在对应宿主阶段补充。

## ADR-040 / 激活时预热候选窗口 / 已采纳

- **决策**：候选窗口复用现有标签，首次输入法激活时创建窗口并在隐藏状态预热中文字体和布局，随后清空候选。预览使用相同窗口初始化逻辑。
- **理由**：真实 AppKit 预检首次窗口/字体初始化约34–96ms，连续更新反复创建标签造成堆分配和碎片；将初始化移到激活阶段，缩短首键路径，不生成输入或学习记录。
- **关联**：Phase 1 性能 DoD、`docs/reviews/003-macos-performance.md`；预热耗时单独报告，正式 IMK 验收仍待完成。

## ADR-041 / 拼音索引共享文本 / 已采纳

- **决策**：内置拼音后端的单字反查索引以 Arc<str> 共享相同音节，解析阶段局部驻留，加载完成后释放驻留表；全拼、简拼与词反查索引共享同一个不可变词文本。查询返回值及公开接口继续使用 String。
- **理由**：大量汉字共享少量音节，逐字持有独立字符串造成重复分配；共享不可变音节降低常驻内存，不改变多音字首选读音规则。
- **关联**：Phase 1 内存预算、`docs/reviews/003-macos-performance.md`；不增加依赖或全局缓存。

## ADR-042 / 候选标签固定层级实验 / 未采纳

- **决策**：保留实验源码/补丁，产品继续使用 ADR-040 标签复用实现。修正持续输入探针的释放池范围后重新判断内存增长。
- **理由**：固定视图层级实验未消除同步探针的增长曲线（22000键约36.7MiB），没有足够证据支持产品改动；探针窗口隐藏和主循环回调位于释放池外，存在测试失真。
- **关联**：`docs/reviews/003-macos-performance.md`；实验保存在 `/private/tmp/yinghuo-stable-views-experiment.*`。

## ADR-043 / GitHub Actions 自动验收出包 / 已采纳

- **决策**：普通 PR CI 上传无凭据审核包；独立 macOS 验收工作流在 main 推送或手动触发时，先验证/构建，再以 GitHub Secrets 中的 Developer ID p12 与 App Store Connect 团队 API p8 签名、公证、staple，生成源码/SBOM/许可/SHA 验收附件。不创建公开 Release。
- **理由**：用户指定放弃 App 专用密码，凭据一次配置用于后续自动出包；临时 runner 钥匙串及私钥文件仅在签名阶段存在并 always 清理。不在 PR/fork 代码上使用签名凭据，产物上传路径只含 ZIP/SHA，不含密钥目录。
- **关联**：ADR-032、T-M3-03、`packaging/macos/CI-ACCEPTANCE.md`；证书到期/密钥撤销仍需维护，不承诺永久有效。

## ADR-044 / 复用组织签名凭据 / 已采纳

- **决策**：macOS 出包工作流引用 EasyIndie 的 APPLE_CERTIFICATE_P12_BASE64、APPLE_CERTIFICATE_P12_PASSWORD、APPLE_ASC_API_KEY、APPLE_ASC_API_KEY_ID、APPLE_ASC_ISSUER_ID，映射到脚本参数；API 私钥接受完整 PEM 或 Base64，保留原 Base64 参数兼容性。
- **理由**：用户已在组织配置共享凭据，避免各仓库重复维护；不读取或输出 Secret，权限仍限 main 签名步骤。
- **关联**：ADR-043、packaging/macos/CI-ACCEPTANCE.md；实际签名公证需首次 CI 验证。

## ADR-045 / CI 临时钥匙串搜索与指纹签名 / 已采纳

- **决策**：临时钥匙串加入当前用户搜索列表，保留原列表并在退出时恢复；从该钥匙串的有效签名身份中按完整名称精确选取唯一 SHA-1 指纹，codesign 使用指纹和显式钥匙串。
- **理由**：运行37876973106证实同名身份有效，但codesign按名称仍找不到，须消除搜索路径和名称解析差异；指纹仅用于定位证书，不是文件完整性摘要。
- **关联**：ADR-043/044；清理测试覆盖搜索列表恢复与无有效身份拒绝，日志不包含私钥。

## ADR-046 / 回车提交原始组合码 / 已采纳

- **决策**：组合态 Return/Enter 提交原始编码并清空组合，不选择或学习候选；空格/数字键保持选字。非组合态回车透传。核心负责统一语义，正式和预览宿主一致。
- **理由**：用户验收发现字母无法单独上屏；显式回车保留英文输入，避免强制中文转换。

## ADR-047 / IMK 组合结束及失焦清理 / 已采纳

- **决策**：实现 commitComposition/hidePalettes 清理候选和组合；记录当前文本客户端，deactivate 使用原客户端清预编辑。监听该客户端应用失活通知作为跨应用清理兜底，不记录输入或应用历史。

## ADR-055 macOS 13 ad-hoc 本地验收与全架构候选

- **状态**：冻结（2026-10-09）
- **背景**：ADR-032 依据 macOS 26/27 机器上“非 Apple 签名不被枚举”的实测，宣布 Phase 1 不签名前提被推翻；但那次实测时 bundle ID 仍是错误的 `org.yinghuo.inputmethod`（ADR-023 之前），**签名与注册元数据两个变量被混在一起**。
- **决策**：
  1. **本地开发/本机验收可用 ad-hoc**：在 macOS 13.7.8（Intel、`security find-identity` 为 0）上，ad-hoc 签名 + 正确 bundle ID `org.yinghuo.inputmethod.Yinghuo` 的 `.app` 被 TIS 正常枚举（`enabled=true`、`selectCapable=true`、共 284 源），用户实体输入 `wq→你`、`nihao→你好` 通过。**macOS 13 不要求公证**；日常迭代与阶段性真机验收不再依赖签名机。
  2. **分发与 macOS 26+ 仍按 ADR-032**：对外分发必须 Developer ID + hardened runtime + 公证 + stapler；macOS 26/27 更严的签名要求维持实机结论，不因本条而削减。
  3. **全架构候选（universal）**：`build.sh --universal` 同时为 arm64 与 x86_64 构建 staticlib 和 Swift 宿主并 `lipo` 合成；`prepare.sh` 依可执行文件的 `lipo -archs` 标注 `universal`/`arm64`/`x86_64`；CI 安装两个 rustup target 并出 universal 候选；`run-repro.sh` 以 `--universal` 重建并逐字节校验（本轮本机实测通过）。
- **理由**：ADR-023 的注册标识修正是 macOS 13 可见性的充分条件；签名/公证面向分发与新版系统，不应作为本地迭代门槛。单包同时覆盖 Apple Silicon 与 Intel，避免维护两份候选，也让 Intel 本机能直接安装 CI 产物。
- **链接注意**：`-whole-module-optimization` 下**不能**用 `-L … -lime_ffi`（链接器会选到 `libime_ffi.dylib`，把绝对构建路径写进 `LC_LOAD_DYLIB`，破坏可分发与可复现）；必须用 `-Xlinker <lib.a>` 强制静态归档。
- **关联**：ADR-023/024/032/033、SIG-1/SIG-2、T-M3-03、P1-M5；`platforms/macos/README.md`、`packaging/macos/CI-ACCEPTANCE.md`。

## ADR-056 英文/包名定为 Lampyris（关闭 TBD-4）

- **状态**：冻结（2026-10-09）
- **背景**：ADR-003 定了中文名「萤火虫」，英文/包名在 `yinghuo` / `lampyris` 间一直未决（TBD-4），代码里暂用 `org.yinghuo.inputmethod.Yinghuo`。`yinghuo` 是拼音，非中文用户难以拼读、记忆与检索，不利于产品面向国际；`org.yinghuo.*` 也是一个无所有权的机构段。
- **决策**：
  1. **英文/包名 = `Lampyris`**；中文名保持「萤火虫」。
     - **读法**：/læmˈpɪərɪs/，近似 “lam-PEER-iss”，重音在第二音节（学术拉丁语中 y 读 /ɪ/，也有人读 /læmˈpaɪrɪs/）。
     - **词源**：希腊语 λαμπυρίς（“发光的虫、萤火虫”），源自 λάμπω（“发光、照耀”）。
     - **含义**：萤科（Lampyridae）下的一个属，模式种 *Lampyris noctiluca* 即欧洲常见萤火虫；直接表达“自带微光”，契合“默认离线、不依赖云端”的产品寓意。
  2. **bundle 标识**：采用自有域名 `jokerhub.cn` 的反向 DNS `cn.jokerhub`：bundle ID `cn.jokerhub.inputmethod.Lampyris`，模式 ID `cn.jokerhub.inputmethod.Lampyris.default`，连接名 `cn.jokerhub.inputmethod.Lampyris_Connection`（保留 ADR-023 的 `.inputmethod.` 规则）；调试窗口 `cn.jokerhub.lampyris.debugpreview`。
  3. **改名范围**：可执行/App `Lampyris.app`、控制器类 `LampyrisInputController`、bundle 资源 `Lampyris.icns` / `LampyrisTemplate.png`、安装/卸载校验与路径、发布物与 CI 附件名 `Lampyris-*`、SBOM 组件名、用户词库默认导出名、备份目录，以及 ASCII 化的应用支持目录 `~/Library/Application Support/Lampyris/`。
  4. **不改**：中文代码/文档注释中的「萤火虫」；`assets/icons/yinghuo-*` 设计稿文件名（历史资产）；历史记录（`docs/experiments/**`、`docs/archive/**`、`docs/tasks/T-M3-02.md`、`docs/reviews/003|005`）。ADR-022 §4、ADR-023、ADR-032、ADR-033、ADR-050、ADR-055 中的旧标识作为历史保留，本条取代其中的“当前标识”。
- **理由**：仓库 private、无公开 Release、仅本机一个 ad-hoc 安装 + 一个 CI 公证候选，改名成本最低；发布后再改等于更换系统输入源身份、需用户重装重加。自有域名做反向 DNS 比无所有权的 `org.yinghuo` 更规范可持续。

- **关联**：ADR-003（关闭 TBD-4）、ADR-023（标识规则）、ADR-032/033/050/055；`技术方案.md` §2.1、`配置架构.md`、`platforms/macos/README.md`。

## ADR-057 候选窗显示候选来源（混输可解释性）

- **状态**：冻结（2026-10-09）
- **背景**：`技术方案.md` §2.2 要求混输时「五笔候选在前（标注“五笔”），拼音候选在后（标注“拼”）」，候选携带 `source` 贯穿排序与词频记账。`ime-core` 与 `ime-ffi` 已实现 `CandidateSource` → `IME_SOURCE_*`（0=码表、1=拼音、2=词组）并随 `ImeCandidate.source` 暴露；但 Swift 宿主 `ImeCandidate` 只保留 `text`/`code`/`isPrefix`，候选窗只收 `[String]`，混输时用户无法区分来源（报告 006 MVP-02）。
- **决策**：
  1. **FFI 契约不变**：沿用既有 `ImeCandidate.source`，不新增 ABI、不改顺序/去重/学习归属（仍由 `ime-core` 依 `source` 处理）。
  2. **来源贯穿到窗口**：Swift `ImeCandidate` 增加 `source`（映射 `IME_SOURCE_*`）；`CandidateWindow` 在候选文本后用 `NSAttributedString` 追加小号次要色中文标签：码表→「五笔」、拼音→「拼」、词组→「词」。
  3. **显示规则**：仅当**当前页**候选来源 ≥2 种时显示标签（这正是混输需要区分的场景）；单一来源页不显示，模式本身不改变此规则，避免常态噪声。
  4. **布局**：标签 11pt 次要色、与正文同基线，沿用既有超宽竖排/屏幕约束逻辑，不新增弹层或改变命中区域。
- **理由**：来源是混输可解释性的关键（五笔优先、拼音兜底），但只在真正混合时才有区分价值；FFI 已有字段，改动集中在宿主侧，小且可独立验证（独立窗口可自测）。
- **关联**：`技术方案.md` §2.2；报告 006 MVP-02；ADR-022/023/024；`platforms/macos/Sources/{ImeSession,CandidateWindow,InputController}.swift`、`platforms/macos/Preview/main.swift`。

## ADR-058 配置变更无按键即时刷新

- **状态**：冻结（2026-10-09）
- **背景**：`配置架构.md` §11.1 要求“改 `config.toml` 保存后，正在输入的候选窗立即按新设置变化，无需重启”；`ime-config`（快照 + 原子写 + `subscribe`）与 `ime-ffi`（`ime_config_subscribe`）已具备通知能力，文件监视也会触发 `reload` 并只广播**变化**的键。但 Swift 宿主只在每个按键的 `handle` 里读 `mode`/`candidate.count`，候选窗的 0.2s 计时器只刷新主题；外部改 `candidate.count`/`mode` 时，显示中的候选不会主动重新分页/取消，只能等下一次按键才生效（报告 006 MVP-03）。
- **决策**：
  1. 宿主新增全进程单例 `ConfigWatcher`：在首个所有者注册时经 `ime_config_subscribe` **只订阅一次**；回调可能在 `ime-config` 文件监视线程上触发，**绝不直接触碰 AppKit**，一律 `DispatchQueue.main.async` 派发到主线程。
  2. 当前所有者（`LampyrisInputController`）在 `activateServer` 注册处理器、`deactivateServer` **按身份解绑**（多控制器互不误清）；不重复订阅、不泄漏。
  3. 主线程收到通知后即时应用：`session.prepare()` 重套引擎选项；`candidate.count` 变更 → `set_page_size` 并重画当前候选；`mode` 变更 → `set_mode`（取消组合、清预编辑、隐候选窗）。主题仍由窗口计时器与显式刷新覆盖。
  4. 保留按键路径的读取作为幂等兜底（订阅失败也不影响输入）。
- **理由**：符合配置架构 §4/§11「唯一真值 + 即时生效」，把配置变化从「下一按键」提前到「保存即生效」，且订阅仅发生一次，避免重复/泄漏。
- **关联**：`配置架构.md` §4/§11、报告 006 MVP-03、ADR-008/009、Skill `add-config-option`；`platforms/macos/Sources/{Config,InputController,CandidateWindow}.swift`、`Preview/main.swift`。

## ADR-059 配置错误反馈（保留有效快照 + 可读错误）

- **状态**：冻结（2026-10-09）
- **背景**：`配置架构.md` §11.5 要求“写坏语法 → 输入法照常工作（用上一份快照）并提示错误行”。现状：`ime-config` 的 `reload()` 确实保留旧快照，但 `FileWatcher` 的 `let _ =` 把错误丢弃；`ime-ffi` 首启 `ConfigStore::load` 失败时静默降级为 `with_defaults`；Swift `main` 忽略 `ime_config_init` 结果，宿主对错误毫无可见性（报告 006 MVP-04）。
- **决策**：
  1. `ime-config` 的 `ConfigStore` 记录最近一次加载/重载失败原因（`last_error()`，含行号）；新增 `load_or_defaults()` 在**首启坏文件**时降级为默认值并保留错误。
  2. `reload` 在错误状态**发生变化**时广播哨兵键 `CONFIG_ERROR_KEY = "*error"`（不与 Schema 键冲突），修复后同样广播以清除；状态未变不重复广播。
  3. `ime-ffi` 暴露 `ime_config_last_error()`（UTF-8，空串=无错误，借用指针），首启改用 `load_or_defaults`。
  4. 宿主：`ImeConfig.errorMessage()`；控制器在激活与配置变更时检查，同一错误**只弹一次** `NSAlert` 并 `NSLog`，修复后自动复位（`lastAlertedConfigError`）；输入菜单常驻一条「配置错误：…」条目。
  5. **不引入第二配置**：错误只读，绝不自动改写/删除用户文件；错误提示不影响输入（沿用上一份快照）。
- **理由**：同时满足“照常工作 + 提示错误行”与“宿主可见且不反复弹窗”；错误经既有订阅通道即时到达，无需新增轮询。
- **关联**：`配置架构.md` §7/§11.5、报告 006 MVP-04、ADR-058、Skill `add-config-option`；`crates/ime-config/src/{lib,watch}.rs`、`crates/ime-ffi/src/config.rs`、`platforms/macos/Sources/{Config,InputController}.swift`、`Preview/main.swift`。

## ADR-060 词典数据结构：文本 TSV 真值 + 排序数组（cedarwood 降级为可选优化）

- **状态**：冻结（2026-10-09）
- **背景**：ADR-015 冻结 `cedarwood` 双数组 Trie，并计划「M0 排序数组验证、M1 换 cedarwood」；`技术方案.md` §4/§6.2/§11 也按 cedarwood/`.imedict`/mmap 描述。但事实上 M1 从未迁移：**仓库任何 `Cargo.toml` 都没有 cedarwood**，`ime-table` 一直是排序 `Vec`，`ime-dict` 只实现了用户词库（ADR-029 有界 TSV），没有 `.imedict` 编译器/mmap 装载器。实测规模：`wubi86-core.tsv` 491,854 B / 37,828 行 / 30,384 个码；`pinyin-chars.tsv` 575,473 B；`pinyin-core.tsv` 262,131 B（8.4MB 全量词表**不默认装载**，ADR-031）；按键→候选 P95 在预算内、常驻约 18.5 MiB（≤ 30 MB）。即：文档与事实不一致，且现有方案已满足 DoD。
- **决策**：
  1. **源数据格式 = 纯文本 TSV**（`code\ttext\tweight`）为唯一可审计真值；**不引入二进制 `.imedict`** 作为 Phase 1 交付物。
  2. **系统码表内存索引 = 排序数组**（精确二分 + 同前缀连续区间）——保留为当前实现。
  3. **用户词库 = 有界 TSV v1**（ADR-029，`ime-dict`），与系统表分离、查询期合并；不在 DAT 上做动态增删。
  4. **cedarwood / 编译期二进制索引 + mmap 降级为“带触发条件的可选优化”（P2+）**，不再是 Phase 1 交付项。
  5. **迁移触发条件**（任一满足才立项评估）：① 单表码数/条目数超过实现卡约定阈值；② 按键→候选 P95 连续 >16 ms 或长尾 >50 ms 且定位到码表扫描；③ 常驻内存逼近 30 MB；④ 需要默认装载远大于当前规模的数据。若采用，强制：**TSV→二进制可复现编译 + 提交 SHA-256 + 仓库内校验器**（二进制只能是可验证派生物）。
  6. **立即修正实现债**（单独卡片）：`CodeTableEngine::convert` 目前为统一支持 `z` 通配而**全表线性扫描**；改为 `exact`（二分）+ 前缀区间扫描，`z` 通配走受控分支。这是小改动、不改行为、可回归。
  7. **文档追认**：更新 `技术方案.md` §4/§6.2/§7/§11、`ROADMAP.md`、`T-M1-09` 等，使其反映已交付事实，不再宣称 `.imedict`/mmap 已交付。
- **理由**：项目价值在“更小、更干净、可被第三方验证”；文本真值 + 显式排序键比不透明二进制更符合长期可审计性。当前规模无性能压力，过早引入 DAT 只增依赖与验证负担。**cedarwood 的价值是规模/内存，不是正确性**，故以可测触发条件而非“计划必然”来管理。
- **关联**：ADR-013/014/015/021/029/031、报告 006 MVP-01/12；`crates/ime-table`、`crates/ime-dict`、`技术方案.md` §4/§6.2/§7.2/§11。

## ADR-061 解析器 fuzz：有界目标 + 确定性边界语料（dev-only）

- **状态**：冻结（2026-10-09）
- **背景**：`AGENTS.md` 安全工程铁律要求“解析器要有 fuzz 目标”；`Makefile` 已有 `make fuzz`（`dict_parser`）但仓库无 `fuzz/` 目录，目标不可运行（报告 006 MVP-06）。解析器是**唯一不可信输入入口**：用户词库 TSV（`ime-dict::parse`）、系统码表 TSV（`ime_table::Table::from_tsv`）、拼音 TSV（`ime_pinyin::TablePinyinBackend::from_tsv`）。
- **决策**：
  1. 建立独立 `fuzz/`（cargo-fuzz）crate `lampyris-fuzz`，**属于独立 workspace、不属于主 workspace**，不参与 `make verify`、不入发布产物；新增三个目标：`dict_parser`（兼容现有 Makefile）、`table_parser`、`pinyin_parser`。
  2. **有界**：每个目标先对输入长度设上限（256 KiB）再调用解析器，避免 fuzz 输入诱导无界分配；用户词库解析本身已有 2 MiB / 10k 条上限。
  3. 在主 workspace 加**确定性边界语料单测**（截断行、缺列、多余列、CRLF、BOM、NUL、非 BMP、超范围数字、空字段、超长行），作为 `make verify` 每次都跑的“短时验证”，**不依赖 nightly**。
  4. `libfuzzer-sys` 等仅作为 `fuzz/` 的 dev 依赖（MIT/Apache-2.0），不受主 `deny.toml` 约束（不入发布依赖树）。
  5. `make fuzz` 依次运行三个目标，默认限时（`FUZZ_SECONDS`，可用 `make fuzz FUZZ_SECONDS=120` 调整）。
- **理由**：fuzz 是“不可信输入”的持续保障，但 nightly 工具链不应进入主构建；把确定性边界语料放进常规测试，等于每次 CI 都做一次有界 fuzz，重活留给 `make fuzz`。
- **关联**：AGENTS 铁律、报告 006 MVP-06、ADR-029（用户 TSV v1）；`crates/ime-dict`、`crates/ime-table`、`crates/ime-pinyin`、`fuzz/`。

## ADR-062 组合缓冲区有界（超限忽略后续字母）

- **状态**：冻结（2026-10-09）
- **背景**：报告 006 MVP-07 指出 `ime-core::Session` 的组合缓冲区**无长度上限**（`handle_key` 对 `'a'..='z'` 只 `push`），且 `recompute` 不读 `Engine::max_code_length()`。在真实数据上用 `cargo run --release -p ime-cli --example compose_bound`（新增复现基准）实测，单键/累计耗时随长度**超线性**增长：

  | 模式串 | 64 | 256 | 1024 |
  |---|---|---|---|
  | `a`（累计 ms / 最慢单键 ms） | 5.7 / 0.46 | 317 / 4.58 | **16712 / 69.95** |
  | `nihao` | 1.6 / 0.34 | 48.7 / 2.95 | 1945 / 13.56 |
  | `zhongguo` | 0.6 / 0.11 | 10.2 / 0.19 | 402 / 4.78 |

  即：粘贴/长按产生千级字母串时会瞬时冻结（单键 70ms、整段 16.7s），违反 DoD “按键 < 16ms”。约束：五笔码 ≤4、拼音引擎按 **32** 码设计、用户词库编码 ≤ **64**（ADR-029）。
- **决策**：
  1. **组合缓冲区硬上限 `MAX_COMPOSE_LEN = 64`**：达到上限后，后续 `a..z` 字母键**被忽略**（返回 `Consumed`）——不硬截断已输入内容、不误上屏、不透传插入。上限 64 覆盖所有引擎的合法码长（含用户编码 64），不损害任何正常输入。
  2. **引擎门控**：`recompute` 跳过 `max_code_length() < buffer.len()` 的引擎（五笔 4 / 拼音 32），避免对不可能匹配的长码做无用功。
  3. 非字母键（退格/Esc/空格/回车/数字/翻页）在上限处**仍正常**，可回退、取消、上屏。
- **理由**：既钉住 DoD 时间/内存上界，又保持“不回改已输内容”的直觉行为；64 是三个引擎合法码长的并集上界，没有任何合法码长会被截断。
- **复现**：`cargo run --release -p ime-cli --example compose_bound -- data/generated 256,512,1024`。
- **关联**：报告 006 MVP-07、ADR-029、`技术方案.md` §12 DoD；`crates/ime-core`、`crates/ime-cli/examples/compose_bound.rs`。

## ADR-063 正式数据加载失败可诊断（不把样本兜底当正常）

- **状态**：冻结（2026-10-09）
- **背景**：严格打包会阻止缺失文件，但**正式宿主**在资源缺失/损坏时仍静默回退内置样本引擎，只 `NSLog` 一句（报告 006 MVP-09）；用户面对的是一个“只能打几个演示字”的输入法，却得不到任何可见解释。
- **决策**：
  1. `makeSession()` 区分**真实数据加载成功**与**降级**，并记录可读原因：资源目录缺失 / 缺码表 / 码表解析失败 / 缺拼音字表（拼音兜底不可用）。
  2. 一旦降级，宿主**可见**：输入菜单常驻「数据文件错误：…」条目 + **同一错误只弹一次** `NSAlert`（沿用 ADR-059 的去重模式）+ `NSLog`。
  3. 内置样本引擎**仅作为不崩溃的安全网**，绝不当作正常发布功能；提示文案明确“请重新安装完整包”，恢复步骤见 `docs/故障恢复.md` §4。
  4. 独立调试窗口（ADR-024）仍从参数加载真实数据、**失败即退出**（不样本兜底），保持不变。
- **理由**：与配置错误一致，“出错要看得见且不反复弹”；样本兜底保命但不掩盖安装损坏。
- **关联**：报告 006 MVP-09、ADR-059（错误提示模式）、ADR-024；`platforms/macos/Sources/InputController.swift`、`Preview/main.swift`、`docs/故障恢复.md`。
