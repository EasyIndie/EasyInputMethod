## 1. 范围

本标准规定：

1. **五笔86 的字根集合与键位**（规范性数据 `roots`）；
2. **逐字拆字（字根序列）与全码的对应关系**（规范性数据 `chars`）；
3. **一/二/三级简码槽位**（规范性数据 `shortcodes`）；
4. **识别码（末笔 × 结构）的判定**；
5. **一致性等级与判定程序**，使第三方实现可自测。

**适用范围**：五笔86（`wubi86`），字符范围以发布的数据包声明为准（1.0 版为 **GB2312-1980 一级 3,755 字**，
另含学习字表并集的 5,021 字，见 §9.2）。**不适用**于五笔98 / 新世纪 / 郑码 / 仓颉（不同方案的根序不可互推，ADR-380）。

## 3. 术语

- **字根（root）**：取码单位，必须出现在 `roots` 数据中；同一字形允许挂多个键（同形多键，如 `𠂇` 在 D/H）。
- **根序（decomposition）**：把某字按取码顺序排列的字根序列。
- **全码（code）**：该字在五笔86 键盘输入下的完整码（3 或 4 位小写字母）。
- **识别码（recognition code）**：字根不足四码时补的末位字母，由「末笔 × 结构」唯一确定。
- **简码槽位**：一级（1 位）/ 二级（2 位）/ 三级（3 位）。
- **标准字根清单**：`roots` 数据里 `kind = standard | key-roots | variant` 的全部条目。

## 4. 数据模型（规范性）

一个实现要声明一致性，必须能提供三张表（字段见 `schema/*.schema.json`）：

| 表 | 键 | 必填字段 |
|---|---|---|
| `roots` | 字根字形 | `glyph`, `key`, `kind` |
| `chars` | 字 | `char`, `code`, `roots[]`, `class`, `recognition{key,stroke,structure}?`, `quality`, `evidence` |
| `errata` | 码表勘误 | `char`, `erroneous`, `corrected`, `family`, `evidence`（可选层，见 §10.1） |
| `shortcodes` | 字 | `char`, `level(1/2/3)`, `code` |

- `keys` 列是**导出信息**（由 `roots` 表推得），判定时不采信实现方提供的 `keys`（防自证）。
- `roots[]` 是**取码字根序列**（按码位），不是字面结构拆分（见 `docs/standards/wubi-decomposition.md` §2 第 6 条）。
- `class ∈ {compound, radical-char, radical-char-exception, key-name}`：合体字 / 成字字根 / 官方特例的成字字根 / 键名字。
  只有 `compound` 走 R2/R3 的逐位规则；其余三类走 R8/R9（见 §5）。
- `quality ∈ {full, partial, unknown}`：`full` 必须通过 §5 全部规则；`partial` 必须写明 `reasons[]`；`unknown` 不得给根序。
- 私有区字形（PUA）**不得**出现在任何表中。

## 5. 规则（规范性，MUST）

对 `chars` 中每个 `quality = full` 的条目：

1. **R1 字根合法**：`roots` 的每个字形 MUST 出现在 `roots` 表中。
2. **R2 键位一致**：第 i 个根的字形在该表允许的键位 MUST 等于 `code[i]`（i 从 0 起）。
   **多键位字根（R2-note）**：`roots` 表里有 7 个字形挂了两个键（`⺋` B/N、`凵` B/M、`丆` D/G、`𠂇` D/H、
   `丷` I/U、`儿` I/Q、`𠂉` R/T），**静态字根表不足以判定某个字里该用哪个键**；此时以 `chars` 的
   `keys` 列为准（1.0 数据里 755 个字含这类字根）。实现方 MUST NOT 自行按"常见键"猜；拿不到逐字键位时
   该字 MUST 标 `partial`（ADR-388）。
3. **R3 长度一致**：若无识别码，根数 MUST 等于 `code` 长度；若有识别码，根数 MUST 等于 `code` 长度 − 1。
4. **R4 识别码一致**：`recognition.key` MUST 等于 `code` 末位；`(stroke, structure)` MUST 由 §6 的网格唯一推出该字母。
5. **R5 码表一致**：`code` MUST 是该字在五笔86 下的官方全码（以发布数据包为准；实现方不得自行"修正"码）。
6. **R6 简码槽位**：若给出 `shortcodes`，一级 MUST 为该字全码前缀且长度 1，二级长度 2、三级长度 3；同一字同一等级 MUST 唯一。
7. **R7 不猜**：无法同时满足应适用规则的字 MUST 标为 `partial` 并写原因，不得标 `full`。
8. **R8 键名字**：`class = key-name` 时，码 MUST 为 4 个相同字母，`roots` MUST 为该字自身或空（连打该键四次）。
9. **R9 成字字根**：`class = radical-char` 时，`code[0]` MUST 等于该字在 `roots` 表的键位，
   `code[1:]` MUST 全为笔画键（`g h t y n`）；单笔画字用 **R9a**：`码 = 键 ×2 + "ll"`。
   **R9e 官方特例**：`class = radical-char-exception` 时只要求 `code[0]` 等于报户口键，
   其余位 MUST 在 `evidence` 写明"官方特例取码，未由笔顺推导"。1.0 共 4 例：
   `母 XGUI`（报户口 + 特例）、`方 YYGN`、`车 LGNH`、`止 HHHG`——后三者的官方码无法由
   "报户口 + 首笔 + 次笔 + 末笔" 从各自笔顺推出（`方` 丶一乙丿 → 应得 `yygt`，官方为 `yygn`；`车` 一乙丨一 →
   应得 `lgng`，官方 `lgnh`；`止` 丨一丨一 → 应得 `hhgg`，官方 `hhhg`）。这类字 MUST 标
   `radical-char-exception`，不得为了让规则"通过"而改写码或笔顺（ADR-388）。
   **R9-bis 部件尾**（ADR-383）：`class = radical-char` 时，`code[1:]` 也 MAY 是
   "该字实际含有的标准部件序列 + 识别码"，前提是每个部件都在 `roots` 表内、键位逐位对齐、
   识别码可推导，并在 `evidence` 写明"报户口+部件尾"（当前仅 `卯 QTBH`）。
10. **R1-bis 部件内部拆分**：某字根在合体字内 MUST 按官方笔画段拆开时，以拆开后的段为取码单位。
    当前已知一例：**母 = 毌(x) + 一(g) + 丷(u)**（单字「母」仍按成字字根 `XGUI`），
    由此 `每 txgu` / `毒 gxgu` / `酶 sgtu` 等 11 字全部逐位可解释（ADR-384 附二）。
11. **R10 不冒充**：任何条目 MUST NOT 把 `radical-char-exception` 标成 `compound` 以绕过 R2/R3。

**PUA/占位规则**：解析私有区字形时，若某字的字形序列长度 = `code` 长度且末位不是该键的标准字根，末位 MUST 视为识别码槽
（R3 的一种情形）；不足四码的合体字根数 MUST 为 `code` 长度 − 1（否则该字最多只能标 `partial`）。

## 6. 识别码网格（规范性）

| 末笔 \ 结构 | 左右 | 上下 | 杂合 |
|---|---|---|---|
| 横 | g | f | d |
| 竖 | h | j | k |
| 撇 | t | r | e |
| 捺 | y | u | i |
| 折 | n | b | v |

末笔取该字**最后一笔**的笔画类别（横/竖/撇/捺/折）；结构取该字的五笔结构判定（左右/上下/杂合）。
**末笔与结构的判定口径**：以识别码字母反推的 `(末笔, 结构)` 组合为准（网格是双射），并在 `evidence` 记录来源；
与 IDS/CDP 结构不一致时 MUST 记录为 `structureConflict`，不静默改写。

## 7. 一致性等级（规范性）

| 等级 | 判定 | 适用 |
|---|---|---|
| **L1 码表** | 实现提供的 `char → code` 与标准 `chars.code` 完全一致（范围内全部字） | 输入法引擎/码表 |
| **L2 拆字** | 在 L1 基础上，`roots[]` 与标准逐位相同（字形与键位都相同） | 教学/学习区 |
| **L3 简码** | 在 L1 基础上，`shortcodes` 与标准逐条相同（含缺项） | 简码题型/提示 |
| **L4 教学** | 在 L2 基础上，能对每个 `full` 字给出识别码理由（末笔+结构）且与网格一致 | 拆解解释/题库 |

判定程序：`python3 tools/wubi86-std-check.py --bundle <数据包目录> --impl <实现数据目录> --level L2`。
**允许的实现差异**：`L2` 只比较根序，不比较 `evidence`/`notes`；`partial`/`unknown` 条目不参与等级判定，
但 MUST 在实现报告中列出（便于评估覆盖差距）。

## 8. 版本与变更（规范性）

- 版本号 `MAJOR.MINOR`；1.x 只允许**向后兼容**的增补（新增字、新增例字、勘误），破坏性变更（改规则/改已有字的根序）必须 `2.0`。
- 每次发布必须给出：`spec` 文本、`data` 表、`SHA256SUMS`、`CHANGELOG` 条目（含"为何改/证据"）。
- 勘误（errata）单独登记，不改历史版本的数据文件，只在新 MINOR 版本修正。
- 差异声明：本标准**独立制定**，不宣称与王码官方软件/教材逐字一致；不提供官方对照清单（无权威公开数据源，ADR-382）。
  若将来获得可再分发的权威数据，再按 MINOR 版本补差异说明。

## 10. 已知限制

1. **不等于"权威拆法"**：本标准只保证"规则自洽 + 可复核"，不保证与王码官方软件逐字一致（差异清单见 §8）。
2. **覆盖有限**：1.0 覆盖 GB2312 一级 3,755（学习字表并集 5,021）；扩展区/生僻字未收录。
3. **末端歧义**：4 码字中"3 字根 + 识别码"与"4 字根"在字形数据上可能同构，本标准以 `code` 与规则约束判定，
   无法区分时标 `partial`（见 `docs/standards/wubi-decomposition.md` §2 第 6 条与报告 304 F7）。
4. **不评价实现优劣**：L1–L4 只判一致性，不判输入体验与排序。

## 10.1 码表勘误（ADR-384）

标准允许**独立声明**的码表勘误层：若某一码被"同族 ≥3 字互证 + 规则完整解释"证明为错，
可在 `errata` 层登记 `erroneous → corrected`，实现方 MUST 在数据包 `meta.json` 里声明勘误条数与 SHA；
未声明勘误的实现，按原码判定（不影响其自身一致性）。

当前勘误：`酶 sgtu → sgtx`（同族 每/海/梅/悔/霉）。
