# EasyInputMethod 技术架构方案（v0.1 草案）

> 定位：**跨平台、开源可审计、默认离线、只做核心输入（拼音/五笔）、体积小、可扩展**的最小化中文输入法。
> 本文回答：怎么复用代码、选什么引擎、各平台怎么接入系统、怎么压体积、语音怎么本地化、以及安全工程怎么做。

---

## 1. 设计原则（先立规矩，后面所有取舍都服从它）

1. **默认离线**：核心二进制里不链接任何网络库；云功能若将来要加，必须是独立模块 + 显式开关 + 默认关。
2. **零遥测**：不上报任何按键、候选、词频、设备信息。要"改进"，只允许用户手动导出词库文件。
3. **核心与外壳分离**：引擎（纯逻辑）不感知平台、不感知 UI、不感知网络。
4. **开源可审计**：核心 + 前端全部开放；发布可复现构建 + 签名。
5. **最小可用**：不做皮肤商店、不做广告、不做账号、不做内容分发。
6. **可扩展而非可膨胀**：扩展点通过稳定的 C ABI 插件接口暴露，而非往核心里堆功能。
7. **数据即插件**：拼音词库、五笔码表、语音模型都是"数据包"，按需下载、可离线校验。

## 2. 总体架构

```
┌──────────────────────────────────────────────────────────────────┐
│                        平台前端 (Frontends)                        │
│  Windows: TSF (Text Services Framework, COM C++)                  │
│  macOS:   InputMethodKit (ObjC++ .app)                            │
│  Linux:   Fcitx5 addon (.so) / IBus engine (可选)                  │
└───────────────▲──────────────────────────────────────────────────┘
                │  稳定 C ABI：ime_session_*  (纯 C，跨语言安全)
┌───────────────┴──────────────────────────────────────────────────┐
│                      Core (framework-agnostic)                    │
│  Session/State Machine │ Candidate UI Model │ Config │ Commit      │
│  ┌─────────────┐  ┌─────────────┐  ┌──────────────────────────┐   │
│  │ Pinyin      │  │ Table(Wubi) │  │ Engine Registry (插件)    │   │
│  │ Engine      │  │ Engine      │  │  EngineV1 C ABI          │   │
│  └─────────────┘  └─────────────┘  └──────────────────────────┘   │
└───────────────▲──────────────────────────────────────────────────┘
                │
┌───────────────┴──────────────────────────────────────────────────┐
│            Data 层：编译后的二进制词典（mmap 只读，懒加载）          │
│   pinyin.bin (trie + n-gram)   wubi.bin (trie)   用户词库(user.bin) │
└──────────────────────────────────────────────────────────────────┘

           ┌───────────────────────────────────────────┐
           │ 可选模块（独立进程 / 独立 dlopen，默认不启用） │
           │  ASR: sherpa-onnx 本地语音；仅本地推理        │
           └───────────────────────────────────────────┘
```

**关键决策：核心用 C++ 还是 Rust？**

| 方案 | 优点 | 代价 |
|---|---|---|
| **C++17/20 core + C ABI** | 直接复用 librime(C++)；前端本来就是 C++/ObjC++；工具链成熟 | 内存安全需靠纪律 + 审计 + fuzz |
| **Rust core + C ABI** | 内存安全，隐私/安全是卖点，错误更难变漏洞 | librime 需 FFI(bindgen)；前端适配要写 C++ glue；团队需懂 Rust |

**建议**：若追求最快落地 + 复用 librime → **C++ 核心**；若把"安全"当第一卖点且团队有 Rust 能力 → **Rust 核心 + C ABI**，前端仍用 C++/ObjC++ 薄壳。两条路的对外接口都是同一套纯 C ABI，互不锁死。

**C ABI 草案（跨语言稳定接口）：**
```c
typedef struct ime_session ime_session;

ime_session* ime_session_new(const char* config_json);
void         ime_session_free(ime_session*);

// 输入一个按键，返回是否需要重绘 + 候选列表
int  ime_session_key(ime_session*, uint32_t keysym, uint32_t mods, int is_keyup);
const ime_candidate_list* ime_session_candidates(ime_session*);
int  ime_session_select(ime_session*, int index);      // 选中候选
int  ime_session_page(ime_session*, int delta);        // 翻页
char* ime_session_commit(ime_session*);                // 取待上屏文本
void ime_session_clear(ime_session*);
size_t ime_session_serialize(ime_session*, uint8_t* buf, size_t cap); // 可恢复状态
```

## 3. 引擎选型（这是最关键的决策）

### 3.1 三个候选

| 选项 | 许可 | 拼音质量 | 五笔 | 体积 | 移植性 | 结论 |
|---|---|---|---|---|---|---|
| **A. librime** | **BSD-3** | 好（成熟语言模型） | 好（table 引擎） | 中（核心库 + 词库） | 三平台已跑通 | **首选起步** |
| B. libpinyin | **GPL-3** | 好 | 需自写 table | 大（依赖 BerkeleyDB/KC） | Linux 为主 | 会传染 GPL，不推荐 |
| C. 自研引擎 | 你的(MIT/Apache) | 需自己训练/调 | 自写（简单） | 最小 | 原生 | 终局目标，成本高 |

**建议路线：A → C。**
- **M1 用 librime 起步**：BSD-3 允许你用 MIT/Apache 发布自己的产品，只要不复制 weasel/squirrel 的代码（那两个是 GPL-3）。librime 自带拼音 + table（五笔）翻译器，你只需把 **YAML/`*.bin` 那套复杂配置藏在内部**，对外只暴露简单设置。
- **M2+ 视体积/依赖情况**：可逐步把拼音引擎换成本地自研（trie + n-gram + 简繁错字模型），五笔本来就是码表引擎，自研成本很低。

> 注意：你的"开源可审计"目标与 GPL 并不冲突。真正要避开的是**无意中引入 GPL 代码导致授权被动**。librime 是 BSD，最安全。

### 3.2 五笔引擎（其实很简单，建议自研）

五笔是典型的**码表输入法**：输入串 → 精确/前缀查表 → 候选。
- 数据结构：Trie（前缀树）或双数组 Trie（double-array trie）+ 优先级。
- 支持 86/98/新世纪 三套码表，纯数据切换。
- 支持"四码自动上屏""简码""z 键万能键"等规则。
- 这部分自研收益最大：代码量小、无依赖、体积可控、可完全掌控。

### 3.3 拼音引擎（最难，先借力）

拼音难点在**语言模型与纠错**（连续整句、模糊音、错拼纠正、简繁、中英混排）。
- 起步用 librime 的拼音方案（推荐数据源见 §5）。
- 自研路线的核心是：双数组 Trie 词库 + n-gram 语言模型（可用 kenlm 训练，或自训小模型），再加一个"纠错/模糊音"规则层。
- 不要一上来重写拼音，投入产出比低。

## 4. 各平台前端接入

### 4.1 Windows — TSF（Text Services Framework）

- **必须用 TSF**（IMM32 已过时，Win10/11 现代应用不认）。实现 COM 组件：
  - `ITfTextInputProcessorEx`
  - `ITfThreadMgrEventSink`（焦点/文档切换）
  - `ITfKeyEventSink`（拦截按键）
  - `ITfCompositionSink`
  - `ITfDisplayAttributeProvider`（下划线/组合样式）
  - 候选窗：自定义窗口 + `ITfCandidateListUIElement`，或先用默认 UI 快速跑通。
- 注册：DLL + `regsvr32`，装到系统目录，注意 **32/64 位**都要。
- 参考实现：`rime/weasel`（GPL-3，**只能读不能抄**，否则你的前端被迫 GPL）。
- 坑：UWP/沙箱应用、管理员权限进程、Electron、游戏 DirectInput 各有兼容问题；候选窗要在不同 DPI 下正确。

### 4.2 macOS — InputMethodKit

- `IMKServer` / `IMKInputController` 子类，核心方法：
  - `handleEvent:client:` 拦截按键
  - `setMarkedText:selectionRange:replacementRange:` 显示预编辑
  - `insertText:replacementRange:` 上屏
- 打包成 `.app`，安装到 `~/Library/Input Methods/` 或 `/Library/Input Methods/`。
- 系统要求授权 **"输入监控"**（Input Monitoring）权限；分发需 **签名 + 公证（notarization）**。
- 参考实现：`rime/squirrel`（GPL-3，同样只读不抄）。
- 坑：候选窗需要自己画（无系统候选 UI API 给第三方）；不同 macOS 版本 API 有差异；Apple Silicon + Intel 通用二进制。

### 4.3 Linux — Fcitx5（首选）+ IBus（可选）

- **Fcitx5 addon**：实现 `fcitx::InputMethodEngineV2` / `InputContext`，编译成 `.so` 放进 Fcitx5 addon 目录，附 `.conf`。Wayland 支持好，开发体验最好。
- **IBus engine**：GNOME 默认栈，用 C + GObject 实现 `IBusEngine`。为覆盖 GNOME 用户需要，但可以第二阶段再做。
- 打包：`.deb`/`.rpm`/AUR/Flatpak。开源引擎如 `fcitx5-chinese-addons`、`ibus-libpinyin` 是同类参考（GPL，可参考架构）。
- 现实：Linux 用户群小但最拥护开源，是你的"口碑基本盘"。

## 5. 词典与数据策略（体积的关键）

体积主要不是代码，而是**词库 + 语音模型**。策略：

| 内容 | 体积 | 是否内置 | 策略 |
|---|---|---|---|
| 核心二进制（引擎+前端） | 2–8 MB | 是 | LTO + `-Os` + strip |
| 五笔码表 | < 1 MB | 是 | 编成双数组 Trie，mmap |
| 精简拼音词库 | 1–5 MB | 是（默认） | 选小型方案，如"袖珍简化字拼音"类 |
| 完整拼音词库 | 10–40 MB | 否（可选包） | 用户按需下载（雾凇拼音等，**先核实其许可**） |
| 用户自学习词库 | 小 | 是（本地生成） | 二进制 + 可选加密 |
| 语音模型 | 50–500 MB | 否 | 首次使用语音时下载，校验哈希 |

**压缩技术**：
- 词典用 **marisa-trie** 或双数组 Trie，`mmap` 只读，惰性加载，常驻内存低。
- UTF-8 处理用 `utf8proc`，**不要引入 ICU**（体积大）。
- 避免 Boost（librime 会带一些，评估能否裁剪）。
- 二进制用 LTO、`-ffunction-sections -Wl,--gc-sections`、strip。

**目标体积**：Windows 安装包 ≤ 15 MB，macOS app ≤ 15 MB，Linux 包 ≤ 10 MB（不含语音模型）。

## 6. 可扩展性设计

1. **引擎插件 ABI**（C，版本化）：
   ```c
   #define IME_ENGINE_ABI_V1 1
   typedef struct ime_engine_v1 {
       int  abi_version;
       const char* name;         // "pinyin" / "wubi" / "cangjie"
       void* (*create)(const char* cfg);
       void  (*destroy)(void*);
       int   (*translate)(void*, const uint32_t* keys, int n, ime_candidates* out);
       int   (*learn)(void*, const char* commit);  // 可选
   } ime_engine_v1;
   ```
   动态库放 `engines/` 目录，运行时加载；也可静态编译进核心（默认只带拼音+五笔）。
2. **方案/码表格式公开**：给出 `*.ime-table` 文本格式 + 编译器 `ime-dictc`，社区可贡献仓颉、郑码、小鹤。
3. **配置单一化**：用户只面对一个 `config.toml`（输入方案、模糊音、翻页键、候选数），不暴露内部 YAML。
4. **主题/候选窗**：定义简单主题文件，避免做皮肤商店。

## 7. 本地语音输入方案调研（默认不内置）

**原则**：推理全程本地、断网可用、模型按需下载、接口可插拔。

| 方案 | 许可 | 类型 | 中文效果 | 模型体积 | 适配度 |
|---|---|---|---|---|---|
| **sherpa-onnx** | Apache-2.0 | 流式 + 非流式，C/C++ API，跨平台 | 好 | 中 | ★★★★★ |
| whisper.cpp | MIT | 非流式（整句） | 中上 | 大 | ★★★★ |
| Vosk | Apache-2.0 | 流式 | 中 | 小 | ★★★ |
| FunASR 模型(SenseVoice/Paraformer) | 模型许可需逐个核实 | 非流式（可经 sherpa 跑） | 很好 | 中 | ★★★★ |

**推荐**：
- **首选 sherpa-onnx**（Apache-2.0，纯本地，支持流式 Zipformer/Paraformer，正好适合"按键说话、实时出候选"）。
  - 流式中英双语 Zipformer int8 模型约 100–200 MB，可做增量识别。
  - 若只做"按一次说一句"，用 SenseVoice-small / Paraformer 非流式，质量更好、实现更简单。
- **备用 whisper.cpp**：整句、MIT、生态成熟；但中文标点和实时性弱，适合"说完一遍再上屏"。
- **VAD**：用 silero-vad 做说话端点检测（避免把静音送去识别），体积 < 1 MB。
- **工程要点**：
  - ASR 作为**独立模块/独立进程**，通过 IPC 与核心通信 → 崩溃隔离、权限隔离、不影响核心体积。
  - 麦克风权限明确申请，录音**只进内存不回写磁盘**，识别完即丢。
  - 模型下载走 HTTPS + SHA-256 校验；支持完全离线导入模型文件。
  - 后期可选更小模型（如量化到 int8/4bit）把常驻压到 50 MB 级。

## 8. 安全与隐私工程（这是卖点，要能证明）

1. **编译期断网**：核心不链接 socket/DNS 库；CI 里检查生成的二进制不含网络符号。
2. **威胁模型**：外部**词典/方案文件是唯一不可信输入** → 解析器必须 fuzz（libFuzzer/AFL），限制递归深度、数组长度。
3. **内存安全**：优先 Rust；C++ 则用 `-fstack-protector-strong`、ASan/UBSan 测试、`std::span`/边界检查、禁用裸指针滥用。
4. **可复现构建**：固定工具链（Nix/Docker），发布产物可校验；提供 SBOM。
5. **签名分发**：Windows Authenticode、macOS 签名+公证、Linux 包签名 + GPG。
6. **最小权限**：只读自己的数据目录；不读剪贴板（除非用户主动用"粘贴上屏"）；非语音场景不申请麦克风。
7. **可验证的隐私**：README 给出一份"网络行为说明"，并附抓包脚本，任何人都能验证它不联网。
8. **依赖审计**：`cargo-audit` / `osv-scanner` / `Dependabot`，SBOM 随版本发布。

## 9. 里程碑路线图

| 阶段 | 交付物 | 验收标准 |
|---|---|---|
| **M0** 内核原型 | `core/` + CLI 测试器 `ime-cli` | 命令行里输入 `nihao`/`wqvb` 能出候选并上屏 |
| **M1** Linux 先行 | Fcitx5 addon | 在 Wayland/X11 上正常打字，候选窗正常 |
| **M2** Windows | TSF DLL | Win10/11 记事本/浏览器/Office 可用 |
| **M3** macOS | IMK .app | 签名公证后可安装，TextEdit/Safari 可用 |
| **M4** 可配置 | config.toml、用户词库、自定义短语、翻页键 | 普通用户不改代码能配好 |
| **M5** 体积与数据 | 词典编译器、精简/完整数据包分离 | 安装包 ≤ 15 MB |
| **M6** 语音(可选) | sherpa-onnx 本地 ASR 模块 | 断网可识别、模型可离线导入 |
| **M7** 发布 | 签名安装包、可复现构建、SBOM、隐私说明 | 第三方可复现 + 可抓包验证 |

**建议的第一个可用版本只做：拼音（librime 或自研）+ 五笔（自研码表）+ Linux/Windows 前端 + 简单配置。** macOS 和语音后置。

## 11. 主要风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 拼音质量打不过搜狗 | 用户不愿换 | 起步借 librime 方案，别裸写；主打"离线+安全"而非"最准" |
| librime 依赖/体积偏大 | 违背"最小" | 评估裁剪；终局自研拼音引擎 |
| Windows TSF 兼容性 | 上屏失败/崩溃 | 早做多应用矩阵测试；参考 weasel 的兼容处理思路 |
| macOS 公证/权限 | 安装受阻 | 提前准备开发者账号、签名流程 |
| 抄了 GPL 前端代码 | 授权被动 | 只读 weasel/squirrel 学架构，代码自己写 |
| 词库/方案许可不清 | 法律风险 | 每个数据包单独核实许可并记录在 `data/README` |
| 语音模型巨大 | 破坏"小"定位 | 模型永远外置、按需下载、可离线导入 |
| 单人/小团队维护跨平台 | 长期不可持续 | 先做 1–2 个平台做深，社区化前端维护 |

## 12. 一句话总结

**用 BSD-3 的 librime 做拼音起步、自研小体积码表引擎做五笔，核心写成框架无关的 C++/Rust 库并暴露纯 C ABI，三平台前端各写一层薄壳；数据与语音全部外置为可选包；核心编译期断网、零遥测、fuzz + 可复现构建，把"小而安全"做成可被第三方验证的事实而不是口号。**
