## 1. WindInput 评估：学什么，是否复用

### 1.1 它实际是什么（实测数据）

- **MIT**，★~970，官网 + 签名安装包 + 文档站；`wind_input` Rust ≈ **2.26 万行 / 12 crates + 2 apps**（此前还有一版 Go ≈ 15.3 万行，正在被 Rust 版替代）。
- 组件：`wind_input`(Rust 核心) + `wind_tsf`(C++ TSF) + `wind_macos`(Swift IMKit) + `wind_linux`(在建)；设置程序 `wind-setting` **未开源**。
- 设计文档规模惊人，仅 `docs/architecture/` + `docs/design/` 就有**上百个文件、数 MB**：
  - `engine-candidate-pipeline.md`（**100 KB**）——从词库到候选的完整链路
  - `candidate-sorting-rules.md`（45 KB）、`codetable-candidate-ordering.md`（22 KB）
  - `codetable-wildcard-plan.md`（144 KB）、`codetable-reverse-mode-plan.md`（155 KB）
  - `rime-dict-loading.md`（33 KB）、`config-design-rules.md`（14 KB）
  - `tsf-docmgr-focus-semantics.md`、`tsf-openclose-compartment-semantics.md`、`candidate-window-shadow-compat-notes.md`、`caret-position-host-compat-notes.md`
  - `association.md`（53 KB）、`codetable-sentence-input.md`（46 KB）、`data-custom-layer.md`（65 KB）

### 1.2 值得学的东西（具体、可落地）

1. **`Engine` trait 的契约设计**（`convert(input, max_candidates) -> ConvertResult`）——正是"预留多引擎混输接口"的成熟答案：
   - `EngineType`: `Pinyin` / `CodeTable` / `Mixed` / `English`
   - `ConvertResult`: `candidates` / `preedit_display` / `completed_syllables` / `partial_syllable` / `should_commit` / `should_clear` …
   - `Candidate` 带 `source`（`CodeTable`/`Pinyin`/`Phrase`…）、`is_prefix`/`is_partial`/`is_fuzzy`、`consumed_length`
   - → **我们要设计一套更小的同构 trait**，字段名可以参考，但裁到最小。
2. **两层排序模型**：第一层 `base_sort`（词库 `weight` 或 `natural` 出现序），第二层 `user_frequency`。这是"排序不回归"的关键，直接采用其思想。
3. **分层词库（CompositeDict）**：基础库 + 扩展库 + 用户库，支持 `base_order` 让扩展库候选永远排在基础库后。
4. **方案驱动的 TOML 配置**（`data/schemas/*.schema.toml`）：与我们"用户只面对一个 TOML"的想法一致，验证了方向。
5. **平台兼容性坑清单**：TSF 焦点/compartment 语义、候选窗阴影兼容、光标位置读取兼容——**这些是他们用真金白银踩出来的，我们直接读，能省几个月。**
6. **redb 作为用户数据存储**（纯 Rust 嵌入式 KV）：用户词库/词频/临时词/影子词的落地方案，值得采用。
7. **`key-pipeline S0–S4`**：把散装 bool 收敛为单一模式枚举、符号单点决策——状态机设计经验。

### 1.3 为什么不建议复用其代码

| 理由 | 说明 |
|---|---|
| 体量冲突 | 2.26 万行 + 12 crates，功能面覆盖通配符、反查、辅助码、整句、自动造词、Emoji、剪贴板反查、统计…**与"只做核心、最小"直接矛盾** |
| 架构耦合 | 它的 schema/config/dict 格式会变成我们的事实标准，失去设计自由 |
| 迁移债 | 它正处于 Go→Rust 迁移中（Go 版 15.3 万行），携带历史包袱 |
| 开源完整度 | 设置程序未开源，与"全部开源"目标不符 |
| 差异化 | 如果直接复用，我们就成了 WindInput 的分支而非独立产品 |

### 1.4 决策

> **读它的 `docs/architecture/` 与 `docs/design/`，把结论内化成我们的设计；代码全部自研。**
> MIT 意味着将来若某个具体算法（如拼音 lattice、候选窗兼容）想复用，可以**小段移植 + 保留版权声明**，作为例外而非基础。建立 `docs/参考与致谢.md` 记录借鉴来源。

### 2.1 Rust Only 的可达性核对（各平台）

| 平台 | 纯 Rust 可行性 | 结论 |
|---|---|---|
| macOS | `objc2` 无 InputMethodKit 现成绑定；IMK 用 Swift 是行业共识（karukan/pure-ime/vnkey/inputx 全这么做） | **Swift 薄宿主**（引擎 100% Rust） |
| Windows | `windows` crate 有 `Win32_UI_TextServices`（已确认），可用 `#[implement]` 实现 COM | **纯 Rust**（首选） |
| Linux | Fcitx5 addon 是 C++ 插件 ABI；社区有 `crrvx/hux-ime`（纯 Rust fcitx5 核心）证明可行，但成本高 | 先 **C++ 薄壳**，后评估纯 Rust |
| Android | `jni` crate 成熟 | **纯 Rust 核心 + Kotlin 宿主** |
| iOS | 需 Swift 键盘扩展 + Rust staticlib；不申请 Full Access | **Swift 薄宿主**（引擎 100% Rust） |

## 3. 五笔码表调研（实测）与体积策略

### 3.1 实测数据

| 数据源 | 许可 | 文件 | 体积 | 单字条数 | 词组条数 |
|---|---|---|---|---|---|
| `KyleBing/rime-wubi86-jidian` | **Apache-2.0** | `wubi86_jidian.dict.yaml` | **1.32 MB** | 26,602（313 KB） | 62,657（1.01 MB） |
| `rime/rime-wubi`（官方） | **LGPL-3.0** ❌ | `wubi86.dict.yaml` | 2.29 MB | 75,696（1.02 MB） | 61,220（1.26 MB） |
| `KyleBing/.../pinyin_simp` | **Apache-2.0**（源自 AOSP PinyinIME） | `pinyin_simp.dict.yaml` | 2.04 MB | 17,037（186 KB） | 83,660（1.86 MB） |
| `aardio/wubi-lex` | MIT | `86.txt`/`98.txt`/`06.txt` | 117–471 KB | — | **不是码表，是"拆字表"**（字→字根），可用于反查/字根提示 |

**关键观察：单字部分很小（186–313 KB），词组部分是大头（1–1.9 MB）。**

### 3.2 ⚠️ 必须正视的 provenance 风险

`rime-wubi86-jidian` 的 README 明确写道：

> "码表也是使用原有**极点码表**进行扩展的。单字的顺序严格对标原极点输入法词库"

即：**该表的底层是"极点五笔"的码表**。极点五笔是闭源软件，第三方把它的码表以 Apache-2.0 重新发布，**法律上存疑**。`wubi-lex` 号称的"微软五笔码表"同理属于微软，也未必能被 MIT 重新授权。

> 五笔"编码"本身（字→码）是事实性数据，通常不受版权保护；但**词库的编排/选择/权重**可能构成汇编作品。这是 Rime 生态长期存在的灰区——`pure-ime` 专门为此写了 `docs/data-provenance.md` 和 data intake policy。

### 3.3 决策：体积策略 + 数据准入

**体积策略（内置最小、外置可选）：**

| 层 | 内容 | 目标体积 |
|---|---|---|
| 内置核心 | 五笔86 **单字全量**（含 GB2312 外常用字）+ **精选高频词组**（~10k 条） | ≤ 0.6 MB（编译后） |
| 可选包 1 | 五笔86 全量词组（~62k） | ~1 MB |
| 可选包 2 | 五笔98 / 新世纪 / 郑码 / 小鹤音形 | 各 0.3–0.6 MB |
| 可选包 3 | 拼音词库（`pinyin_simp`，Apache-2.0） | ~2 MB |
| 可选包 4 | 反查/拆字表（`wubi-lex` 拆字，MIT） | ~0.2 MB |

**数据准入制度（必须建立 `docs/数据来源与许可.md`）：**
1. 每份数据记录：来源 URL、上游、声明许可、**原始作者**、加入日期、校验和。
2. 优先选择许可清晰且**作者自有**的数据；对"第三方重新授权"的数据打 ⚠️ 标记。
3. **长期方案**：考虑从公开的**五笔86 编码规范 + 开放字形分解数据**自行生成单字码表，彻底规避风险（编码规则是公开规范，字根拆分可自建）。列为 M 阶段任务。
4. 数据与代码解耦：码表只是"可替换的数据包"，法律问题不牵连代码。

## 4. 拼音：可插拔后端设计（不写死实现）

### 4.1 设计（留好切换口）

```rust
// ime-core
pub trait PinyinBackend: Send {
    /// 音节切分
    fn segment(&self, input: &str) -> Vec<Syllable>;
    /// 由输⼊得到候选（含模糊音、简拼、前缀补全）
    fn convert(&self, input: &str, max: usize) -> Vec<PinyinCandidate>;
    /// 反查：字/词 → 拼音（五笔用户的高频需求，成本极低）
    fn reverse_lookup(&self, text: &str) -> Option<String>;
    fn name(&self) -> &'static str; // "inputx" | "librime" | "native"
}
```

- `ime-pinyin` crate 只依赖这个 trait；
- 具体后端通过 **Cargo feature** 或运行时注册选择；
- **关键：`reverse_lookup` 单独抽象**，因为它只需"字→拼音"数据（`pinyin` crate + MIT 数据即可），**Phase 1 就能用**，不依赖完整拼音引擎。

### 4.2 后端对比

| 后端 | 许可 | 语言 | 质量 | 体积/依赖 | 建议 |
|---|---|---|---|---|---|
| **`inputx-pinyin`** | **MIT OR Apache-2.0**（已确认仓库含 `LICENSE-MIT`+`LICENSE-APACHE`） | **纯 Rust** | 未知（v1.4.0，自研 FSA + 模糊音 + 简拼 + 前缀补全） | 小，WASM 友好 | **✅ 快速实现首选**（保持纯 Rust、可交叉编译到移动端） |
| `librime` FFI | BSD-3 | C++ | 最高 | 大（C++ 工具链 + boost 等） | ⚠️ 可选高质量后端（非默认） |
| 自研 FSA | Apache-2.0 | Rust | 需打磨 | 最小 | 🎯 终局 |
| `libpinyin` | **GPL-3** | C++ | 好 | 大 | ❌ 许可不允许 |

### 4.3 决策

> **trait 先行。Phase 2 先用 `inputx-pinyin`（纯 Rust、许可干净）跑通；若质量不足或 API 不适用，切换 `librime` 后端（BSD-3，可链接）。终局用自研 FSA 替换。整个过程不改 `ime-core`。**
>
> **Phase 1 只做 `reverse_lookup` 的轻量实现**（`pinyin` crate + `mozillazg/pinyin-data` MIT），让五笔用户可以反查生字，不需要完整拼音引擎。

## 6. Phase 1 重新定义：完整可用的 macOS 五笔输入法

**不是"只能打几个字的 MVP"，而是"能替换掉现有输入法日常使用"的版本。**

### 6.1 Phase 1 功能清单

| 类别 | 必须包含 |
|---|---|
| 五笔核心 | 五笔86 单字 + 词组、**一级/二级/三级简码**、键名字、成字字根、`z` 万能键、四码自动上屏（可配） |
| 候选交互 | 候选窗（自绘原生）、数字/空格选字、翻页、上下键、退格回退、Esc 取消 |
| 输入辅助 | 中英切换、全半角、标点符号（含成对匹配）、大小写 |
| 反查 | **拼音反查**（字→拼音，轻量实现，帮助五笔用户查生字） |
| 词库 | 系统码表 + **用户词库 + 词频学习**（redb 或自研二进制存储） |
| 配置 | TOML 配置文件（方案切换、模糊/翻页键、候选数、自动上屏开关） |
| 系统集成 | 安装/卸载（.pkg 或脚本）、输入法菜单、图标、随系统明暗主题、**不崩溃/不卡顿** |
| 隐私 | 零网络、零遥测、`PRIVACY.md` + 抓包验证脚本 |

### 6.2 Phase 1 验收标准（DoD）

1. 在 **TextEdit / Safari / VS Code / 微信 / Terminal** 中五笔输入**长时间稳定**，无候选窗错位、无残留、`Cmd+Z` 正常。
2. 单次按键 → 候选 < 16 ms；常驻内存 ≤ 30 MB（不含 mmap）。
3. 用户词库与词频在重启后保留；可手动导出/导入。
4. 安装包 ≤ 15 MB；签名（若条件允许）或提供清晰的手动安装说明。
5. `scripts/verify-no-network.sh` 证明进程零外联。
6. `ime-cli` 能复现全部核心逻辑（便于 CI 与回归）。

### 6.3 里程碑

| 阶段 | 交付 | 说明 |
|---|---|---|
| **P1-M0** | workspace + `ime-core` + `ime-table` + `ime-cli repl` | 纯逻辑跑通：码→候选→上屏→学习 |
| **P1-M1** | `ime-dict` 编译器 + 五笔86 数据 + `数据来源与许可.md` | 产出 `.imedict`，体积达标 |
| **P1-M2** | Swift/IMK 宿主 + C ABI | 系统内可安装、可打字 |
| **P1-M3** | 候选窗 + 用户词库 + 配置 + 拼音反查 | 达到 DoD |
| **P1-M4** | 发布工程（安装包、隐私文档、抓包脚本、可复现构建） | **Phase 1 完成** |
| P2 | 拼音引擎（`inputx-pinyin` 后端）+ 五笔拼音混输 | 横向扩展 |
| P3 | Windows（Rust TSF） | |
