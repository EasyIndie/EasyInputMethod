## 1. 产品命名

### 1.1 设计原则（按你的要求）

- **靠联想而非直述**：不叫"极简输入法""安全输入法"这类把功能写在脸上的名字；
- **接地气**：取自日常事物/口语（食物、纸张、做人道理），不文绉绉、不拗口；
- **一看就懂**：听到名字的瞬间能把"没添加、不越界、不添乱"与产品特点对上；
- **不与现有输入法冲突**（GitHub 已粗筛，均无直接撞名，见 §1.4）。

### 1.2 候选（按联想角度分组）

| 名称 | 联想来源 | 一眼就懂的点 | 英文名 | 适配度 |
|---|---|---|---|---|
| **原味** | 原味酸奶/原味鸡等食品术语 | **"无添加"** → 无广告、无追踪、无冗余功能，只留原始功能 | Original | ★★★★★ |
| **本分** | "做人要本分" | **"守本分、不越界"** → 不偷看、不多事、不多装东西 | Principled | ★★★★★ |
| **留白** | 国画/设计术语 | **"不填满、留出空间"** → 克制、只做核心、不堆砌 | Margin / Whitespace | ★★★★☆ |
| **白纸** | 白纸/白板 | **"干净、空白"** → 简单、从零开始、没有预装的乱七八糟 | Blank | ★★★★☆ |
| **两全** | 成语"两全其美" | **"两种都满足"** → 五笔准 + 拼音兜底，不用二选一 | Both / Dually | ★★★★ |
| **素面** | "素面朝天" | **"不加修饰"** → 素净、本真、不浮夸 | Bare | ★★★☆ |
| **顺手** | 口语"用着顺手" | **"顺手、不添乱"** → 流畅、无干扰 | Handy | ★★★☆ |
| **省心** | 口语"省心" | **"不用操心"** → 无广告无捆绑、装上就不管 | NoWorry | ★★★ |
| **一根筋** | 口语"一根筋" | **"就干一件事"** → 只做输入，不花心、不外扩 | Singleminded | ★★★（有趣但略自嘲） |

### 1.3 推荐

**首推：原味（Original）**
> **联想路径最短、最接地气**：日常语境里"原味"就是"**没加料**"。听到"原味输入法"，用户立刻能对上——**没有广告、没有追踪、没有一堆用不上的功能，只保留输入本身**。
> 标语：**原味输入法 —— 只做输入，不加料。**
>
> 之所以把它排在"本分""留白"之前：原味是**大众食品语汇**，理解成本几乎为零；而"本分"偏向做人道理、"留白"偏设计圈，联想都多一步。

**强烈并列备选：本分（Principled）** —— 如果更想突出**隐私/安全**这层灵魂，`本分` 的"不越界、不偷看"比"原味"更直击隐私卖点。标语：**只做该做的，不多看一眼。**

**第三：留白（Margin）** —— 如果更想突出**极简美学**。标语：**少即是多。**

### 1.4 落地提示

- GitHub 粗筛：`原味输入法 / 本分输入法 / 留白输入法 / 白纸输入法` 均**无直接撞名**（结果为不相关仓库）。
- 待办：**商标检索**（国家知识产权局）+ 域名/GitHub org 可用性；确定后统一 crate 前缀与产品标识。
- 英文名建议与中文并列使用（README/包名），如 `Original IME` / `yuanwei-ime`。

## 2. 五笔码表自建：可行性评估与方案

### 2.1 实测证据（关键）

用 `rime-wubi86-jidian`（Apache-2.0）的数据反向验证**词组码能否由单字全码按标准规则推导**：

| 词组长度 | 规则 | 结果 |
|---|---|---|
| 2 字词 | 取每字前 2 码 `AaAbBaBb` | — |
| 3 字词 | `AaBaCaCb`（1字首、2字首、3字首、3字次） | — |
| 4–10 字词 | `AaBaCaZa`（首字首、2字首、3字首、末字首） | — |
| **合计** | | **62,657 条中 62,592 条命中，命中率 99.90%** |

65 条不符的**全部是含英文/字母的词**（`AirPods`、`Apple`、`B站`、`GoPro`、`IMAX`、`卡拉OK` 等），属规则外特例，不影响结论。

> **结论：词组码 = 单字码 + 词表，可以 100% 自动生成。**

### 2.2 自建流水线

```
[字根表] 25 键 → 字根（公开规范，固定）
      +
[编码规则] 键名字 / 成字字根 / 合体字 / 末笔字型识别码   ← 自研 Rust，约 400–600 行
      ↓
[字 → 字根拆分]  ← 多份 MIT 拆字表交叉校验
      ↓
[字 → 全码] →  code → [字]     （单字码表，自建）
      ↓
[词表]（phrase-pinyin-data, MIT）+ [词组编码规则]  →  code → [词]
      ↓
[词频权重] → 排序            （开放词频数据）
      ↓
                   .imedict  （出厂码表 = 我们生成的）
```

### 2.3 数据来源（全部要求 MIT / 可再分发）

| 环节 | 来源 | 许可 |
|---|---|---|
| 词组编码规则 | 公开标准（与 jidian 表的 encoder 规则一致，已实测验证） | 事实 |
| 字→字根拆分 | `aardio/wubi-lex` 的 `86.txt`（6,861 字） | **MIT** |
| 字→字根拆分（交叉校验） | `huanfeng/WindInput` 的 `data/schemas/wubi86/wubi86_chaizi.txt` | **MIT** |
| 词表 | `mozillazg/phrase-pinyin-data` `pinyin.txt`（~9.8 万词，1.25 MB，含拼音） | **MIT** |
| 词频 | 开放词频表（选型待定，需核许可）或按词表启发式 | 待定 |

### 2.4 复杂度评估

| 环节 | 复杂度 | 工作量 |
|---|---|---|
| 编码器（含识别码/键名/成字字根） | 低 | 1–2 天 |
| 字根拆分数据交叉校验 + 差异人工裁定 | **中**（主要工作量） | 3–7 天 |
| 词组自动生成 | 低（几乎全自动） | 0.5 天 |
| 词频接入与排序调优 | 中 | 1–3 天 |
| 回归测试（用公开码表当测试集，**不打包**） | 低 | 1–2 天 |
| **合计** | **中等偏低** | **约 1–2 周** |

> 测试集可以用公开码表（包括 LGPL 的表）**只做对照测试、不进产物**，不构成分发。

### 2.5 决策

> **采用自建。** 好处：
> 1. **许可最干净**——出厂码表由我们自己的脚本从 MIT 数据生成，脚本 + 源数据哈希全部开源可审；
> 2. **可扩展**——同一套编码器可再生成五笔98 / 新世纪 / 郑码；
> 3. **差异化**——"码表可复现生成"本身就是一个开源项目难得的卖点；
> 4. 顺带产出 `字→字根拆分`，直接用于**字根提示 / 反查拆字**功能。
>
> 过渡期：在自建流程跑通前，可临时用 `rime-wubi86-jidian`(Apache-2.0 声明) 作为**开发用数据**，并在 `docs/数据来源与许可.md` 标注 provenance 风险，**不进入正式发布**。

## 3. 输入模式设计（默认混合输入）

### 3.1 三种模式

```rust
enum InputMode {
    Mixed,      // 默认：五笔为主 + 拼音兜底
    WubiOnly,   // 仅五笔
    PinyinOnly, // 仅拼音
}
```

- **默认 `Mixed`**；模式随配置持久化；提供快捷键/菜单显式切换另两种模式。
- 模式是**单一状态**（参考 WindInput 的 key-pipeline 经验：把散装 bool 收敛成一个枚举），避免"半开半关"的混乱。

### 3.2 混输合并规则

1. 输入串先交 **五笔引擎**（精确 + 前缀）求解。
2. 同时判断输入串是否能构成**合法拼音音节序列**，能则交 **拼音引擎**求解。
3. **合并排序**：
   - 五笔候选在前（标注来源为"五笔"）；
   - 拼音候选在后（标注"拼"）；
   - 同一字/词重复时去重，保留权重高者。
4. **空码兜底**：五笔无候选时，直接展示拼音候选——这就是"想不出五笔时"的兜底路径。
5. **自动上屏保守**：仅在「五笔精确唯一匹配」时触发自动上屏，避免拼音兜底误上屏。
6. 候选的 `source` 字段贯穿排序与词频记账（借鉴 WindInput 的 `CandidateSource`）。

### 3.3 对 Phase 1 的影响

> **默认混输 ⇒ Phase 1 必须带一个可用的正向拼音引擎**（不是只做反查）。
> 因此原计划"拼音 Phase 2"调整为：**Phase 1 接入拼音后端（用于混输兜底）**，Phase 2 再打磨拼音体验（整句、模糊音、简拼、长句）并替换自研引擎。

### 3.4 关于"拼音 vs 五笔速度差距"

- 这个差距在**默认混输**下被抹平：五笔能打就打五笔（快、准），想不出码就拼音兜底，不用切模式。
- **不做**打字速度统计/比拼这类功能（属"花哨功能"范畴），保持核心纯净。

## 4. 拼音后端（Rust 优先，Phase 1 接入）

| 优先级 | 后端 | 许可 | 语言 | 说明 |
|---|---|---|---|---|
| **1** | **`inputx-pinyin`** | MIT OR Apache-2.0（已确认含双许可文件） | **纯 Rust** | 自研 FSA + 模糊音 + 简拼 + 前缀补全；保持全 Rust 构建与移动端交叉编译 |
| 2 | 自研 FSA（复用 `ime-table` 的 Trie/词典设施） | Apache-2.0 | Rust | 终局 |
| 3 | `librime` FFI | BSD-3 | C++ | 仅在 1/2 质量不足时作为可选后端 |
| ❌ | `libpinyin` | GPL-3 | C++ | 许可不允许 |

- 全部实现 `PinyinBackend` trait（`segment` / `convert` / `reverse_lookup`），**通过 Cargo feature 或运行时注册切换，不写死**。
- Phase 1 至少接入 **1 个**后端；trait 保证未来可无痛替换。

## 5. 配置文件格式

### 5.1 选型对比

| 格式 | 可读性 | 注释 | 层级 | Rust 生态 | 结论 |
|---|---|---|---|---|---|
| **TOML** | 高 | ✅ | ✅ | `toml` crate 成熟 | **✅ 选它** |
| KDL | 高 | ✅ | ✅（节点式） | 一般 | 更现代但用户不熟，联想成本高 |
| YAML | 中 | ✅ | ✅ | 成熟 | 缩进敏感、易写错，不推荐给普通用户 |
| INI | 高 | ✅ | ❌ | 简单 | 太受限 |
| JSON | 低 | ❌ | ✅ | — | 不能写注释，不适合配置 |

### 5.2 决策：配置用 TOML，码表用 TSV

- **配置**：TOML。它已经是"简洁易读 + 可注释 + 有层级"的最优解，且 Rust 生态最好。
- **码表/词库**：**不用 TOML**（几十万行数据会变得难读且解析慢），用 **TSV**（`字\t码\t权重`），人类可读、工具链简单。

### 5.3 配置设计规则（保证"一读就懂"）

1. **全中文注释**，每个选项一句话说明，必要时给示例；
2. **扁平化**，最多两层；
3. **合理默认值**，用户不改也能用；
4. **选项要少**（先控制在 10 个以内）；
5. 每个选项注明**可选值**。

示例（草稿）：

```toml
# ── 原味输入法配置 ──
# 修改后重启输入法生效

mode = "mixed"        # 输入模式: mixed(五笔+拼音) | wubi(仅五笔) | pinyin(仅拼音)

[input]
auto_commit_4code = true   # 输入满四码且唯一时自动上屏
z_key = "wildcard"         # z 键功能: wildcard(万能键) | none(无)
fuzzy_pinyin = false       # 是否启用模糊音(拼音兜底时生效)

[candidate]
count = 7                  # 每页候选数量（3-9）
page_keys = ",-"           # 翻页键

[appearance]
theme = "auto"             # auto(跟随系统) | light | dark
font_size = 16
```

> 若日后觉得 TOML 仍不够"接地气"，可再加一层**纯文本快捷配置**（如 `settings.txt` 键值对）作为简化前端，TOML 作为完整后端。

## 7. 更新后的 Phase 1 范围与里程碑

**目标：macOS 上"默认可混输"的完整五笔输入法，能替换现有输入法日常使用。**

### 7.1 功能范围（相对 v0.3 的变化）

| 变化 | 说明 |
|---|---|
| ➕ 默认 `Mixed` 模式 | 五笔为主 + 拼音兜底，含三模式切换 |
| ➕ 拼音后端接入 | Phase 1 即接入 Rust 拼音后端（`inputx-pinyin` 优先） |
| ➕ 拼音反查 | 用字→拼音数据，帮助查生字 |
| ➕ 自建码表流水线 | 编码器 + 词组自动生成 + `数据来源与许可.md` |
| ➖ 签名/公证 | 移出 Phase 1 |
| 配置 | TOML，完全中文注释 |

### 7.2 里程碑

| 阶段 | 交付 | 完成标志 |
|---|---|---|
| **P1-M0** | Cargo workspace + `ime-core`（`Engine`/`InputMode`）+ `ime-table` + `ime-cli repl` | 纯逻辑：码→候选→上屏→模式切换跑通 |
| **P1-M1** | 自建码表流水线：`wubi-encoder` + 拆字交叉校验 + 词组自动生成 + `数据来源与许可.md` | 生成 `.imedict`，体积达标，许可可审 |
| **P1-M2** | 拼音后端接入（`PinyinBackend` + `inputx-pinyin`）+ 混输合并 | `ime-cli` 里空码自动出拼音候选 |
| **P1-M3** | Swift/IMK 宿主 + C ABI | 系统内可安装、可打字 |
| **P1-M4** | 候选窗 + 用户词库/学习 + TOML 配置 + 拼音反查 | 达到 DoD |
| **P1-M5** | 打包脚本 + 隐私文档 + 抓包验证 + 可复现构建 | **Phase 1 完成** |
| P2 | 拼音体验打磨（整句/模糊音/简拼）+ 自研引擎替换 | |
| P3 | Windows（Rust TSF） | |
| P4 | Linux（Fcitx5） | |
| P5 | Android / iOS | |
| P6 | 本地语音（可选） | |

### 7.3 Phase 1 验收（DoD）

1. 在 TextEdit / Safari / VS Code / 微信 / Terminal 长时间稳定，候选窗不错位、无残留、`Cmd+Z` 正常。
2. **默认混输**：五笔能打则快，空码自动出拼音候选；三模式切换生效并持久化。
3. 拼音反查可用。
4. 按键→候选 < 16 ms；常驻内存 ≤ 30 MB（不含 mmap）。
5. 用户词库与词频重启保留，可导出/导入。
6. 安装包 ≤ 15 MB；手动安装流程文档清晰。
7. `scripts/verify-no-network.sh` 证明零外联。
