# EasyInputMethod 技术方案 v0.2（Rust / Apache-2.0 / 五笔优先）

> 本文取代 `docs/技术架构方案.md`（v0.1）。v0.1 是通用调研，本文是基于**竞品与生态实测**后的可执行方案。
>
> 目标：跨平台、开源可审计、默认离线、只做核心输入、体积小、可扩展的最小化中文输入法。
> 本阶段语言 **Rust**、许可 **Apache-2.0**、输入法类型 **五笔优先**，平台顺序 **macOS → Windows → Linux → Android/iOS**。
>
> **本文只做方案，经审查后再进入实现。**

---

## 0. 调研带来的三个关键结论（先说最重要的）

1. **这个赛道已经有人做了，而且做得很接近。** `huanfeng/WindInput`（清风输入法）就是"Rust 核心 + 五笔优先 + Windows/macOS"的同类产品，MIT、★~970、已有官网和签名安装包。**我们不能再做"另一个五笔输入法"，必须有明确差异化。**
2. **架构不用重新发明。** `karukan`（日文）、`vnkey`（越南文）、`pure-ime`、`inputx` 已经验证了同一套模式：**Rust 核心 + 窄 C ABI + 各平台原生薄宿主**。我们直接采用，并借鉴它们踩过的坑。
3. **Rust 生态的轮子是齐的**：`windows` crate 有 `Win32_UI_TextServices` feature（TSF 可用）、`yada`/`daachorse` 提供双数组 Trie、`mozillazg/pinyin-data`（MIT）提供拼音数据、`sherpa-onnx` 提供本地语音。**核心不需要依赖 librime 这类 C++ 大件。**

## 3. 语言与许可策略

- **语言**：Rust（`edition 2021`，MSRV 固定），核心 `#![forbid(unsafe_code)]`（FFI 层例外且集中）。
- **许可**：Apache-2.0，附 `NOTICE` 与第三方依赖清单。
- **依赖治理**：
  - CI 跑 `cargo-deny`：禁 GPL/AGPL/LGPL、禁未知许可；
  - CI 跑 `cargo-audit` / `osv-scanner`；
  - 生成并随版本发布 **SBOM（CycloneDX）**；
  - 依赖尽量少，能用 `core`/`alloc` 就不用 std 之外的东西。

### 4.2 C ABI 草案（`ime-ffi`）

```c
typedef struct ImeSession ImeSession;

// 生命周期
ImeSession* ime_session_new(const char* config_json_utf8);
void        ime_session_free(ImeSession*);

// 输入事件：返回位掩码（是否需要重绘 / 是否消费该键）
uint32_t    ime_session_key(ImeSession*, const ImeKeyEvent*);

// 候选查询：返回的指针在下次调用前有效，由库持有
const ImeCandidates* ime_session_candidates(ImeSession*);
void        ime_session_select(ImeSession*, int32_t index);
void        ime_session_page(ImeSession*, int32_t delta);

// 取上屏文本（调用方负责 ime_string_free）
ImeString   ime_session_commit(ImeSession*);
void        ime_string_free(ImeString);

// 焦点/重置
void        ime_session_focus_out(ImeSession*);
void        ime_session_reset(ImeSession*);
```

**设计要点**（学 `pure-ime` / `msime` 的 `host-api`）：
- 纯 C，不透明句柄，**显式释放**，禁止跨线程共享句柄（线程绑定）。
- 文本一律 UTF-8 + `(ptr, len)`，**永不返回 Rust `String`**。
- 错误用返回码，不 panic 穿越 FFI（`catch_unwind` 兜底）。
- 所有 FFI 集中在 `ime-ffi`，`ime-core`/`ime-table` 保持 `forbid(unsafe_code)`。

## 5. 平台宿主实现（顺序：macOS → Windows → Linux → Android/iOS）

### 5.1 macOS（第一优先）

- **形态**：`.app` bundle，装到 `~/Library/Input Methods/`，`IMKServer` + `IMKInputController` 子类。
- **技术选择**：**Swift/AppKit 宿主 + Rust `staticlib`**，而不是纯 Rust `objc2`。
  - 理由：`objc2` 没有现成的 InputMethodKit 绑定；Swift 写 IMK 是标准路径；`karukan`/`pure-ime`/`vnkey`/`inputx` **全部这么做**。Rust 只负责引擎，边界是 C ABI。
- 关键 API：`handleEvent:client:`、`setMarkedText:selectionRange:replacementRange:`、`insertText:replacementRange:`。
- 候选窗：自绘 `NSPanel`/`NSWindow`（系统不提供第三方候选 UI）。
- 权限：需**输入监控**；分发需 **签名 + 公证（notarization）**（WindInput 目前就卡在未公证）。
- 坑：通用二进制（arm64+x86_64）、多显示器/DPI、Command 键与系统快捷键冲突、`Cmd+Z` 撤销要保住。

### 5.2 Windows（第二优先）

- **形态**：TSF 文本服务（COM）。
- **技术选择**：**Rust + `windows` crate（`Win32_UI_TextServices`）** 直接实现 COM；若 COM 样板过于痛苦，退回 **C++ 薄壳 + Rust 核心**（WindInput 用 C++，retype 用 Rust，两条路都有人走）。
  - 需要实现：`ITfTextInputProcessorEx`、`ITfThreadMgrEventSink`、`ITfKeyEventSink`、`ITfCompositionSink`、`ITfDisplayAttributeProvider`。
- 候选窗：自绘 layered window。
- 分发：Authenticode 签名；注意 32/64 位、以及 SmartScreen 信誉累积。
- 坑：UWP/沙箱、管理员进程、Electron、游戏 DirectInput、高 DPI。

### 5.3 Linux（第三优先）

- **首选 Fcitx5 addon**：C++ 薄壳实现 `fcitx::InputMethodEngineV2`，调 Rust C ABI。Wayland 支持好。
- **可选 IBus**：覆盖 GNOME 默认栈。
- 打包：`.deb`/`.rpm`/AUR/Flatpak。
- 参考：`karukan-im/fcitx5`、`vnkey-fcitx5`、`crrvx/hux-ime`（纯 Rust fcitx5 核心）。

### 5.4 Android / iOS（第四优先）

- **Android**：Kotlin `InputMethodService` + `jni` 调 Rust `cdylib`（`libime.so`）。参考 `retype`、`trime`。
- **iOS**：Swift `UIInputViewController` 键盘扩展 + Rust `staticlib`；**不申请 Full Access**（`inputx` 证明不申请也能用本地词库）。参考 `inputx`。
- 移动端要在 Phase 1 就把 `ime-core` 设计成 **no_std 友好、无 IO**，否则移植会痛。

## 6. Phase 1：五笔优先，打通全流程（本阶段的核心工作）

### 6.1 五笔引擎设计（`ime-table`）

五笔本质是**码表输入法**，但要做得"像商业输入法"需要这些细节：

| 能力 | 说明 |
|---|---|
| 单字码表 | code(≤4) → [字 + 权重]，用 **`yada` 双数组 Trie** |
| 词组码表 | 2~4 字词；每字取前 2 码 |
| 简码 | 一级(25)/二级(625)/三级简码；打出后直接出字 |
| 键名字/成字字根 | 特殊规则 |
| 前缀提示 | 输入 1~3 码时给候选预览 |
| 四码唯一自动上屏 | 可配置 |
| `z` 万能键 | 可配置 |
| 标点/中英切换 | 核心必备 |
| 用户词库 + 学习 | `cedarwood` 动态 Trie，本地持久化 |
| **五笔拼音混输** | 五笔无候选时，把同一串喂给拼音引擎并合并候选（WindInput / inputx / 万能五笔的核心体验） |

> 「五笔拼音混输」是**决定用户是否会换用**的关键体验，必须先留好接口（`Engine` trait 支持多引擎合并候选），即使 Phase 1 只实现五笔。

### 6.2 输入流程状态机（`ime-core`）

```
Idle ──按键──▶ Composing(keys=[], candidates=[])
                  │ 每次按键：
                  │   1. 累积 code
                  │   2. 码表查询：exact + prefix
                  │   3. （预留）拼音引擎并行查询
                  │   4. 候选合并、去重、按权重排序
                  │   5. 判断是否需要重绘
                  ▼
      ┌── 选字(数字/空格) ──▶ Commit(上屏) ──▶ 学习(可选) ──▶ Idle
      ├── 退格 ──▶ 删一个 code，回到 Composing
      ├── Esc ──▶ Cancel ──▶ Idle
      └── 无效键 ──▶ 透传给系统
```

### 6.3 词典编译与加载（`ime-dict`）

- 源格式：TSV（`code\ttext\tweight`）或 Rime `*.dict.yaml` 导入器（**仅本地导入，不内置未授权数据**，学 `pure-ime` 的做法）。
- 编译产物：`.imedict` = 头部 + `yada` 序列化数据 + 元信息（版本、生成时间、源校验和）。
- 运行期：`mmap` 只读，惰性加载，常驻内存低。
- 用户词库单独一层 `.imedicd`（可写），与系统词典分层查询。

### 6.4 Phase 1 的"全流程跑通"验收标准（DoD）

1. **macOS**：安装 `.app` 后，在 TextEdit / Safari / VS Code 里用五笔打出「我」「五笔」「输入法」等词，候选窗正常、撤销正常、切换应用不残留。
2. **混输接口**：`Engine` trait 已支持多引擎，测试里用 mock 拼音引擎验证合并逻辑。
3. **CLI**：`ime-cli repl` 能加载词典、输入 code 出候选、选字上屏、demo 学习。
4. **测试**：核心逻辑单测覆盖率达标；词典解析器过 fuzz（`cargo-fuzz`）。
5. **体积**：macOS app ≤ 15 MB（不含可选数据包）。
6. **可验证**：`scripts/verify-no-network.sh` 能证明进程无外联。

## 7. Phase 2：拼音引擎调研结论（横向扩展）

| 方案 | 许可 | 质量 | 体积/依赖 | 结论 |
|---|---|---|---|---|
| **自研 FSA 引擎** | 你的(Apache) | 需打磨 | **最小，纯 Rust** | **✅ 推荐主线**。参考 `inputx-pinyin`、`pure-ime`：双数组 FSA + n-gram + 模糊音规则 + 简拼 + 前缀补全 |
| `librime` FFI | BSD-3 | 最好 | C++ 大件，破坏"最小" | ⚠️ 作为**可选 feature**，不做默认 |
| `libpinyin` | **GPL-3** | 好 | 大 | ❌ 许可不允许 |
| `pinyin` crate + 数据 | MIT | 只做转换 | 小 | 🔧 作为数据来源之一 |
| `mozillazg/pinyin-data` | MIT | 字典数据 | — | ✅ 单字拼音数据源 |
| `mozillazg/phrase-pinyin-data` | MIT | 词组数据 | — | ✅ 词组数据源 |

**推荐**：拼音做成**与 `ime-table` 同构的第二个引擎**，复用同一套 `Engine` trait 和 `ime-dict` 格式，只是查询/排序策略不同（FSA + Viterbi/n-gram + 模糊音 + 简拼）。数据全部用 MIT 来源。这样"拼音=横向加一个引擎"，而不是"给核心塞一个大依赖"。

**拼音要补的能力（按优先级）**：全拼 → 简拼/首字母 → 模糊音（z/zh, l/n, an/ang…）→ 前缀补全 → 整句/长词（n-gram）→ 用户学习。

## 8. 本地语音（仅调研，Phase 3+，默认不实现）

## 10. 安全与隐私工程（卖点，必须可证明）

1. **编译期断网**：核心 crate 不依赖任何网络 crate；CI 检查产物符号表无 socket/DNS。
2. **零遥测**：不收集任何数据；`docs/隐私与安全说明.md` 逐条列明。
3. **威胁模型**：词典/方案文件是唯一不可信输入 → 解析器 fuzz + 长度/深度上限。
4. **内存安全**：`ime-core`/`ime-table`/`ime-pinyin` `#![forbid(unsafe_code)]`；unsafe 只在 `ime-ffi`。
5. **可复现构建**：固定工具链（`rust-toolchain.toml` + Docker/Nix），产物可校验。
6. **签名分发**：macOS 签名+公证、Windows Authenticode、Linux 包签名。
7. **可验证**：`scripts/verify-no-network.sh` + 抓包说明，任何人都能验证。
8. **依赖审计**：`cargo-deny` + `cargo-audit` + SBOM。

## 12. 风险登记

| 风险 | 影响 | 对策 |
|---|---|---|
| 与 WindInput 高度同质化 | 无人使用 | 明确"极简 + 零遥测 + 全开源 + 可复现"差异化；不追功能 |
| 五笔码表许可不清 | 法律风险 | 只用 Apache-2.0/MIT 来源；建 `sources.toml`；未核实不收录 |
| 五笔拼音混输体验难做 | 用户不用 | 先留接口，M3 专门做；参考 WindInput/inputx |
| Windows TSF COM 样板重 | 拖慢进度 | 先 Rust `windows` crate，卡住就退回 C++ 薄壳 |
| macOS 公证/权限 | 装不上 | 提前准备开发者账号与签名流程（WindInput 的坑） |
| 纯 Rust 跨 5 平台工作量 | 不可持续 | 竖切优先，平台宿主薄；社区化 |
| 拼音质量打不过搜狗 | 拼音阶段受挫 | 明确"不做最准，做最干净"；必要时上 librime 可选后端 |
| 依赖许可污染 | 授权被动 | `cargo-deny` 白名单，CI 强制 |

## 14. 附录：一句话总结

**用 Rust 写一个零 IO、零网络、`forbid(unsafe_code)` 的 `ime-core`；五笔作为第一个码表引擎（`yada` 双数组 Trie），把"多引擎混输"接口先留好；macOS 先用 Swift/IMK 宿主 + C ABI 竖切打通全流程，再依次补 Windows/Linux/移动端；拼音阶段用自研 FSA 加 MIT 数据横向扩展；全程 Apache-2.0、零遥测、可复现构建。差异化不靠功能多，靠"更小、更干净、可被第三方验证"。**
