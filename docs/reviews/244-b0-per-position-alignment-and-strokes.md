# 244 — D2 是「每码位一形」：组件数对不上 100% 解决 + 成字字根笔画

- 日期：2026-11-06　｜　关联：报告 240/241/242/243、ADR-189/308/309
- 产物：`modules/hanzi-structure/`（schema **v4**）、`data/learning/wubi86-readable-keys.tsv`（补 3 个字根）

## 1. 结论

报告 242 把 239 条 `partial` 归成 A/B/D 三类，并把 D 类（133 条"组件数少于码长"）判为"D2 漏拆、需要码驱动搜索"。
**这个判断是错的。** 真相是：

> **D2 的拆字序列是「一个码位一个字形」，末位的私有区字形是识别码槽。**

按这个口径重算，合体字的「组件数 ↔ 码长」**100% 对齐**（0 条例外），
D 类的"漏拆"根本不存在——漏的是我们**把中间的私有区字形当垃圾丢了**。

## 2. 证据链

| 观察 | 数值 |
|---|---|
| B0 的 1,000 字里 `len(D2 字形) == len(全码)` | **957**（其余 43 条是单字根/成字字根等特例） |
| 只在**末位**出现的私有区字形 | **15 个**（恰好等于识别码字母数） |
| 同一私有区字形出现在**中间**位置 | 38 个（它们是"无法渲染的字根"，不是识别码） |
| 例：`是 jghu` | D2 = `日 一 [PUA] [PUA]` → 中间是「止」的字根占位，末位是识别码 u |

之前 v3 只把 BMP 私有区当占位、把补充区一律丢弃，于是中间的补充区字根被删掉，组件数就少了——
239 条 `partial` 大多由此而来。报告 242 §4 说的"173/176 的已知组件键序列是码的子序列"，
其实是这个对齐规律的副作用，不是"可以按码补齐"的暗示。

## 3. 改了什么（schema v4）

1. **末位私有区 = 识别码槽**：D2 与全码等长时，末位私有区字形整位丢弃，识别码由全码末位给出；
2. **其余私有区 = 占位字根**：保留为 `components[i] = null`，键位取 `code[i]`，仍**不含任何 PUA**；
3. **成字字根笔画推导**（`strokes`）：全码形如「键 + 首/次/末笔」时直接得到笔画序列；
   `XXLL` 的单笔画按"连打两次 + 补 LL"；
4. `positionMismatch`（诊断字段）：字形键与码位不一致的位次。D14 只收常用字根，复合字形会误报，
   所以**只做诊断、不据此降级**。

D14 顺手补了 3 个成字字根（都可由全码首字母核验）：`了:b`、`也:b`、`上:h`。

## 4. 覆盖变化（B0，1,000 字）

| 指标 | v3（报告 243） | v4（本次） |

| `full` | 759 | **714** |
| `partial` | 233 | **278** |
| `unknown` | 8 | 8 |
| 识别码可解释 | 525 | **622**（+97） |

**`full` 从 759 降到 714，是刻意的。** 少掉的 56 条都是"中间有未识别字根、v3 却丢了它并判 full"的条目；
多出的 11 条是成字字根笔画（`也 一 用 门 儿 力 车 刀 七 乃` 等）转 full。
按 ADR-309 的口径，**宁可少说，也不把未知字形说成已知**。

## 5. 这一轮没做的事（以及为什么不做）

- **码驱动拆法搜索**：原本以为能补 133 条，实际不需要——对齐规律一改，0 条对不上；
- **真笔画数据**：`strokes` 是**取码笔顺**（全码反推），不是笔顺教学数据，spec 与讲解文案都已写明；
- **解中间那 297 个占位字形**：需要字形库（BMP 私有区字根），属后续 corpus 工作。

## 6. 可解释性样例

```
用 「etnh」｜成字字根（丿乙丨）｜报户口 E + 首笔撇 + 次笔折 + 末笔竖（按五笔取码规则，非笔顺教学数据）
一 「ggll」｜成字字根（单笔画：连打所在键 G 两次，再补 LL）
和 「tkg」｜字根：禾(t) 口(k)｜2 个字根不足四码：末笔横 + 结构左右 ⇒ 识别码 g
是 「jghu」｜字根：日(j) 一(g) ？(h)｜拆解待核验（第 3 个字根字形未识别）｜参考识别码 u
```
