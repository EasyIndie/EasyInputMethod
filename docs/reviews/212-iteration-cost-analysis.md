# 212 迭代与验收耗时分析（0.1.14 一轮的实测拆解与优化建议）

> 目的：用这一轮（0.1.14，2026-10-26）的真实数据找出「迭代慢、验收久」的原因，给出可执行的优化项、预期收益与风险。
> 结论先说：**慢的主因不是产品复杂度，而是"每个小改动都要走一遍完整流水线"+"必须在真机上人工确认的环节没有批处理"**；其中约一半可以不改规则就压掉。

## 1. 实测数据（本轮）

| 项 | 数据 |

## 2. 耗时根因（按影响排序）

1. **一改动一 PR、一 PR 一次全量 CI**（本轮 12 个 PR）。
   `macos` job 中位 9.2 min；合并后 main 再触发 acceptance（8.6 min）。改动越小，固定开销占比越高。
2. **真机验收没有"一条命令跑完"**。
   单机一轮要 4 条命令 + 人工判读（auto-acceptance / quality-samples / memory-gate / 网络采样），两台机器还要串行来回切；每次换包又是「停宿主 → 换 → 起 → 等 preflight」。
3. **必须人在场的环节没有批处理**（最大隐性成本）。
   移除/添加输入源、VO 复听、切 Space、唤醒——每类都要一次对话往返；一次试听失败（VO 秒退、输入上下文掉 ABC）就要再来一轮。
4. **环境黑箱，排查时间不可控**。
   这轮踩到：air 锁屏（唤醒前一切 GUI 自动化全废，浪费约 30 min）、`open` 起的 VoiceOver 秒退、第三方输入源无法用 TIS/⌃Space 切换、macOS 27 的 Safari 标题不随输入更新、多实例 TextEdit、首个按键被窗口激活吞掉。每一条都要现场取证。
5. **探针覆盖不足导致"装完才发现"**。
   build 22 的播报其实发了，但发在非 AX 元素上——这类"灯下黑"只能靠装包+人耳发现；现在有了 `candidateContainerIsAccessibilityElementForTesting` 这类断言，但同类契约（面板在屏内、播报文本、AX 树形状）还没成体系。
6. **文档成本与重复**。
   207/209/210 三份报告贴了高度相似的表；每轮还要改 HANDOFF + 发布说明 + 清单。
7. **我自己的等待方式**。
   用的是"提交 → 轮询 CI → 合并"的阻塞式节奏，CI 的 96 min 里相当一部分是干等。

## 3. 优化项（按性价比排序）

### 3.1 立刻可做，不改任何规则

| 项 | 做法 | 预期收益 | 风险 |
|---|---|---|---|
| **A. 批量合并** | 一次批次（例如"工具修正"或"一份报告+其配套脚本"）只开一个 PR，做完一起上；AGENTS 本来就是"固定 dev 顺序迭代、每批只推一个待合并 PR" | 12 个 PR → 3–4 个，CI 等待墙钟 **-60~80 min** | 无（本来就是约定，是我这轮没遵守） |
| **B. 一条命令跑完单机验收** | 新增 `make macos-acceptance-full OUT=...`：preflight → auto-acceptance → quality-samples → memory-gate → 网络采样 → 汇总 JSON + 报告骨架 | 每台机器每轮 **-10 min 编排**，且不漏项 | 低（只是编排，不改判定） |
| **C. preflight 前移环境检查** | 把"屏幕是否锁定""多实例客户端""当前输入源是否真的是萤火虫"三类检查放进 `acceptance-preflight.sh`，不满足直接 BLOCKED | 避免 air 锁屏那类 **30 min 死路**与两次假 FAIL | 低 |
| **D. 人在场的动作一次收完** | 换包前给一张清单：切 ABC → 移除源 → 我装 → 你加回源 → 我跑自动项 → 最后一次听 VO / 切一次 Space / 唤一次醒。全部排在同一个 15 分钟窗口 | 往返 **14 次 → 5 次以内** | 低 |
| **E. 报告模板化** | 新报告只写"新增结论 + 证据路径 + 与上一份的差异"，公共表格引用而不复制 | 文档时间 **-30%**，且更容易读 | 低 |
| **F. 非阻塞式等 CI** | 提交后继续做下一件事，合并前统一收；不用 `gh run watch` 死等 | 把 96 min 的等待变成并行工作 | 无 |

### 3.2 需要一条 ADR（结构性）

| 项 | 提议 | 预期收益 | 风险/代价 |
|---|---|---|---|
| **G. 证据绑定产物 SHA，而非"时间"** | 现规则是"历史 PASS 不继承"。改为：**PASS 绑定"被验产物的 SHA-256"**——若新候选的执行 SHA 与已验包完全相同（只改了文档/工具），该项证据继续有效；SHA 变了才必须重跑。这条能同时满足"历史 PASS 不继承"的本意（防的是"包变了还用旧结论"） | 本轮在 build 23 上有大量重复劳动可省；后续每轮 **-20~30 min × 2 台** | 需要 ADR；判定要严格用 SHA，不能用版本号/提交号 |
| **H. CI 分层（fast lane）** | `tools/**`、`docs/**`、`scripts/**` 走轻量 job（py 单测 + swiftc 编译探针），只有 `crates/**`、`platforms/**`、`data/**` 触发完整 `macos` job 与 acceptance | 工具/文档类 PR 反馈 **9.2 min → ~2 min** | 需要改 workflow；要保证 path 过滤不漏（现有 `ci-detect-code-changes.sh` 可扩展） |
| **I. 验收包只在产品码变化时构建** | main 上只改文档/工具时跳过 `macos-acceptance`（或改为手动） | 每次合并 **-8.6 min**（本轮 9 次 = 77 min 的 runner 时间） | 需要保证 release 时能找到对应提交的验收产物（找不到就手动触发，已有 `workflow_dispatch`） |

### 3.3 中期（工程投入较大）

| 项 | 说明 | 收益 |
|---|---|---|
| **J. 输入源切换自动化** | 已验证 `axmenu press` 能改全局选择；对已运行 App 无效时可自动重启该 App 再验证 `imetype` 的 `current_source` | 每轮少 1–2 次往返，人工步骤只剩"移除/添加" |
| **K. 播报/AX 契约测试成套** | 把"容器必须是 AX 元素""播报文本""面板在屏内""选中项可读"做成离屏断言集合 | 把 build 22 那类返工（~40 min + 2 次往返）挡在出包前 |
| **L. 自托管 Mac runner 夜间跑验收** | 每晚对 main 跑 `make macos-acceptance-full` 两台机器并行；白天只跑受影响项 | 把验收从"人盯着"变成"早上看报告" |
| **M. VO 验证降级为"AX 取证 + 一次人耳"** | 每轮只留一次人耳确认（在候选锁定后），其余用 `axobserve` 客观取证 | 每轮少 2–3 次试听往返 |

## 4. 建议的推进顺序

1. **本周先做 3.1 的 A–F**（不动规则、当天见效）：批量合并 + `make macos-acceptance-full` + preflight 前移 + 人的动作清单 + 报告模板 + 非阻塞等 CI。
2. **再写 ADR-293 讨论 G/H/I**（证据绑定 SHA、CI 分层、按需出验收包）——这三条是结构性的，能再砍掉一半固定开销。
3. **J/K 随下次产品改动一起做**；**L/M** 视是否有常开 Mac 决定。

## 5. 一句话

慢的不是"验收项太多"，而是**同样的东西被重复验、每验一次都要人陪、每次改动都付一次固定开销**。
A–F 六条当天就能把这一轮 9 小时的同类工作压到 5–6 小时；G–I 批下来后能稳定在 3–4 小时量级，而且证据强度不降反升（绑定产物 SHA 比"记得上次验过"更硬）。
