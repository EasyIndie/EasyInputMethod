## 3. 工具链缺陷（都已修，逐条给根因）

### 3.1 `perf-session.sh` 的 `--self-post` 不计 IME，指标会被虚高

- 现象：`round-*.json` 里 `has_non_ascii=false`、`keys_seen=0`、`text="wq nihao xuexi ."`（纯 ASCII），
  但脚本仍照常统计出 `p50 2.9ms / p95 7.19ms` 并判 PASS。
- 根因：自投递把事件直接塞进测试窗口的队列，绕开了 IMK 的事件路径，输入法没有参与——
  测到的是**测试窗口自己的文本变更延迟**。
- 修法：`perf-session.sh` 丢弃 `has_non_ascii=false` 或 `keys_seen=0` 的 round；
  一条有效 round 都没有时输出 `{"result":"BLOCKED","reason":"所有 round 都没有走 IME…"}`、退出 78。
- **影响**：历史 p95 数字（报告 191/199/207 等）需在修好的 harness 上复核，不能直接继承。
- 旁证：同一条 imetype app 走 **HID** 路径时 `keys_seen=16`、`text="你你好学习。"`、`has_non_ascii=true`
  —— 说明 IME 本身正常，是自投递路径的问题。

### 3.2 相对 `OUT` 让测速 app 把结果写到别处

- 现象：`keys=0`、`$OUT/perf` 里一个 `round-*.json` 都没有。
- 根因：`open -n` 拉起的 app 工作目录是 `/`，脚本把**相对路径**当 `--out` 传过去。
- 修法：`perf-session.sh` 把 `OUT` 规范成绝对路径；另外补一条「一个 round 都没产出 → BLOCKED」。

### 3.3 客户端矩阵：顺序、终端项与「回读为空」的判定

- **顺序**：客户端矩阵结尾会把输入源还原成 ABC，而性能项开头要选回第三方源——
  之前把客户端矩阵排在前面，导致性能项即使修好路径也可能拿不到 IME。现在**性能在前、客户端在后**。
- **终端项改用系统 Terminal.app 后实测不可用**：`do script` 的前台窗口不确定，
  `cat > 文件` 收不到按键，按键有落进**用户自己的 shell 会话**的风险（本轮已发生一次，未见残留）。
  因此终端项从自动化矩阵**移除**，只留一条 `{"status":"SKIP"}` 记录，仍由 `T-ITER-22 §3.5` 人工覆盖；
  顺带符合「不用 Ghostty」的设备偏好（旧实现用的是 Ghostty 独立实例）。
- **回读为空 ≠ 产品 FAIL**：Chrome（已知 Chrome 侧问题）、Safari（macOS 27 标题不随输入更新）、
  Xcode（编辑器未取到焦点）会出现「按键投递成功但读不到落点」。现在这类计入 `BLOCKED` 并在摘要里写明，
  要求 `attempted ≥ 4` 且全部取证才 PASS——**不拿空结果冒充通过**。
- 性能项选源后新增回读校验：选不中第三方源就是 `BLOCKED`（报告 095 的老坑）。

## 6. 追加实验：合成事件能不能进 IMK（2026-11-06）

为判断"自投递没走 IME"是**实现选择**还是**平台限制**，做了三组对照（都在 1.1.0 已装包上，实验产物用完即删）：

| 投递方式 | 代码改动 | `text` | `keys_seen` | `has_non_ascii` | 结论 |
|---|---|---|---|---|---|
| `view.keyDown(with:)`（现状，`--self-post`） | 无 | `wq nihao xuexi .` | 0 | false | 绕开输入上下文，纯 ASCII |
| `window.sendEvent(_:)`（实验） | 一行 | `wq nihao xuexi .` | 0 | false | 同样不触发 IMK |
| `CGEvent.postToPid(self)`（`--tap self`） | 无 | 空 | 0 | false | 根本没投递进窗口 |
| `CGEvent.post(.cghidEventTap)` + 窗口在前台（`type-session.sh`/`keytopid`） | 无 | `你你好学习。` | 16 | **true** | **只有走窗口服务器的真实事件才会进 IMK** |

结论：`runSelfPost` 里那句「经输入上下文走真实 IME 往返」的注释是**错的**——进程内合成事件进不了
`NSTextInputContext`，所以在 `--self-post` 下无论怎么改调用层级都测不到输入法往返。

因此延迟门禁只有两条可行路线：
1. **HID 投递 + 被测 app 内计时**（`keyDown` 到达 → `NSText.didChange`）：保留精确时间戳，
   只缺"窗口服务器→app"的那一段（亚毫秒）；需要窗口在前台，`guard-focus` 已具备。
2. **HID 投递 + 外部 AXObserver 计时**：不改被测 app，但引入 AX 通知开销。
3. 兜底：物理键盘人工采样（报告 115/120 的协议），自动化只做回归。

在此之前 **不得宣称「16ms 达标」**；真实 IME 往返的历史数据只有物理键盘那几次
（报告 115：total p95 21.2ms；报告 120：p95 10.478ms / max 67.125ms），本身就不是稳定达标。
