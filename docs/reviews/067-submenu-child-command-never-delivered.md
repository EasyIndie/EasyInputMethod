因此首次结论成立，且不是输入法切换造成的误判：**子菜单子项点击不产生任何命令**。

## 结论

在 macOS 27.0.1 上，本输入法的 IMK 输入菜单：

- **顶层菜单项命令可靠**（状态切换、关于、设置）；
- **子菜单子项的点击不会产生任何命令**（不是“投递了错误项”，是完全没有到达）；
- 因此“父项循环 + 子菜单直接选择”这个组合在 IMK 下**无法实现**：挂上子菜单后父项点击被系统吃掉，子项点击又不下发。

这不是候选实现的缺陷，也不是签名、selector、自定义 view 或 A/B 测试方法的问题——两套完全不同实现 + 带日志诊断包给出一致结果。

证据：`build/native-mode-menu-20261017/trace-20261018.log`（484 行，含完整菜单树与 0 条 CMD/APPLY）、`diag-manifest.json`。

## 设计取舍

- **A. 平铺**：父项 `输入模式：X`（点击循环，无子菜单）+ 混输/五笔/拼音三项平铺带勾选。菜单多 2~3 行，但全部走已验证可用的顶层通道。
- **B. 单行循环（原 MVP 交互）**：只保留 `输入模式：X`，点击循环（去掉子菜单后自定义 view 的 `mouseUp` 才能收到点击）；直接三选一保留在设置页与 `ctrl+shift+m`。不新增条目，最接近“原方案”。
- **C. IMK 原生 modes**：把 mixed/wubi/pinyin 声明为 TIS 输入模式，子菜单由系统绘制并投递。最接近“菜单内直接三选一”的 UX，但属于架构级改动（模式状态改由 TIS 源驱动，需要迁移与独立验收）。

建议先按 **B** 恢复原交互并实测（改动最小、可立刻验证），若确实需要菜单内直接选择，再评估 C。
