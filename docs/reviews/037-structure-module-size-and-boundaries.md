# 037 自建结构库的包体积与可拆分模块边界

2026-10-16。用户要求：评估体积；现阶段主仓库内目录独立，便于以后迁出/下沉。ADR-189采纳目录及资源分层；报告036的具体数据模型/算法、全量覆盖与性能仍待试点确认。本轮不创建产品代码或迁移既有数据。

## 1 结论

自建结构库不必全部进入输入法包；体积主要取决于发布哪些运行资源，而非数据由谁建设。采用“源库/工具”和“编译后教学资源”分层有利于控制体积，但全量新包尚未生成，不能承诺增量只有几百KB或必然很小。

现阶段建立`modules/hanzi-structure/README.md`，约定模块自包含、主项目单向消费产物。只做目录隔离，不引入Git submodule、独立仓库或新网络依赖。后续结构/规则实现放在该边界内，现有学习数据/编码器保持原位。

## 2 本地实测与推算边界

[测量脚本](../research/structure-size-20261016/measure.py)与[结果](../research/structure-size-20261016/observations.json)记录源文件哈希。运行：

```sh
python3 docs/research/structure-size-20261016/measure.py \
  --project-root /path/to/EasyInputMethod \
  --app /path/to/Lampyris.app
```

不传app即可只测代码工作树；脚本只读，不写产品数据。安装包是旧1621a6d基线，与未生成的新教学包不可直接作净增量比较。

| 当前对象 | 实测字节 | 含义 |
|---|---:|---|
| 全码索引 | 222,584，约217.4 KiB | 27,823字符×8字节，只有全码，不等于完整拆字 |
| 教学TSV | 325,506，约317.9 KiB | 3,597条记录，仅112条现有完整说明，其余有明确缺失 |
| 上述两项合计 | 548,090，约0.523 MiB | 原始输入数据大小，不等于二进制或新增包大小 |

纯算术情景，**不是已实现格式的测量或体积承诺**：

| 假设每字记录平均字节数 | 27,823字记录小计 |
|---:|---:|
| 64 | 1.698 MiB |
| 128 | 3.396 MiB |
| 256 | 6.793 MiB |
| 512 | 13.585 MiB |

小计不含共享字根/规则池、索引/头部、读取/呈现代码、几何/字体、签名对齐，也未扣除被替换旧数据或计算压缩。达到哪一档必须由有足够字段的真实样本编译证明；不能为了卡预算丢弃中间根、依据或完整说明。相对10.57 MiB基线，几MiB增量仍然有意义，不能直接称“可忽略”。

现实现`ime-table/src/learning.rs`用include_bytes/include_str嵌入以上数据；macOS按两个架构分别静态链接后合并universal可执行文件。按此构建方式，大资源可能分别存在于两个架构切片，单纯把Rust源码移入另一个crate不能消除重复。以共享资源文件保存则可避免按架构嵌入同一数据，但需要另行设计装载/验证/FFI迁移，不在本轮改动。静态库包含依赖这一链接属性亦见[Rust官方链接说明](https://doc.rust-lang.org/reference/linkage.html)。

## 3 分层策略

| 层 | 典型内容 | 输入法默认包的关系 |
|---|---|---|
| 编辑源库 | 结构图、笔顺事实、自绘源资产、作者/审核证据、分析候选 | 开发和配套源码保留，不整库复制进App |
| 教学运行资源 | 完整根序、取码/省略/识别码依据、共享根/模板索引、小型必要图形 | 已承诺学习功能所需部分随包离线可用；同一运行包不重复嵌入多处 |
| 扩展显示/教程资源 | 逐笔几何、高分辨率图、课程、多版本对照、罕见字字体 | 独立分层；按功能需要选择是否随包，非默认资源只由用户显式本地导入等离线流程提供，不自动下载 |
| 构建工具 | 校验器、分析器、生成器、测试语料 | 不进入输入服务，不常驻运行 |

多版本共享事实和图形，按版本保存规则与不同取码结果，避免复制三套完整图形库。运行记录引用共享池，文案由规则参数派生；具体存储和压缩格式待试点，不为了体积先引入新依赖。

安装体积与RSS分开验收：不加载的图片仍占安装包；压缩资源若启动时全量解压成对象也可能增加RSS。后续测冷启动、首次/重复学习查询、长词、资源未启用及几何显示峰值，区分输入服务与教程窗口。核心零IO/零网络约束保持，加载责任另决策。

## 4 模块拆分契约

`modules/hanzi-structure/`的README是本轮落地的目录边界。后续按需增设spec、corpus、schemes、assets、tools、tests、provenance，保持事实与五笔版本规则分层。

- 模块不导入ime-*或平台UI，不读用户配置，不依赖父目录data/、主仓库git状态或Makefile。
- 显式输入目录/方案/输出目录，内部引用相对模块根；依赖和工具链在模块内申明/固定。
- 主项目只消费版本/哈希明确的静态产物与契约，适配器留在主项目；不能从模块反向读取主项目源码来取得规则。
- 将来复制模块到临时目录，离开父仓库仍能校验和构建，输出一致，才算通过可迁出验收。本轮只有文档，未执行此构建验收。
- 数据、规则、schema、生成器版本分别记录；独立来源链和质量统计随模块迁移。具体资产许可仍需逐项登记，目录独立不代替数据准入。

模块边界有利于独立迭代；Git submodule是以后独立仓库的一种接入选择，两者不等同。其具体语义见[Git官方文档](https://git-scm.com/docs/gitsubmodules)。现阶段普通目录足够。
