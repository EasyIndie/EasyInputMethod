### 4.2 首键 +4.6 MiB 的归因

从 A/B 留下的 `vmmap` 快照里读 MALLOC ZONE 表的**存活分配**（字节与个数），而不是「私有已提交」：

| 包 | 时点 | 存活堆 MiB（逐轮） | 存活分配个数（逐轮，千） |
|---|---|---|---|
| 旧 | first-key | 5.2 / 5.2 / 5.2 / 5.2 / 5.2 | 26.7 ×5 |
| 新（两次共 8 轮） | first-key | 5.1 / 5.2 / **19.2** / 5.2 / 5.2 / 5.2 / **19.4** / **19.2** | 26.7 ×5，**188–191 ×3** |
| 旧 | six-words / idle-8s | 20.5–20.6 / 20.4–20.5 | 188–189 |
| 新 | six-words / idle-8s | 21.0–21.2 / 20.9–21.2 | 190–193 |

1. **首键时点的存活堆只有两种状态**：5.2 MiB（约 2.67 万个分配）或约 19 MiB（约 19 万个分配）。差的那 14 MiB 就是码表与拼音数据。
   引擎数据由会话以 `Arc` 持有、缓存只留 `Weak`（`ime-ffi/src/data.rs`）——**没有任何会话存活时数据整体释放**。
   所以这个时点测到的是「测试窗口退出后，是否恰好有别的客户端的输入会话已经激活」，而不是首键路径分配了多少。
2. 新包 8 轮里 3 轮处于「有会话存活」状态，旧包 5 轮里 0 轮；把这 3 轮按「私有已提交」算进中位数，就得到了 +4.6 MiB。
   **在「无会话存活」的那 5 轮里，新包的存活堆与旧包完全相同**（5.2 MiB，分配个数相差不到 30）。
3. 这是采样时机问题：13 轮里共 3 轮「有会话」，全落在新包的概率按超几何分布约 20%，不足以说明是新代码造成的；
   新增代码里也没有会延长控制器或会话生命周期的引用（闭包均为 `weak self`，`AppLanguageMemory` 只存字符串与布尔）。
   **不能完全排除**新包让别的客户端更早激活，但没有找到机制。
4. **稳态存活堆新包多约 0.5 MiB**（21.0 vs 20.5，分配多约 1,500–4,000 个）。这是真实增长，量级与「每次组合多保留几十个补全/分段候选、
   `Candidate` 多一个字段、更多配置项」相符，未进一步拆分。
5. 「私有已提交」在首键时点远大于存活堆（23–28 MiB 对 5.2 MiB）：多出来的是分配器已释放但尚未归还系统的页。
   该口径受采样时机与碎片影响大，这也是 §4.1 里同一份包三次判定不一致的原因之一。

**结论**：首键内存不需要改产品代码。**工具已改**：`memory-gate.sh` 的每个采样现在额外输出 `heap_live_mb` 与 `heap_allocations`
（只作参考、不参与判定），以后能直接区分「数据真变多了」与「分配器残留 / 会话是否存活」。

**对冷首键延迟的含义**：数据随最后一个会话释放，意味着「所有输入框都失焦后的第一次按键」要重新读盘解析码表——
这很可能就是冷首键 30 ms 量级延迟（ADR-307）的主要来源，且与本批改动无关。是否改成「宿主存活期间常驻数据」是内存换延迟的取舍，
需单独立 ADR（会让无会话时的常驻内存从约 5 MiB 升到约 20 MiB）。

### 4.3 重启后重测（2026-11-12 夜，用户重启电脑后）

条件：开机后等 1 分钟负载降到 4 以下再开始；全程 **swap 用量 0**，负载 1.3–3.7。同一配置（学习区开，门槛 34 MiB），各 5 轮，新 → 旧 → 装回新。

| 包 | 时点 | 「私有已提交」逐轮 | 中位数 | 存活堆 | 判定 |
|---|---|---|---|---|---|
| 新 `f38e4e1a…` | six-words | 35.0 / 37.5 / 37.2 / 37.4 / 37.6 | **37.4** | 20.1–20.2 | FAIL |
| 新 | idle-8s | 34.9 / 37.3 / 37.0 / 37.3 / 37.5 | **37.3** | 20.1 | |
| 新 | first-key | 33.2 / 34.1 / 33.0 / 32.7 / 34.4 | 33.2 | 19.2 / 5.1 ×4 | |
| 旧 `3eeeb0aa…`（1.2.1 发布版） | six-words | 37.3 / 37.5 / 37.5 / 37.3 / 37.7 | **37.5** | 20.2 | FAIL |
| 旧 | idle-8s | 37.2 / 37.3 / 37.3 / 37.2 / 37.5 | **37.3** | 20.1 | |
| 旧 | first-key | 33.0 / 33.1 / 32.4 / 33.3 / 34.1 | 33.1 | 5.1 ×5 | |

结论：

1. **新旧包没有差别**：稳态中位数 37.4 对 37.5、37.3 对 37.3，存活堆都是 20.1–20.2 MiB，首键时点也一致。§4.1 里看到的差异全部是测量噪声。
   本批改动（ADR-325…336）**没有内存回归**。§4.2 说的「稳态存活堆 +0.5 MiB」在干净状态下也不成立（那是用户词库与系统状态的差异）。
2. **已发布的 1.2.1 在干净系统上同样过不了这道门禁**（5 轮全超，约 37.3–37.7 对 34）。门槛失效与本批无关。
3. **「私有已提交」这个口径随系统内存压力反向变化**：swap 用满时 31–34 MiB，swap 为 0 时 35–37.6 MiB，而存活堆始终约 20 MiB。
   差出来的 13–17 MiB 是分配器已释放但系统尚未回收的页——内存紧张时被回收（数字变低），内存宽裕时留着（数字变高）。
   它量的主要是系统状态，不适合做有固定门槛的门禁。首键时点最能说明问题：存活堆只有 5.1 MiB，这个口径却报 33 MiB。

**已落地（ADR-338，2026-11-13）**：门禁判定口径改为 `heap_live_mb`，门槛 24 MiB，不再按学习区分档；「私有已提交」与 footprint 降为参考项。
用 `ANALYZE_ONLY=1` 对本报告的 5 组快照（共 23 轮）重新判定：全部 PASS，稳态存活堆 20.1–21.2 MiB。

结束状态：已装回新包 `f38e4e1a…`（`3e428b7`），宿主跑新二进制，输入源为萤火虫。证据：`50-mem-reboot-*.txt`、`51-mem-reboot-*.txt`、`memory-reboot-new/`、`memory-reboot-old/`。
